网上流传的「RK3588 跑 YOLO」数字差两个数量级，因为**测的是三件不同的事**。必须分清：

[go-rknnlite example/README](https://github.com/swdee/go-rknnlite/tree/master/example#yolo-benchmarks)，

### 2.2 多输出导出 + 3 核满载的吞吐上限

[rknn_model_zoo#454](https://github.com/airockchip/rknn_model_zoo/issues/454)（2026-09-23，**目前 0 回复**）——
一份自称实测的数据，3 核满载、满频、空载、zero-copy：

| Model | 640 | 480 | 320 |
|---|---|---|---|
| **YOLO11n** | **162 FPS** | 279 | 557 |
| YOLOv8n | 199 FPS | 330 | 649 |
| YOLO11s | 85 FPS | – | – |

原文还给了几条**对多模型流水线极其关键**的话：

> **Export path affects FPS materially.** This repo's multi-output (9-output) export is noticeably faster than
> ultralytics' single-output `format=rknn` export — **162 vs 134 FPS for YOLO11n@640 in our testing (~20%)**.

> **The NPU is DDR-bandwidth sensitive, not purely compute-bound.** Running memory-heavy CPU work alongside NPU
> inference dropped FPS from 84 to 62 in our tests, while in-cache CPU compute had no measurable effect.
> **Concurrent CPU (ncnn) or GPU (Mali panvk) inference on the same board reduces NPU throughput more than raw
> core-count accounting would suggest** — worth a callout for anyone building multi-model pipelines on RK3588.

> **YOLOv8n is consistently ~20% faster than YOLO11n on this NPU** at matched resolution, despite YOLO11 generally
> being marketed as the more efficient architecture (true on GPU/CPU, not on this NPU in our measurements).

**这条要谨慎采用**：issue 至今 0 回复、未被打包进官方文档，且发帖人自述环境是 Vicharak Axon（非香橙派）。
**但「多输出导出比 `format=rknn` 快 20%」与我们现状直接相关**——我们用的正是改头的 9 输出模型
（见 `detector.py::_dfl`），也就是说我们的导出路径**恰好是快的那条**。

**含义（对我们的决策极重要）**：
- **官方 FPS 表不能用来做设计预算**，它大概率是「多核 + 理想条件 + 不含前后处理」的口径。
- 我们自己那份「改头 9 输出」的模型 + Python 前后处理，**实际很可能落在 15–30 FPS 而不是 60 FPS**。
- 这与第 2.2 节 #454 的「160 FPS」差得更远——**再次印证：那些数字是吞吐上限，不是我们的帧率。**

### 2.5 ⭐ 最接近我们的数字：纯 Python RKNNLite 端到端实测

前面三个数字都是 C++ 或纯 NPU。**我们跑的是 Python + RKNNLite + OpenCV**，这是完全不同的量级。
找到一份**源码已核实为真 Python RKNNLite 端到端循环**的实测（含解码 → 前处理 → NPU → NMS → 渲染）：

`leafqycc/rknn-multi-threaded`，`rknnpool.py` 原文确认用的是 `from rknnlite.api import RKNNLite`，
且**每个实例绑一个核**（`init_runtime(core_mask=RKNNLite.NPU_CORE_0/1/2)`）：

```python
def initRKNNs(rknnModel, TPEs=1):
    rknn_list = []
    for i in range(TPEs):
        rknn_list.append(initRKNN(rknnModel, i % 3))   # ← 每实例绑一核
    return rknn_list
```

README 的多线程帧率表（`yolov5s_relu_tk2_RK3588_i8.rknn`，OpenCV 视频循环）：

| 线程数 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| yolov5s FPS | **27.4** | 49.1 | **65.4** | 63.3 | 71.8 | **72.1** |

**Python vs C++ 的代价（同一作者、同模型、同池化方法）**——C++ 版 `leafqycc/rknn-cpp-Multithreading`：

| 线程数 | Python | C++ | Python 相对损失 |
|---|---|---|---|
| 1 | 27.4 | 41.6 | **−34%** |
| 3 | 65.4 | 98.6 | **−34%** |
| 6 | 72.1 | 114.7 | **−37%** |

> **Python 固定损失约 1/3 吞吐，且与线程数无关**（说明瓶颈在解释器/GIL 开销，不在 NPU）。

另一个独立佐证（`AndrewJNg/NPU-on-rk3588` issue #1，Orange Pi 5，OpenPilot 模型）：

> iXcess：I am already running using the C++ rknn_api, **10ms savings** for the latest model compared to using
> python, **not worth**.

**对我们的直接含义**：
- 我们**单实例**（`Detector` 只 init 一个 RKNNLite）、**单线程**推理 → 大概率落在 **20–30 FPS** 量级，
  前提是前后处理不拖后腿。
- 若前后处理重（我们的 `_dfl` 纯 numpy 逐尺度 softmax + `cv2.dnn.NMSBoxes`），**会更低**。
- **想上 60 FPS，唯一途径是多实例池化绑核**（`core_mask=i%3`），而不是让单模型吃 3 核——
  见 6.1/6.2 的官方说明（小网络多核收益有限甚至退化）。

⚠️ **仍须注意**：上表是 **YOLOv5s**，不是 YOLO11n；且各人前后处理不同。
**这是我们能找到的最接近的参照，但仍不等于我们的数字——必须实测。**

### 2.6 综合判断（我们该预期多少）

**这三个数字都不是「我们的帧率」**，因为我们的 `Detector.detect()` 里还有 Python 侧开销：

- `letterbox()`：`cv2.resize` + `np.full` + 切片赋值，**1080p→640 缩放是 CPU 大头**
- `cvtColor` + `transpose(2,0,1)` + `[None]`：1080p 全图两次拷贝
- `_dfl()`（9 输出路径）：纯 numpy 做 3 个尺度的 softmax 期望，比标准头重得多
- `cv2.dnn.NMSBoxes`：Python 侧 NMS
- **rknnlite Python 绑定本身**：`inference()` 每次跨 CPython ↔ C 边界 + list/np 转换

**结论：板端实际 per-frame 总耗时大概率在 30–80ms（12–30 FPS）量级，而不是 15.6ms。**
结合 2.6 的 Python 实测（单实例 27.4 FPS = 36ms/帧，含前后处理），**我们的合理预期是 15–30 FPS**。
这是我们**必须实测**的东西——代码里已经有现成的 `detector.timing`（preprocess/inference/postprocess/total），
`viewport.py` 每帧都打印了。**先看这行日志再谈优化**，别信任何二手数字。

⚠️ **诚实标注**：我**没有找到**「香橙派 5 Plus + rknn-toolkit-lite2 + YOLO11n + 我们的前后处理」的公开实测。
2.6 那个 27.4 FPS 是 YOLOv5s 的数字。**这仍属于推断，必须实测。**
速算法：若日志显示 total ≈ 35ms → 28 FPS；若 ≈ 70ms → 14 FPS。**这个数直接决定下面所有取舍。**

**一句话总结本节**：官方标 64 FPS，实测有人报 68ms（14.7 FPS），Python 实测约 27 FPS —— 
**同一个板子、同一个模型，数字差 4 倍以上，全看流水线条件。所以「我们的帧率」只能自己测。**

## 三、「人走快了就丢 ID」的真正机理

这是本文最核心的一节。用户的痛点是表象，机理有三层，**按可能性排序**：

### 3.1 第一层（最可能）：现 tracker 根本没有运动模型

读 `slintui/vision/tracker.py` 原文：

```python
class ByteTracker:
    def __init__(self, high_conf=0.4, iou_thresh=0.3, max_age=10, min_hits=2):
```

```python
    def _match(self, dets, track_ids=None):
        ...
        for i in ids:
            for j, d in enumerate(dets):
                v = iou(self.tracks[i].box, d[:4])   # ← 只用「上一次的框」算 IoU
```

**关键点：`self.tracks[i].box` 是上一帧的检测框本身，没有任何位置预测。**
人走得越快，帧间位移越大，两帧框的 IoU 越小。当位移超过约一个框宽时 IoU 就归零，**必然配对失败**。

用我们的参数算一下：`iou_thresh=0.3`。对同尺寸框做纯平移，IoU 掉到 0.3 时位移约 0.55 倍框宽。
走廊里人框宽约 60px（1080p）→ 帧间位移 > 33px 就丢。
若实际 15 FPS，即 **> 500 px/s 就丢**；人正常步速 1.2m/s，若在 2m 宽的画面里横穿约 900px/s
（走廊纵深方向更夸张）→ **走快一点必然丢**。这完全解释了用户观察到的现象。

### 3.2 第二层：ByteTrack 的 Kalman 就是为解决这个而生的

上游 [ifzhang/ByteTrack](https://github.com/ifzhang/ByteTrack) 的 `STrack` 维护 8 维状态
`(x, y, a, h, vx, vy, va, vh)`——**后 4 维是速度**，用匀速模型外推位置：

`yolox/tracker/kalman_filter.py`：

```python
    def initiate(self, measurement):
        mean_pos = measurement
        mean_vel = np.zeros_like(measurement)
        mean = np.r_[mean_pos, mean_vel]

        std = [
            2 * self._std_weight_position * measurement[3],   # x
            2 * self._std_weight_position * measurement[3],   # y
            1e-2,                                             # aspect ratio
            2 * self._std_weight_position * measurement[3],   # height
            ...
        ]
```
默认 `std_weight_position = 1./20`，`std_weight_velocity = 1./160`（`KalmanFilter.__init__`）。

`byte_tracker.py::STrack.predict()`：
```python
    def predict(self):
        mean_state = self.mean.copy()
        if self.state != TrackState.Tracked:
            mean_state[7] = 0          # 非 Tracked 状态把高度速度清零
        self.mean, self.covariance = self.kalman_filter.predict(mean_state, self.covariance)
```

**这就是「运动模型」**：先按速度外推，再用 IoU 匹配「预测框 vs 本帧检测框」，
而不是「上一帧框 vs 本帧框」。对快速目标，外推框基本落在真实位置上，IoU 依然很高。

### 3.3 第三层（关键工程细节）：C++ 移植版有个真 bug，而我们正好在踩

调研中专门 clone 了两个 C++ 实现对照。**发现一个必须记录的真实缺陷。**

`Vertical-Beach/ByteTrack-cpp`（277 stars，MIT，`git clone` 到 `/tmp/agents/ByteTrack-cpp`，HEAD 2024-04-08）
的 `src/STrack.cpp`：

```cpp
void byte_track::STrack::predict()
{
    if (state_ != STrackState::Tracked)
    {
        mean_[7] = 0;
    }
    kalman_filter_.predict(mean_, covariance_);
    // ← 没有 updateRect()
}
```

而 `updateRect()` 才是把 `mean_` 写回 `rect_` 的地方：

```cpp
void byte_track::STrack::updateRect()
{
    rect_.width()  = mean_[2] * mean_[3];
    rect_.height() = mean_[3];
    rect_.x() = mean_[0] - rect_.width()  / 2;
    rect_.y() = mean_[1] - rect_.height() / 2;
}
```

`updateRect()` 的调用点只有 3 处（`STrack.cpp:67, 84, 110` = activate / reActivate / update），
**`predict()` 里没有**。而 `BYTETracker::update()` 的匹配流程是：

```cpp
    for (auto &strack : strack_pool) { strack->predict(); }   // 只更新 mean_
    ...
    const auto dists = calcIouDistance(strack_pool, det_stracks);  // ← 内部读 getRect()，即陈旧 rect_
```

`getRect()` 就是 `return rect_;`，而 `calcIouDistance` → `calcIous` → `a_tracks[i]->getRect()`。

**所以：Kalman 预测算了，但算完就被丢掉，IoU 匹配用的还是上一帧的框。运动模型等于没生效。**

这不是我一个人的解读，社区里已经有人在 issue 里指出（[ByteTrack-cpp#20](https://github.com/Vertical-Beach/ByteTrack-cpp/issues/20)，
2025-01-09 开，标题 "ID Switching Issues in ByteTrack with YOLOv8"）：

> **fredcombaneyre（2025-03-03）**：The problem is that there is a bug in `byte_track::STrack::predict()`,
> where the prediction is never done. Try to add `updateRect();` at the end of this function in STrack.cpp.
> This should fix the issue. With this fix it works perfectly fine for me.

> **junhui-ng（2025-07-16）**：I encountered the same issue. In my case, **the original ByteTrack Python
> implementation works well, but the C++ implementations (including emptysoal/TensorRT-YOLOv8-ByteTrack)
> do not provide the same accurate tracking results.** I reviewed the code and addressed the discrepancies.

**对照上游 Python 为什么不踩这个坑**：因为 Python 版把框做成**计算属性**，每次都从 `mean` 现算：

```python
    @property
    def tlwh(self):
        if self.mean is None:
            return self._tlwh.copy()
        ret = self.mean[:4].copy()
        ret[2] *= ret[3]
        ret[:2] -= ret[2:] / 2
        return ret
```
（`yolox/tracker/byte_tracker.py`）

**上游没有这个 bug，是 C++ 移植引入的「缓存了派生量却忘记刷新」的经典错误。**

#### 对我们当前代码的直接含义

**我们现在的 `tracker.py` 比这个 C++ 版还差一档**（连 Kalman 都没有），
但**好消息**是：因为我们在 Python 里、且没有缓存派生量，**我们不会踩这个具体 bug**。
含义是——**加 Kalman 是有明确收益的、且上游 Python 版有正确实现可直接照抄**，不需要自己发明。

⚠️ 反向提醒：如果将来有人为了性能把 tracker 改写成 C++/Cython 并缓存框坐标，**必须注意刷新**，
否则就会复现这个 bug。这是本次调研最有价值的一条「别人踩过的坑」。

### 3.4 硬数据：帧率越低，ByteTrack 掉得越快（附量化上界）

前面 3.1 的算术是推理。这里有一份**直接量化「低帧率 → 关联失败」的论文**，我已**下载 PDF 全文逐表核对**。

[APPTracker: Improving Tracking Multiple Objects in Low-Frame-Rate Videos](https://infzhou.github.io/folder/Zhou_APPTracker_Improving_Tracking_Multiple_Objects_in_Low-Frame-Rate_Videos_MM_2022.pdf)
（Zhou et al., ACM MM 2022；`n_d` = 帧采样间隔，`n_d=1` 即原帧率）：

**MOT17 val 上的 ByteTrack（原文 Table 6/7/8）：**

| n_d | IDF1 | ID switches (IDs) |
|---|---|---|
| 1（原帧率） | **73.0** | 262 |
| 10（1/10 帧率） | **61.5** | 5282 |
| 30（1/30 帧率） | **54.9** | **8502（×32）** |

论文对 ByteTrack 的评语原文：

> Though its performance in normal-frame-rate cases is good, **it drops more quickly than other methods since no other
> information (e.g., appearance embeddings, optical flows) except motion cues is leveraged in the association.**

机理原文（Introduction）：

> First, **the displacement of objects between frames becomes larger; in some cases, two detections of the same target
> in two consecutive frames even have no overlap.** Methods that assume objects moving slightly between frames thus
> fail in low-frame-rate cases.

> Besides, the larger displacement leads to the **failure of motion models (like the Kalman filter) with zero-velocity
> initialization assumptions.**

**"two detections of the same target in two consecutive frames even have no overlap" —— 这正是我们 3.1 节算出的结果，
论文直接给了同样的结论。**

**⚠️ 但注意这条论文结论对我们的方向性**：它论证的是「**降低帧率**有害」，而不是「Kalman 无用」。
论文同时指出 Kalman 在**正常帧率**下 IDF1 = 72.0%，且：

> Without a good initial velocity estimation (the velocity of an object is usually initialized to zero) or a good
> velocity measurement, the Kalman filter fails to chase objects in low-frame-rate cases.

**含义**：Kalman 有效，但它**需要速度能被正确初始化/测量**。这支持我们 7.1 节的建议——
**先用「匀速外推」（速度直接用两帧差，等于显式测量速度）比上完整 Kalman 更稳妥**，
因为完整 Kalman 的速度初值是 0，前几帧外推不准。

#### ⭐ 附带一张极其实用的表：track_buffer 必须随帧率换算

论文附录 B（Table 5，原文 "Buffer sizes for different settings of n_d"）：

| 采样间隔 n_d | 1 | 2 | 3 | 6 | 10 | 15 | 30 |
|---|---|---|---|---|---|---|---|
| **buffer size** | **30** | 15 | 10 | 10 | 10 | 6 | 3 |

> A proper buffer size, above which an inactive tracklet is terminated, is required for preserving the identities of
> objects involved in occlusions.

**关键洞察**：`track_buffer` 的单位是**帧**，但它真实的语义是「丢失后容忍的**时间**」。
**帧率变了，必须同步换算 buffer，否则容忍时间会变。**

**对我们直接可用**：Ultralytics 的 `bytetrack.yaml` 默认 `track_buffer: 30`（我已读源码核实），
这是按 30 FPS 设计的（30 帧 = 1 秒）。**我们现在的 `max_age=10` 是「10 帧」**：
- 若实际 15 FPS → 容忍 0.67 秒
- 若实际 30 FPS → 容忍 0.33 秒

按上表 n_d 与帧率的关系，**30 FPS 场景应保持 30 帧左右**。
→ **建议把 `max_age` 按实际帧率换算：`max_age ≈ 1 秒 × FPS`。**
若实测 15 FPS，`max_age` 应约 **15**（现在 10，偏小）；这不是玄学，是有论文表格支撑的。

### 3.5 「快走丢 ID」的其它可能成因（也需要排查）

- **检测本身就是漏检**（见第五节）：tracker 再好，检测没框就无从关联。
- **抽帧/掉帧**：`viewport.py` 是「多快算多快」，帧率不稳。**帧率越低，帧间位移越大，越容易丢**。
  这形成一个恶性循环：算得慢 → 掉帧 → 位移大 → 丢 ID → 漏计。
- **`min_hits=2` 的副作用**：新轨迹要连续 2 帧命中才输出。对快走的人，可能还没攒够 2 帧就已经过线了。
- **ID 复用/清理导致丢侧别**：`counter.py` 每帧用 `alive` 集合清理已消失轨迹的 `sides` 记录
  （`sides = {k: v for k, v in self.sides.items() if k in alive}`）。
  这意味着**同一个人一旦丢了 ID 再拿到新 ID，他之前的「在哪一侧」也一并丢失**，这次过线就漏计了。
  → 这是「丢失的累计误差」的直接来源，**治本要靠减少丢 ID**（3.1/3.5），
  而不是在计数侧打补丁（因为没有身份信息，计数侧无从判断新 ID 是不是旧人）。

## 四、脚点 vs 中心点 vs 头部：这是把双刃剑

用户问：判定点该用框中心还是脚点（底边中点）？**证据非常一致：业界普遍用脚点。**

### 4.1 三家独立实现都用脚点

**(a) NVIDIA DeepStream `nvdsanalytics` —— 官方文档明文规定，且是「所有 analytics 计算」**

[NVIDIA 官方文档 gst-nvdsanalytics](https://docs.nvidia.com/metropolis/deepstream/dev-guide/text/DS_plugin_gst-nvdsanalytics.html)：

> **for all the analytics calculations bottom center coordinate of bounding box of an object is being used.
> If bounding box is defined as (x_left, y_top, width, height) then the bottom center coordinate would be
> (x_left + width/2, y_top + height)**

**(b) Frigate —— 源码实锤，底部中心**

`frigate/track/tracked_object.py:187-206`：

```python
# check zones
current_zones = []
bottom_center = (obj_data["centroid"][0], obj_data["box"][3])
...
if cv2.pointPolygonTest(contour, bottom_center, False) >= 0:
```

**(c) AXIS Object Analytics —— 官方手册，且给了原因**

[AXIS Object Analytics 手册](https://help.axis.com/en-us/axis-object-analytics)：

> Each classified object has a **point of detection** that the application uses to decide if an object is inside or
> outside an include area or when it crosses a virtual line. **For a human, the point of detection is at its feet**,
> and for a vehicle it's at its center. If a human's feet or a vehicle's center gets obstructed from the camera's
> view, the application makes an assumption of the location of the point of detection.

> **It's particularly important that characteristic features, such as legs or wheels, are visible.**

**(d) 商用客流厂商 FootfallCam —— 安装指南按脚点思路给规则**

[Camera Positioning & Counting Line Guide](https://footfallcam.com/doc/docs/User-Guides/Camera-Positioning-And-Counting-Line-Guide)：

> If a person is only detected on one side, the crossing is incomplete and may not be counted.
> **Leave visible tracking space on both sides of the counting line.**

> **Angled CCTV Camera Considerations** ... More horizontal angles increase body overlap ... Occlusion increases as
> people block each other ... **Tracking reliability drops faster than with top-down views.**
> Use the steepest practical angle. Avoid placing the counting line far from the camera.

### 4.2 为什么脚点更好（物理解释）

斜视走廊里，**地面是类平面的**，而人的**头会前后左右晃、会被人挡住、会走出画面顶端**。
脚点对应「人在地面的真实位置」，是**唯一在透视下仍然单调、可比的量**。
框中心等于「脚点和头的中点」，会随人的姿态/遮挡抖动，且**在透视下不是地面的投影**。

### 4.3 ⚠️ 但脚点有一个我们的场景特有的陷阱

**AXIS 和 DeepStream 都是「俯视/斜俯视进门」场景**——人走向摄像头、脚一直在画面里。
**我们的走廊机位是斜侧视，且一排门在纵深方向**：远处的人**脚部极易被前景物体、地面反光、
或前一个行人挡住**；而且人贴墙走过门口时，**脚点可能根本不在画面里**（框底被截断）。

DeepStream 官方在论坛里亲自确认了脚点的这个失效模式
（[NVIDIA 论坛 #262267](https://forums.developer.nvidia.com/t/false-line-crossing-count-for-persons-who-do-not-pass-the-line-in-deepstream-occupancy-analytics/262267)，
2023-08，NVIDIA 工程师 `fanzh` 回复用户报的「没跨线却计数了」）：

> about "at 00:08 (ID=22), 00:30 (ID=43)" 's issue, please refer to nvdsanalytics,
> nvdsanalytics plugin will check the bottom center coordinate (x_left + width/2, y_top + height).
> **when the person's bottom center coordinate passed the crossing line, the bbox disappeared because the
> person's body left the frame partially, as a result, nvdsanalytics did not count.**

**这是同一个 bug 类别**：脚点越界/被截断 → 判定点跳变 → 漏计或误计。
NVIDIA 工程师在同一帖里还承认了另一个方向的错误：`at 00:15 (ID=1), the person did not pass the line,
but nvdsanalytics counted.` ——**即使是大厂实现，跨线计数也会两个方向都错。**

### 4.4 对照：Ultralytics 用的是**框中心**（而且有另一个坑）

读源码核实（`git clone --depth=1` + sparse-checkout，`ultralytics/solutions/`）：

`region_counter.py:125`：
```python
center = self.Point(((x0 + x1) / 2, (y0 + y1) / 2))
```
`object_counter.py` 的跨线判定也是基于这个 center，走 `shapely` 的线段相交：

```python
        if len(self.region) == 2:  # Linear region (defined as a line segment)
            if self.r_s.intersects(self.LineString([prev_position, current_centroid])):
```

**两个可借鉴的点，以及一个必须避开的坑：**

✅ **借鉴 1：用「上一帧中心 → 本帧中心」的线段相交，而不是「当前点在哪一侧」。**
这正是对付快走的人的**正确姿势**——`object_counter.py:100-101` 的注释直说了原因：

```python
        # An object fast enough to straddle the region leaves no centroid inside it, so count a crossing segment
        # too, but only from outside: a track already inside has had the containment check since it entered.
```

翻译：**走得够快的人会「跨过」区域而不留下任何一帧中心点在区域内**。用线段相交就没有这个漏洞。

❌ **坑：`counted_ids` 让每个 ID 一辈子只计一次。** `object_counter.py:77` 和 `:98`：

```python
        if prev_position is None or track_id in self.counted_ids:
            return
        ...
                self.counted_ids.add(track_id)
```

而且 `BaseSolution.forget_tracks()`（`solutions.py:187-195`）**只清 `track_history`，不清 `counted_ids`**：

```python
    def forget_tracks(self, track_ids: list[int]) -> None:
        for track_id in track_ids:
            self.track_history.pop(track_id, None)
```

**这意味着 Ultralytics 的 ObjectCounter 只适合「单方向过线计数」（只数进、或只数出），
不适合我们的「进 − 出 净累积」**——同一个人先出后进（或反之）会被漏掉。
**不能直接照搬，只能借它的线段相交思想。** 我们现在的 `counter.py` 用 `sides` 字典记录每人当前侧别，
方向是对的（支持双向），这点比 Ultralytics 更适合我们的业务。

### 4.5 结论：脚点更好，但要给「脚点不可信」留退路

| 方案 | 优点 | 缺点（我们的斜视走廊） |
|---|---|---|
| 框中心（现状） | 永远在框内，不会突然消失 | 受姿态/遮挡抖动；透视下不是地面位置 |
| **脚点（底边中点）** | 业界标准，对应地面真实位置，单调可比 | **远处/贴墙时脚可能被截断或遮挡** → 跳变 |
| 头部 | 遮挡比脚少 | 头部晃动大，且透视下越远越小，**最不稳** |

**建议（低风险改动）**：
把判定点从中心点改成脚点，但**保留一个「脚点不可信时退回中心点」的判断**：
当框底边贴着画面底边（`y2 >= H - 2`）说明人被画面裁掉，此时脚点无意义，退回中心点。
代价：约 3–5 行代码。**这是本次调研里性价比最高的单点改动之一。**

### 4.6 五家实现对照总表

| 实现 | 版本/日期 | 锚点 | 死区/迟滞 | IPM/warp | 丢失容忍 |
|---|---|---|---|---|---|

| Frigate | `62ca5b25` 2026-10-15 | **脚点** `box[3]` | **`inertia: 3` 帧** | `create_ground_plane` 按 y 插值（**仅用于速度**） | `max_disappeared: 25`（5×fps） |

### 4.7 一条零成本、收益大的建议：线的位置

AXIS 官方对虚拟线布置的建议原文（[手册](https://help.axis.com/en-us/axis-object-analytics)）：

> **Virtual line recommendations** — Adjust the virtual line so that:
> - **objects are unlikely to be waiting at the line.**
> - objects are clearly visible in the image before they cross the line.
> - an object's point of detection is likely to cross the line.

FootfallCam 同口径：

> If a person is only detected on one side, the crossing is incomplete and may not be counted.

**落到我们场景**：判定线**不要画在门槛正上方**（那里人可能驻足、开门、等同伴，
造成脚点在线上反复抖动或长时间停留）。**建议画在门内侧约 30–50cm 处**——
那里人不会停留，是"通过"而非"驻留"的位置。

**这是纯配置改动，零代码、零算力，但直接减少抖动误计。收益/成本比最高的一条。**

⚠️ 注意：线往门内挪之后，「房间内人数」的口径要跟着想清楚（门外走廊的人不应计入）。
这属于业务口径，需用户确认。

## 五、检测侧：远处的人会不会漏

用户问：1080p 广角画面，640 letterbox 后远处的人会不会漏检。**会，而且这是首要误差源。**

### 5.1 letterbox 后的实际像素尺寸（算术，不是估算）

1080p（1920×1080）整帧 letterbox 到 640×640：比例 `ratio = 640/1920 = 0.333`。
缩放后高度 1080×0.333 = 360px，上下各补 (640−360)/2 = 140px 灰边。

走廊里一个人高约 1.7m。广角机位下：
- **近处**（画面高占比 80%）→ 原图 864px → **letterbox 后 288px**，非常充裕
- **中距**（占比 25%）→ 原图 270px → **letterbox 后 90px**，OK
- **远处**（占比 8%）→ 原图 86px → **letterbox 后 29px**，勉强
- **很远处**（占比 4%）→ 原图 43px → **letterbox 后 14px**，**接近 YOLO11n 的 P3 stride 8 极限**

COCO 对小目标的定义是面积 < 32×32 px。**我们在 640 下，画面后 1/3 的人就是 14–29px 的小目标。**

### 5.2 分辨率是收益最大的一招（有量化证据）

[MDPI, Systematic Evaluation of YOLOv8 Variants for UAV-Based Object Detection](https://www.mdpi.com/2076-3417/16/7/3559)（VisDrone 数据集）：

> **Scaling the input resolution from 640 to 1280 yielded a 25% improvement (12.7% → 15.9% mAP50) in small-object
> detection, while an additional P2 layer improves the performance by only 6% (12.7% → 13.5% mAP50),
> corresponding to a 4× difference in effectiveness.**

> standard CNN architectures with five pooling layers reduce a 640 × 640 input image to a 20 × 20 feature
> representation. **At this resolution, a typical 16-pixel object occupies less than one feature map cell**,
> making reliable detection extremely difficult.

> When the computational budget is constrained, **practitioners should prioritize input resolution over
> architectural modifications.**

**但代价是平方级的**：640→1280 是 4× 像素。RK3588 上 YOLO11n@640 是 23ms(NPU)/162FPS(吞吐)，
1280 下会掉到约 1/3–1/4。**对我们不划算。**

### 5.3 检测侧的性价比排序（我们的选项）

| 手段 | 预期收益 | 代价 | 是否推荐 |
|---|---|---|---|
| **降 conf 阈值**（现 0.15 已很低） | 小；已接近下限 | 误检↑ | ❌ 已经很低了 |
| **提高输入而非模型**（640→960/1280） | **大**（+25% 量级） | 帧率掉一半以上 → 掉帧反而更易丢 ID | ⚠️ 需实测权衡 |
| **换更小的模型但更高分辨率** | 中 | 需重导模型 | ⚠️ 备选 |
| **底部区域裁剪 + 二次检测**（只对画面下半/门口 ROI 提分辨率） | **中高** | 复杂度↑，违背「不 overengineering」 | ❌ 违背项目原则 |
| **抽帧/插值** | **负收益** | 帧间位移↑ → 更容易丢 ID | ❌ **千万别做** |
| **调 NMS IoU**（现 0.6） | 小 | 人重叠时可能合并 | ⚠️ 影响小 |

**关键提醒**：「抽帧」在别处是省算力的手段，**但在我们的场景是反效果**——
帧率越低，帧间位移越大，IoU 关联越容易失败。这与第三、四节完全一致。

### 5.4 为什么「远处的人」对我们是双杀

远处的人**同时**触发两个失效：
1. **检测漏**（14–29px，见 5.1）
2. **跟踪丢**（框小 → 同样的绝对位移占比更大 → IoU 掉得更快，见 3.1）

而**我们关心的是「人进房间」**——门口恰好常常在画面纵深方向（远处）。
**这是本场景最本质的困难，必须正视。**

**含义**：多模型并发**做得到，但要显式设计**（去掉 `target` / 显式 `core_mask` / 多线程或多进程），
**不是 `init_runtime()` 两次就自动并行**。

**(b) 多核不是免费的——官方 SDK 文档明确警告小网络会变慢。**

Rockchip 官方 `RKNN2_SDK_Development_Guide_V2.5.0.pdf` §4.1.2（子代理已下载全文核对）：

> **Note: Multi-core operation is suitable for networks with large per-layer computation workloads.
> For small networks the improvement is limited, and performance may even degrade due to switching between
> single-core and multi-core modes (this switching requires CPU intervention).**

> `NPU_CORE_0_1_2`: the model runs on NPU Core0, Core1 and Core2 **at the same time**.
> ←（是**单模型摊到 3 核**，不是「3 个模型并行」）

> `NPU_CORE_AUTO`: automatic scheduling mode; the model automatically runs on the currently idle NPU core
> **in single-core mode**.

**关键限制**：只有这些算子支持多核切分 —— `Conv, DepthwiseConvolution, Add, Concat, Relu, Clip, Relu6,
ThresholdedRelu, PRelu, LeakyRelu`。**其他算子（含 Reshape / Transpose / Softmax 等）只能在单核跑。**
SDK 日志里 `WorkLoad(0/1/2)-ImproveTherical` 会显示每层切分比例与理论上限；
很多层显示 `100.0%/0.0%/0.0% - Up:0.0%`（**无加速**）。

⚠️ **这对我们直接相关**：我们的模型是**改头的 9 输出 + Python 侧算 DFL**，输出层/reshape 较多，
**这些层吃不到多核**。`core_mask=NPU_CORE_0_1_2` 的实际收益可能远低于预期。

官方还给了一个削减多核开销的手段：**把大核与 NPU 中断绑到同一个大核上**
（"eliminate the core switching overhead of NPU interrupt processing"）。

### 6.2 ⭐ 最关键：单模型根本吃不满一颗核

`swdee/go-rknnlite` 的 `example/pool/README.md`（Radxa Rock 5B / RK3588）：

> However these settings don't exhaust the NPU's processing capacity, typically you will only see
> **saturation of a single core around 30% when running a single Model**. For this reason running **multiple
> instances of the same Model** allows us to use all NPU cores.

实测（MobileNet-v1，8000 张，多实例池化）：

| runtime 数 | 单张耗时 | 单核饱和度 |
|---|---|---|
| 1 | 7.73ms | ~35% |
| 9 | 1.19ms | ~74% |
| 12 | 1.13ms | — |
| 15 | 1.09ms | 峰值 ~80%，之后收益递减 |

**含义**：单模型跑不满 NPU。**理论上「第二个模型」是有空间的**，但正确姿势是
**池化/错峰（多实例）**，而不是「两个模型真并发」——见下条。

⚠️ **注意区分**：这是**多实例池化**（同一模型开多份、各占一个核），
**不是**「单模型自动摊到 3 核」。两者收益来源不同。

### 6.3 ⚠️ 并发（真并行）是有危害的，社区已多次实证

- [#454](https://github.com/airockchip/rknn_model_zoo/issues/454)（2026-09-23）：
  > **The NPU is DDR-bandwidth sensitive, not purely compute-bound.** Running memory-heavy CPU work alongside
  > NPU inference **dropped FPS from 84 to 62** in our tests.
  → **26% 吞吐损失**，仅因并行的 CPU 侧内存密集工作。

- [zoo#210](https://github.com/airockchip/rknn_model_zoo/issues/210)：多路并发时 yolov5 **随机乱框**
  （"npu占用稍微高一点就会出现乱框"），`swdee` 判断是 **buffer race condition**。
- [zoo#341](https://github.com/airockchip/rknn_model_zoo/issues/341)：2 个模型 `std::async` 并行推理 → **"检测错乱了"**（结果错乱）。
- [zoo#344](https://github.com/airockchip/rknn_model_zoo/issues/344)：3 线程时 **CPU 占用从 90% 涨到 260%**。
- [zoo#432](https://github.com/airockchip/rknn_model_zoo/issues/432)：**RGA 预处理单线程 2ms，多线程涨到 13ms**（6.5 倍恶化）。

**我们的流水线里，`letterbox()`（1080p resize）和 `_dfl()`（numpy 大数组）恰恰都是内存密集的**，
再加上图传拷贝、Slint 渲染——**这些都在抢 DDR 带宽**。
→ **加第二个模型的真实成本，不只是它自己的耗时，而是它带来的额外内存流量会让主检测也变慢。**
（此为基于上述证据的推断，需板上实测。）

### 6.4 ReID 在 RKNN 上确实存在可用件（纠正上一节的印象）

- **`rknn_model_zoo` 确认没有 ReID**（已逐文件核实，见第一节），29 个 examples 到 whisper 为止，无任何 ReID/OSNet。
- **但 `swdee/go-rknnlite` 有可用的 OSNet RKNN 端口**：
  - `example/reid/reid.go`，模型 **`osnet-market1501-batch8-rk3588.rknn`**（在 `../data/models/rk3588/`）
  - 输入 **`[8, 256, 128, 3]` INT8 NHWC**，输出 **`[8, 512]` INT8 512 维 embedding**
  - 实测原文：`Model first run speed: batch preparation=3.900093ms, **inference=47.935686ms**,
    post processing=262.203µs, total time=52.097982ms`
  - **注意：47.9ms 是 batch=8**，即约 **6ms/人**（需确认该数字是否为多核）
  - 度量阈值：Euclidean distance **0.51**（同人 0.42~0.47，异人 >0.68）
  - **该模型是 RKNN 格式，可直接用 rknn-toolkit-lite2 加载，Python 侧无需 PyTorch**；权重需从 `swdee/go-rknnlite-data` 取
- `boxmot`（8313 stars，活跃，2026-10-13 push）**依赖 torch**（`pyproject.toml` 里 `torch`/`torchvision` 指向
  pytorch-cpu / cu130 index）——**板上装不了 PyTorch，直接排除**。
- `norfair`（2694 stars，最后 push 2025-04-30，依赖 `filterpy + rich + scipy + numpy`）——纯 Python，理论可装；
  但 Frigate 已验证它「遮挡仍然 very challenging」（姊妹篇 1.1 引用 discussion #8366），**而我们的痛点是快速运动而非遮挡**。
- RMOT 类 / 其它 RKNN ReID 仓库极少：`gh search repos 'rknn reid'` 最高仅 **7★**（`kuaileBenbi/RKNN-DeepSORT-REID-Convert`，2024-08-08 停更）。
  → **社区件稀少、成熟度低**，与「比赛原型」不匹配。

### 6.5 ⭐ 决定性证据：ReID 实现者本人劝退

`swdee/go-rknnlite` 是目前**唯一**可用的 RK3588 RKNN ReID 实现（OSNet Market1501）。
但**作者在自己的 `example/stream/README.md` 里明确劝退**——我已抓取 raw 原文逐字核对：

> ## Re-Identification (ReID)
> Experimental ReID has been added which follows the implementation of the FairMOT tracker, however this makes use
> of the OSNet model trained with the Market1501 dataset.
>
> **Usage of ReID is expensive and typically takes around 200ms per frame to complete on the RK3588 NPU.
> There is little accuracy improvement over straight ByteTrack which adds little overhead to the YOLO object
> detection.**
>
> **We need to wait for Rockchips next generation RK36xx SoC before this may be useful.**

**"200ms 每帧" vs 我们检测器的 15–40ms/帧 —— 差 5–10 倍。加 ReID 会直接毁掉实时性。**

⚠️ 注意区分两个数字（容易误读）：
- `example/reid/README` 的 `inference=47.9ms` 是 **batch=8** 的耗时（≈6ms/人），看似便宜；
- 而作者在 **stream（真实流水线，含逐人裁剪 + 组 batch + 后处理）** 里实测是 **约 200ms/帧**。
- **真实成本是后者**，因为「按人裁剪 + 组 batch + 相似度矩阵」在 CPU 侧很贵。

同 README 还有一句对我们**跟踪质量**很有价值的自白：

> ## Tracking Accuracy
> The Go ByteTrack code ported outputs the same result as the C++ and Python source code. **Personally I don't find
> object tracking to have the accuracy I would desire, the results vary depending on which YOLO model is run and
> the tracking itself is not 100%.** Whilst this demo shows a complete solution, you would still need to do work
> to train a better model and testing for your own use case.

→ **连认真移植了 ByteTrack 的作者都承认跟踪精度不达预期。** 这说明「换一个更好的 tracker 库」不是银弹，
我们不必在库的选择上纠结，而应聚焦在**具体机理修正**（运动模型 / 脚点 / 线段相交）。

### 6.6 YOLOv8n-pose：比 ReID 便宜两个数量级，且直接给脚点

官方 `rknn_model_zoo` README 性能表：`yolov8n-pose [1,3,640,640] INT8` → **RK3588 @single_core = 58.3 FPS**
（表注明确："Does not include the time-consuming of pre-processing and post-processing"）。

go-rknnlite 实测（p50）：`inference = 25.40ms`、**`postprocess = 1.27ms`**、`render = 3.10ms`、`total = 30.21ms`。

| 模型 | inference (p50) | postprocess (p50) | 备注 |
|---|---|---|---|
| yolov8n-pose | 25.40ms | **1.27ms** | 含 17 关键点（含脚踝 #15/#16） |
| OSNet ReID（真实 stream） | — | — | **~200ms/帧（作者实测）** |

**关键：pose 是「换一个模型」而不是「加一个模型」**——一次推理同时给出 bbox + 17 个关键点，
**不需要第二个 NPU context、不需要并发、不额外争 DDR**。这与 ReID 有本质区别。

且作者在真实摄像头 + ByteTrack 场景里明确说：

> **I find the results with object detection substandard however the YOLOv8-pose model works quite well.**

（运行参数 `-s 6`，即开 6 路池化，说明 pose 开销小到可以池化多实例。）

⚠️ **但有一个必须避开的坑**：`rknn_model_zoo/examples/yolov8_pose/python/yolov8_pose.py` 的后处理是
**逐 anchor 的纯 Python 双层循环**（80×80+40×40+20×20 = 8400 次循环），在 Python 上极慢。
go-rknnlite 的 1.27ms 是 Go 实现。**若我们走这条路，必须用 numpy 广播向量化重写后处理**，
否则后处理会变成最慢的一环。

### 6.7 结论：ReID 不划算，用 pose 更对路

ReID **不是「根本没有」**（有 OSNet RKNN 件），但**在我们场景仍不划算**，理由是：

1. **实现者本人劝退**（6.5 节）：200ms/帧、精度提升微小、"等下一代 SoC"。
2. **治错了病（最重要）**。ReID 解决的是 **re-identification（人消失一段时间后重新认出）**；
   我们的痛点是 **帧间 association 失败**（快速运动导致两帧框不重叠）。
   **后者是运动模型的问题，不是 ReID 的问题。** 用 ReID 治帧间丢 ID 是**用错药**。
3. **数量级不匹配**：ReID 200ms/帧 vs 检测 15–40ms/帧。
4. **工程成本高**：逐人裁剪 → 组 batch（固定 batch=8，人数不足要 padding）→ 512 维 embedding → 阈值标定
   （0.51 是 Market1501 的，我们走廊场景要重标）。**与「比赛原型、不 overengineering」直接冲突。**
5. **并发风险**（6.3 节）：buffer race / 结果错乱 / DDR 争抢全都踩中。

**替代路线**：若要更好的脚点，用 **yolov8n-pose 的脚踝关键点**（同量级算力、不需要第二个模型）。
**但仍建议先做 7.1 的运动模型**——那才是治本且近零成本。

## 七、落到我们场景的结论

> 这一节回答：**板上具体能加什么、加了多少开销、值不值。** 按「性价比」降序排列。

### 7.0 先做的一件事：测出真实帧率

**在改任何代码之前**，先跑起来看 `viewport.py` 已经打印的那行日志：

```
[People] Timing (ms): preprocess=.. inference=.. postprocess=.. total=..
```

**这一个数字决定后面所有取舍。** 如果 `total` 已经 > 60ms，那么**任何增加耗时的优化（提分辨率、加 ReID）
都会因为掉帧而适得其反**——必须优先把帧率弄上去。

### 7.1 加 Kalman 运动模型 —— 【强烈推荐，第一优先】

**改什么**：给 `Track` 加 8 维 Kalman 状态 `(x, y, a, h, vx, vy, va, vh)`，
`update()` 里先 `predict()` 外推，再拿**预测框**去算 IoU。

**开销**：纯 numpy，每人每帧一次 8×8 矩阵运算。
8×8 矩阵乘法约 512 次浮点乘加；假设画面里 10 个人、20 FPS → 每秒 10×20 = 200 次 ≈ 10 万次浮点运算/秒。
**在现代 CPU 上这是微秒级，相对 40–80ms 的推理完全可忽略（<0.1%）。**

**收益**：直接解决「快走丢 ID」的**根本机理**（第 3.1/3.2 节）。人快速移动时，外推框而非上帧框参与匹配。

**证据**：
- 上游 [ifzhang/ByteTrack](https://github.com/ifzhang/ByteTrack) `yolox/tracker/kalman_filter.py` +
  `byte_tracker.py::STrack.predict()` —— **正确实现可直接照抄**，不需要发明。
- Frigate 把 tracker 从纯 IoU 换成 Norfair（Kalman + 尺寸比例距离）后，官方发布说明称
  「ID swapping between tracked objects is **greatly reduced**」（见姊妹篇 1.1，discussion #8366）。
- ByteTrack-cpp#20 里 `junhui-ng` 的原话：**"the original ByteTrack Python implementation works well,
  but the C++ implementations ... do not provide the same accurate tracking results."**

**代码量**：照抄上游约 60–80 行 numpy。**符合「初级程序员不看注释也能读懂」吗？**
⚠️ Kalman 公式本身有一定门槛。**权衡建议**：可以只加**「匀速外推」而不加完整 Kalman**
（即 `predicted_box = last_box + last_velocity`，速度用两帧差或指数滑动平均），
**约 10 行**，能拿到大部分收益（因为瓶颈是「有没有运动模型」，而不是「运动模型多精细」）。
若选这条路，**推荐先做廉价版，实测有没有改善，再决定是否上完整 Kalman**。

**⚠️ 一条来自论文的重要修正（3.5 节）**：APPTracker 论文指出
> Without a good initial velocity estimation (the velocity of an object is usually initialized to zero) ... **the
> Kalman filter fails to chase objects in low-frame-rate cases.**

完整 Kalman 的速度初值是 **0**，前几帧外推会不准。**「匀速外推 + 两帧差速度」反而更直接地测量了速度。**
→ **进一步支持先做廉价版**。

### 7.1b `max_age` 按帧率换算 —— 【推荐，与 7.1 同期做，1 行】

**改什么**：`max_age=10` 是**帧数**，但它真实语义是「丢失后容忍的**时间**」。
按 APPTracker 附录 B 的 Table 5（n_d：1→buffer 30；10→10；30→3），容忍时间应约 **1 秒**。

**建议**：`max_age = round(fps)`，即实测 15 FPS → `max_age≈15`（现在 10，偏小）。
若之后帧率提升，**必须同步调整**，否则容忍时间会缩短、ID 保持能力反而下降。

**开销**：**零**（改一个数字）。
**证据**：[APPTracker 论文附录 B Table 5](https://infzhou.github.io/folder/Zhou_APPTracker_Improving_Tracking_Multiple_Objects_in_Low-Frame-Rate_Videos_MM_2022.pdf)（我已下载 PDF 逐表核对）。

### 7.2 判定点改用脚点（底边中点）+ 截断兜底 —— 【推荐，第二优先】

**改什么**：`counter.py` 里 `t.center` → 底边中点 `((x1+x2)/2, y2)`，
并加「`y2 >= H-2` 时退回中心点」。

**开销**：**零**（只是换个取值方式）。

**收益**：对齐业界标准（DeepStream/AXIS/Frigate 三家一致），判定点对应地面真实位置，
透视下单调可比，减少姿态抖动导致的误判。

**证据**：DeepStream 官方文档明文「for **all** the analytics calculations bottom center coordinate ...
is being used」；AXIS「For a human, the point of detection is at its feet」；Frigate 源码
`tracked_object.py:188`。

**代码量**：3–5 行。

### 7.3 跨线判定改用「线段相交」而非「当前在哪一侧」 —— 【推荐，第三优先】

**改什么**：现在是记录每人上次的 side 符号、翻转就计数（`counter.py::update`）。
**快走的人可能一帧内从线的一侧跳到另一侧、甚至「跨过」线而不在死区内留下任何一帧**，
但**线段相交（上一帧点 → 本帧点）不会漏**。

**开销**：零（两次叉积）。

**证据**：Ultralytics `object_counter.py:100-101` 的源码注释直说了这个原因
（"An object fast enough to straddle the region leaves no centroid inside it, so count a crossing segment too"）。

⚠️ **注意**：我们**不能**照搬 Ultralytics 的 `counted_ids`（每人只计一次），
因为我们要的是**双向净累积**（见 4.4）。**只借它的线段相交思想。**

**代码量**：约 5–10 行改动。

### 7.4 死区/滞回 —— 【保持现状或微调】

现在是 `DEAD_ZONE = 0.02`（画面高的 2%）。这是「中心点落在带子里算线上，不改变侧别」。

**对照业界**：
- Frigate 用 **`inertia`＝连续 3 帧** 在区域内才算在场（`frigate/config/camera/zone.py:42`），
  **这是「帧数」而非「像素距离」的去抖**。
- Frigate 路径采样：只有移动 **≥ 画面对角线 5%** 才追加新路径点（`tracked_object.py:373`）。
- Ultralytics **完全没有死区**。

**判断**：我们的 2% 死区是合理的、且比 Ultralytics 严谨。**若改了 7.3（线段相交），
死区的作用会下降**（因为不再依赖「当前侧别」的稳定性）。**建议先不动**，等 7.1–7.3 落地后再看是否需要。

### 7.5 若想再上一层：yolov8n-pose 换脚点 —— 【可选，等 7.1–7.3 之后再评估】

**改什么**：检测模型换成 `yolov8n-pose`，用**脚踝关键点**作为跨线判定点。

**开销**：官方标 **58.3 FPS @single_core**（yolo11n 标 64.0，**两者同级**）；
go-rknnlite 实测 postprocess 仅 **1.27ms**（关键点解析几乎免费）。
→ **它不是「额外加一个模型」，而是「换一个模型」，算力代价与现方案同量级。**

**收益**：脚点不再靠「框底边」估计，而是模型直接给出脚踝位置，
**天然免疫「框底边被截断」和「框包含行李/阴影导致底边偏移」的问题**。

**代价与风险**：
- 要重导 RKNN 模型（板子不能导，需 x86 机器），要重标 conf/NMS，要写关键点后处理。
- 官方 FPS 数字已被证明乐观 4.4 倍（2.4 节），**须先实测**。
- **违背「不 overengineering」的风险中等**——如果 7.1–7.3 已经解决漏计，就**不必做**。

**判断：先把 7.1–7.3 做完并实测。如果实测显示漏计仍严重，且怀疑是判定点问题，再上 pose。**

### 7.6 不要做的事（明确否决）

| 方案 | 为什么否决 |
|---|---|
| **加 ReID 模型** | 见 6.6：治错病（帧间丢 ID ≠ 重认）、工程量大、抢 DDR 带宽；虽有 OSNet RKNN 件但性价比差 |
| **抽帧** | 帧间位移↑ → 更容易丢 ID（3.1 节数学） |
| **提高输入分辨率到 960/1280** | 收益真实（+25% 量级，MDPI 论文）但耗时约平方增长；**先测出当前帧率再谈**。若当前只有 15 FPS，加分辨率会掉到 5 FPS，反而更糟 |
| **SAHI / 分块检测** | 与「比赛原型、不 overengineering」直接冲突 |
| **换 boxmot** | 依赖 torch，板上装不了 |
| **照搬 Ultralytics ObjectCounter** | `counted_ids` 只计一次，不支持双向净累积 |
| **移植 ByteTrack-cpp** | C++ 版有 `predict()` 不刷新 `rect_` 的真 bug（3.3 节），且引入编译/交叉编译负担 |
| **两个模型真并发（`std::async` / 多线程直跑）** | 社区多次实证会乱框/结果错乱/CPU 暴涨（6.3 节 #210/#341/#344）。要并发必须**池化 + 错峰** |
| **IPM / 单应矩阵做地面投影** | 未找到「斜视走廊 + 跨线计数」的成熟工程先例；AXIS 这类厂商的做法是**标定透视换算物体真实尺寸**，而非 warp 图像。**属于过度工程**（弱证据，见第八节第 6 条） |

### 7.6b 若实测帧率不够，这些是有效的提速手段

**只在 7.0 实测确认帧率不足时才做**（否则属于提前优化）。

| 手段 | 效果 | 代价 | 证据 |
|---|---|---|---|
| **向量化后处理** | 可能最大 | 改代码 | 官方 zoo 的 pose Python demo 是 8400 次逐 anchor 循环，极慢；我们的 `_dfl` 已是 numpy 向量化，但 `cv2.dnn.NMSBoxes` 仍是 Python 循环 |
| **多实例池化绑核**（`core_mask=i%3`） | **~5x** | 需重构为多线程/进程池 | `rknn_set_core_mask(i%3)` → **19→100 FPS**；Python 实测 1→3 线程 **27.4→65.4 FPS** |
| **DDR/NPU/CPU 定频** | ~7% | 一条命令 | "DDR 默认 528 MHz：不定频前 NPU 满载但 DDR 是瓶颈, FPS 跌到 162" |
| **绑大核 + NPU 中断绑同一大核** | 削减多核切换开销 | 配置 | Rockchip 官方 SDK 文档 §4.1.2.3 |
| **确认多输出 RKNN 导出** | ~20% | 已在用 | #454：9 输出 162 FPS vs `format=rknn` 134 FPS。**我们 `_dfl` 走的就是 9 输出路径，已经吃到了** |
| **单核 vs 3 核实测对比** | 可能反而变快 | 试一次 | 官方说小网络多核"may even degrade"；我们模型有较多 reshape/输出层，**这些层只能单核跑** |

⚠️ **注意 `max_age` 联动**：若帧率提升，**必须同步调整 `max_age`**（见 7.1b），否则容忍时间缩短、ID 保持反而变差。

### 7.7 优先级总表（一张图看完）

| 优先级 | 做什么 | 开销 | 代码量 | 证据强度 | 值不值 |
|---|---|---|---|---|---|
| **0** | **实测帧率**（看现有日志） | 0 | 0 | — | **必做，它决定下面所有事** |
| **1** | 加匀速外推运动模型（先用 10 行廉价版） | 近零（<0.1%） | ~10 行 | **强**（上游可抄 + Frigate + 论文） | **值，治本** |
| **1b** | `max_age` 按帧率换算（`≈1s×FPS`） | 0 | 1 行 | **强**（论文 Table 5） | **值** |
| **2** | 判定点改脚点 + 截断退回中心点 | 0 | 3–5 行 | **强**（NVIDIA/AXIS/Frigate 三方一致） | **值** |
| **3** | 跨线改「线段相交」（保留双向） | 0 | 5–10 行 | **中强**（Ultralytics 源码注释） | **值** |
| **4** | 判定线挪到门内 30–50cm | 0 | 0（配置） | **中强**（AXIS 明文建议） | **值，但需定业务口径** |
| **5** | 完整 Kalman（若廉价版不够） | 近零 | 60–80 行 | **中强** | 视 1 的实测结果 |
| **5b** | 若帧率不足：向量化后处理 / 池化绑核 / 定频 | 视手段 | 中–大 | **强** | 视 7.0 的实测结果 |
| **6** | 换 yolov8n-pose 拿脚踝点 | 同级算力 | 重（重导模型） | 中（官方数乐观 4.4×） | 视 1–3 的结果 |
| ❌ | ReID | — | — | — | **不做**（实现者本人劝退，200ms/帧） |
| ❌ | 抽帧 / 提分辨率 / IPM / 并发直跑 | — | — | — | **不做**（见 7.6） |

### 7.8 一句话

**在板上，把钱花在「给 tracker 加运动模型（匀速外推或 Kalman）」上，收益最大、开销近零；
判定点从中心点改成脚点、跨线判定改成线段相交、`max_age` 按帧率换算，是三个几乎零成本的正确性修正。
ReID 和提分辨率都要等帧率实测数字出来再谈——而大概率不该做。**

## 八、风险与不确定点（诚实清单）

1. **我们没有板上实测数字。** 第 2.5 节的 15–30 FPS 是**推断**，必须实测。
   `detector.timing` 已经现成，跑一次就有。
2. **官方 FPS 表被实测打脸 4.4 倍**（2.4 节，issue #433：标 64 FPS，实测 68ms=14.7 FPS）。
   因此**任何官方 FPS 数字都不能直接当设计预算**，包括 yolov8n-pose 的 58.3 FPS。
3. **#454 的 FPS 表是单一来源、0 回复、未进官方文档**，且发帖人用的是 Vicharak Axon 而非香橙派 5 Plus。
   **采信度中等**，但其中「多输出导出快 20%」与我们的现状吻合，值得注意。
4. **6.3 的「加第二个模型会让主检测变慢」是基于 #454 的 DDR 带宽论述 + 多个乱框 issue 推断的**，没有我们的实测。
5. **脚点在斜视走廊的失效模式（远处脚被挡/被截断）没有找到针对走廊场景的专门研究。**
   AXIS/DeepStream 的场景偏「俯视进门」。**我们的兜底方案（截断时退回中心点）是基于工程判断，
   不是有出处的做法。**
6. **没有找到把 RKNNLite 的 Python 侧开销（letterbox / _dfl / NMS）单独量化过的公开数据。**
   这是「我们帧率到底多少」最大的未知来源。
7. **IPM / 单应矩阵**：子代理**逐仓库 grep**（`getPerspectiveTransform` / `warpPerspective` / `findHomography`）
   确认 **DeepStream / AXIS / Frigate / Savant / Ultralytics 五家全部不做 warp-before-tracking**；
   学术上的 IPM 全出现在多相机融合 / 密集人群密度 / 车辆轨迹对齐。
   → **结论：IPM 对我们属于过度工程，不做。**（证据强度：中强——反面证据充分，
   但「没人做」无法被穷尽证明。）
8. **`core_mask=NPU_CORE_0_1_2` 是否真在我们板子上生效**依赖 NPU 驱动 ≥0.9.6（见 rknn-toolkit2#138），**未验证**。
   且官方 SDK 文档说**小网络多核可能反而变慢**（6.1 节），值得实测对比单核/多核。
9. **`swdee/go-rknnlite` 的 OSNet 实测 47.9ms 是否为多核、batch=8 下每人的真实摊销**，
   我没有在香橙派上复现，**该数字仅作量级参考**。
10. **「走快丢 ID」究竟是关联失败还是检测漏检，我们还没有分离测量。**
    建议实测时同时记录「每帧检测到的人数」与「tracker 输出的轨迹数」，
    若检测数就少，则问题在检测侧（第五节），不在 tracker。
