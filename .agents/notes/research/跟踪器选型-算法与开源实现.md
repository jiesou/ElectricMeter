# 跟踪器选型：算法与开源实现

面向场景：固定安装的**斜视广角走廊摄像头**，每扇门画一条判定线，统计「进 / 出 / 净」→ 反推每间客房内当前人数。
硬件约束：香橙派 5 Plus（RK3588，单 NPU）+ Python + rknnlite + numpy + opencv，**板上无 PyTorch、无 GPU**。
现有实现：`slintui/vision/tracker.py` 自写 ByteTracker，贪心 IoU（阈值 0.3）两阶段，max_age=10、min_hits=2，**无 Kalman、无运动模型、无外观特征**。

---

## 先把问题的真实结构说清楚

### 我们的痛点不是「跟踪」，是「净计数的单向误差累积」

这一点决定了后面所有取舍，必须先讲明白。

现有 `counter.py` 的计数逻辑是：轨迹中心点 `side` 符号翻转就 +1，死区为画面高 2%。跟踪 id 不连续**本身不致命**——id 换了，只要同一时刻还有一条轨迹在跨线，计数照样发生。

真正致命的是**跨线那一刻没有任何轨迹可判**：

```
人在门口的那一帧必须有一条轨迹 → 这条轨迹必须在门口那一侧留下过 side
→ 但轨迹的 side 记录只在「该 id 被 tracker 返回」的帧上更新
→ 如果检测漏了 / 轨迹被 max_age 删了 / 轨迹刚被新建还没到 min_hits
→ 那一帧 counter 的 sides 里没有它 → 跨线不发生 → 永久漏计
```

而「房间内人数 = 进 − 出」是**净累积**：一次漏计就永久留在房间里。这跟「客流统计」有本质区别——客流统计错一次只是那一帧的数字抖一下，长期均值还能对；净累积是**不可逆的偏差**。一晚上 20 个人进出，漏 2 次，第二天早上房间人数就永久少 2（或反号）。

**所以我们的优化目标应该写成：最大化「门口区域内的轨迹连续存活率」，而不是最大化 MOTA/IDF1。** 全局 IDF1 高不高其实不关心；关心的是那 1~2 米的门口区域内别断。

### 场景对我们不利的三个点

**斜视透视**：走廊是斜侧视角，人从画面远端走到近端，框会从 30px 高长到 200px 高。这带来两个后果：

1. **IoU 在纵深方向上的语义完全变了**。远端两个相距 5px 的框其实是 3 米开外，近端两个相距 50px 的框可能只有 20 厘米。用同一个 IoU 阈值（现实现是 0.3）去关联远近两处的人，等于在两个不同的尺度上用了同一个物理标准。远端人会因为框小、位移占比大而 IoU 骤降 → 丢 ID。
2. **视线方向上的位移几乎不改变框的位置**。人朝走廊深处走（远离相机），框中心在图像上移动很小，但框在**缩小**；人横向走过门口，框中心移动大，框尺寸不变。也就是说「框中心位移」和「人实际走了多远」在两种运动方向上的比例差了好几倍。恒定速度 Kalman 在图像坐标系里建模，对这两种运动的预测误差结构完全不同。

**判定线是斜的**：门口那条线在图像里是斜的、而且因为透视，实际门口的「地面线」和图像里的直线不重合。现在用轨迹中心点判 side，中心点在透视下会随框大小变化而漂移（人走近，框中心向下移；但人的实际位置——脚——移动方向可能相反）。

**低帧率 + 快走**：推理一帧多快算多快（`viewport.py` 无帧率目标），RK3588 上 YOLO11n @640 大概几帧到十几帧。相邻两帧之间人可能已经走过门口区域。这是**采样率不足**，不是算法问题——任何 tracker 在只有 3 帧覆盖整个门口穿越过程时都很脆弱。

## 算法谱系：每个机制到底加了什么，值多少

以下数据全部来自各论文原文与独立复现（证据链接见文末）。

### 基线：SORT（2016）

Kalman 恒定速度模型（状态 `[x, y, s, r, vx, vy, vs]`）+ 匈牙利匹配 + IoU 代价。**没有外观、没有低分框、没有重连。**

### ByteTrack（ECCV 2022）——低分框二阶段

机制：把检测框按分数切成高分/低分两段。高分框先跟所有轨迹匹配；**没配上的轨迹**再用低分框补配一次；只有高分框能新建轨迹。

论文的关键 ablation（MOT17 + BDD100K 验证集）：

| Similarity#1 | Similarity#2 | MOT17 MOTA | MOT17 IDF1 | MOT17 IDs | BDD100K mMOTA | BDD100K mIDF1 | BDD100K IDs |
|---|---|---|---|---|---|---|---|
| IoU | Re-ID | 75.8 | 77.5 | 231 | 39.2 | 48.3 | 29172 |
| IoU | **IoU** | **76.6** | **79.3** | **159** | 39.4 | 48.9 | 27902 |
| Re-ID | Re-ID | 75.2 | 78.7 | 276 | 45.0 | 53.4 | 10425 |
| Re-ID | IoU | 76.3 | 80.5 | 216 | 45.5 | 54.8 | 9140 |

**读法**：在 MOT17 上，第二阶段用 IoU 明显好过用 Re-ID（MOTA 76.6 vs 75.8，IDs 159 vs 231）。原文说得很直白：

> "It is important to utilize IoU as Similarity#2 in the second association on both datasets **because the low score detection boxes usually contain...**"

以及论文对 Kalman 的一句极重要的自我否定：

> "**Kalman filter fails in autonomous driving scenes and it is the main reason for the low performance of SORT, DeepSORT and MOTDT. Thus, we do not use Kalman filter on BDD100K.**"
> —— 注意 BDD100K 的特征正是**低帧率 + 大相机运动**。

而 BYTE 这个机制本身的价值（把 BYTE 套到 9 个其他 tracker 上）：

| Tracker | 原始 | + BYTE | MOTA 增益 | IDF1 增益 |
|---|---|---|---|---|
| JDE | Motion(K)+Re-ID | ✔ | 60.0 → 60.6 | 63.6 → 66.0 |
| CSTrack | Motion(K)+Re-ID | ✔ | 68.0 → 69.3 | 72.3 → 71.7 |
| FairMOT | Motion(K)+Re-ID | ✔ | 69.1 → 70.4 | 72.8 → 74.2 |
| CenterTrack | Motion | ✔ | 66.1 → 67.4 | 64.2 → 74.0 |

IDF1 增益 1~10 点。**但注意 CSTrack 那行 IDF1 是 −0.6**，说明 BYTE 不是无条件的。

### OC-SORT（CVPR 2023）——以观测为中心

论文针对的正是恒定速度 Kalman 的两个病：**遮挡期无观测 → 先验误差累积**、**非线性运动 → 线性预测错**。三个机制：

- **ORU（Observation-centric Re-Update）**：轨迹重连时，不是直接 update，而是回到最后一次真实观测的状态，用**虚拟轨迹**（在最后观测和当前观测之间线性插值）重放 predict/update，把遮挡期的误差修掉。
- **OCM（Observation-centric Momentum）**：关联代价里加一项「轨迹历史运动方向」与「轨迹→候选框方向」的夹角一致性，权重 `inertia=0.2`。
- **OCR（Observation-centric Recovery）**：用 `last_observation`（上次真实观测位置）而不是 Kalman 预测位置去跟剩余检测框做第二次 IoU 关联。

组件 ablation（MOT17-val / DanceTrack-val）：

| ORU | OCM | OCR | MOT17 HOTA | MOT17 AssA | MOT17 IDF1 | DanceTrack HOTA | DanceTrack AssA | DanceTrack IDF1 |
|---|---|---|---|---|---|---|---|---|
| | | | 64.9 | 66.8 | 76.9 | 47.8 | 31.0 | 48.3 |
| ✔ | | | 66.3 | 68.0 | 77.2 | 48.5 | 32.2 | 49.8 |
| ✔ | ✔ | | 66.4 | 69.0 | 77.8 | **52.1** | **35.0** | 50.6 |
| ✔ | ✔ | ✔ | **66.5** | 68.9 | 77.7 | 52.1 | 35.3 | **51.6** |

**这是全文最重要的一张表。** 读法：

- **ORU 是主力**：MOT17 +1.4 HOTA，DanceTrack +0.7。它修的是「遮挡/漏检期的误差累积」——正是我们丢 ID 的机理。
- **OCM 只在 DanceTrack 上大幅起作用**（+3.6 HOTA，AssA +2.8），MOT17 上只有 +0.1。原文：*"OCM only shows good help on DanceTrack dataset where object motion is more complicated"*。**OCM 是给非线性运动准备的；相机固定、人走直线时它几乎不值钱。**

OCR 的增益很小（+0.1 HOTA），但注意它**恰好修的就是我们关心的问题**——「Kalman 预测位置飘了，导致跟检测框 IoU 掉到阈值以下而丢配」。它用「上次真实观测位置」兜底，是一个极便宜的保险。

另外论文验证了 `delta_t` 的选择（OCM 里算速度方向的帧间隔）：

| ∆t | MOT17 HOTA | DanceTrack HOTA | DanceTrack IDF1 |
|---|---|---|---|
| 1 | 66.1 | 51.3 | 51.3 |
| 2 | 66.3 | 52.2 | 51.4 |
| 3 | **66.5** | 52.1 | **51.6** |
| 6 | 66.0 | 52.1 | 51.8 |

∆t=3 是甜点。**但这假设帧率恒定**——我们的帧率不恒定（见后文「动态帧率」一节）。

### BoT-SORT / BoT-SORT-ReID（2022）——相机运动补偿 + 更好的状态量

机制：把 Kalman 状态从 `[x,y,s,r]` 换成 `[x,y,w,h]`（宽高而非面积/宽高比）、CMC（相机运动补偿，用稀疏光流 + RANSAC 估全局仿射，把轨迹状态跟着变换）、以及 ReID。

MOT17: **80.5 MOTA / 80.2 IDF1 / 65.0 HOTA**（官方声明，MOT17+MOT20 双榜第一）。

**但 CMC 对我们的价值需要打问号。** 最强证据来自 DeepMoveSORT（下面那条）对静态相机数据集的说法。

### Deep OC-SORT（2023）——自适应外观融合

在 OC-SORT 上加了：外观嵌入（固定 EMA）+ 动态外观（DA，按检测置信度调 EMA 系数）+ CMC + 自适应加权（AW）。达到 MOT20 第一（63.9 HOTA）、MOT17 第二（64.9 HOTA）、DanceTrack 61.3 HOTA。

**逐个机制的 ablation（这是难得的「每个机制值多少」的硬数据）**：

| Appr. | DA | CMC | AW | MOT17-val HOTA | AssA | IDF1 | MOT20-val HOTA | IDF1 | DanceTrack HOTA | AssA | IDF1 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| | | | | 68.13 | 70.06 | 79.52 | 58.35 | 74.77 | 53.07 | 35.93 | 52.43 |
| ✔ | | | | 69.66 | 72.72 | 82.44 | 58.33 | 74.63 | 53.57 | 36.68 | 53.30 |
| | | ✔ | | 68.59 | 70.63 | 80.18 | **59.10** | 75.71 | 58.03 | 42.37 | 57.73 |
| | | ✔ | ✔ | 68.65 | 70.85 | 80.45 | 59.16 | 75.87 | 58.36 | 43.00 | 58.17 |
| ✔ | ✔ | ✔ | | 69.80 | 72.86 | 82.56 | 59.35 | 76.11 | 58.46 | 43.33 | 58.83 |
| ✔ | ✔ | ✔ | ✔ | **70.20** | **73.46** | **82.78** | **59.45** | **76.30** | **58.53** | **43.41** | **59.06** |

**这张表信息量极大，我逐条读**：

- **CMC 单独加，在 MOT17 上 HOTA +0.46**（68.13→68.59），在 **MOT20 上 HOTA +0.75 / IDF1 +0.94**（58.35→59.10），在 **DanceTrack 上 HOTA +4.96 / AssA +6.44**（53.07→58.03）。
  - 等一下，DanceTrack 是手持拍摄、相机抖动剧烈，所以 CMC 收益巨大。
  - 但 **MOT20 是固定相机**（论文自己说的：*"MOT20-val, which is captured from static cameras"*），**居然也涨了 0.75 HOTA**。这说明 CMC 在静态相机上并非完全无用——它会白吃一点计算，但也不是负收益。
  - **关键对照**：DeepMoveSORT 论文明确说 *"We did not see significant improvements (i.e. more than 0.1 as measured in terms of HOTA) when we applied CMC to MOT20, DanceTrack, SportsMOT, or SoccerNet datasets."* —— 跟 Deep OC-SORT 的结论**互相矛盾**。这个矛盾很可能来自两者 CMC 实现不同（DeepMoveSORT 用 OpenCV GMC 但接入点不同）。**这是我们判断 CMC 时的主要不确定点。**
- **外观（Appr.）单独加，MOT17 HOTA +1.53，DanceTrack +0.50**；再加 DA 再 +0.06 / +0.08。**注意 DanceTrack 上外观只值 0.5——因为舞者长得一样，外观本来就没信息。** 我们的场景是「人不多、可能穿不同衣服」，介于 MOT17（外观有用）和 DanceTrack（外观无用）之间。
- **AW（自适应加权）在已经全开的基础上还能 +0.4 HOTA、+0.6 AssA、+0.22 IDF1**（MOT17）。原文：*"AdaptiveWeighting provides yet another consistent improvement in performance across all metrics and datasets."*

### Hybrid-SORT / DeepMoveSORT（2024-2026）——工程化堆料，以及一个残酷的诚实结论

DeepMoveSORT 是 "Hybrid-SORT: Weak cues matter" 的后续（Hybrid-SORT 提出 TCM 轨迹置信度建模；DeepMoveSORT 把 KF 换成 Transformer 滤波器 TransFilter）。

它的 DanceTrack 组件 ablation（**这是全文对我们最有参考价值的一张表**）：

| Filter | HPC | DT-IoU | ATCM | Appearance | HOTA | IDF1 | MOTA |
|---|---|---|---|---|---|---|---|
| TransFilter | Yes | Yes | Yes | Yes | **72.6** | 78.9 | 91.0 |
| **KF** | Yes | Yes | Yes | Yes | **70.1** | 74.7 | 91.2 |
| RNNFilter | Yes | Yes | Yes | Yes | 72.4 | 79.0 | 90.8 |
| TransFilter | **No** | Yes | Yes | Yes | 72.6 | 78.9 | 91.0 |
| TransFilter | Yes | **No** | Yes | Yes | **70.7** | 75.8 | 91.0 |
| TransFilter | Yes | Yes | **No** | Yes | 72.4 | 78.6 | 91.0 |
| TransFilter | Yes | Yes | Yes | **No** | **66.0** | 70.8 | 90.8 |
| TransFilter | No | No | No | Yes | 70.6 | 75.8 | 91.0 |

读法：

- **把 Transformer 滤波器换回普通 Kalman，DanceTrack HOTA 只掉 2.5**（72.6→70.1）。所以「学会学习的滤波器」值 2.5 HOTA —— **代价是要在板上训/跑 PyTorch，我们直接出局。**
- **DT-IoU（遮挡期衰减的 IoU 阈值）值 1.9 HOTA、1.8 IDF1**（72.6→70.7）。这是个**纯几何、零训练**的机制，性价比极高。
- **HPC（Horizontal Perspective Cues）值 0.0 HOTA** —— 原文说它在 DanceTrack 上没用，但在**拥挤场景**有用。
- **ATCM（自适应轨迹置信度）值 0.2 HOTA —— 作者说它是 DanceTrack 上最有用的启发式**（*"The ATCM heuristic proves to be the most beneficial heuristic in this case, mainly due to crowded scenes with many occlusions"*）。注意数字小是因为 DanceTrack 本身不挤。
- **Appearance 值 6.6 HOTA**（72.6→66.0）。**这是全表最大的单项。** 但注意这是在 DanceTrack 上，而 DanceTrack 的外观按理说是**最没信息**的（都是舞者）—— 这很反直觉，说明**在这个 regime 下 ReID 起了别的用**（可能是提供互补的失败模式多样性），而不是「认脸」。

HPC 的定义对我们**特别相关**，值得原样贴出来：

> "due to perspective, objects that are further away appear higher on the y-axis on the coordinate system of the image frame. Instead of simply using the L1 distance, we focus on **the bounding box's height and bottom position**, as these tend to fluctuate less over time compared to the width and x-axis position... We define the Horizontal Perspective Cues (HPC) cost C_HPC between the predicted track bounding box x̂ and the detection D as:
> **C_HPC(x̂, D) = λ_h·|x̂_h − D_h| + λ_y·|x̂_y − D_y|**
> where x̂_h and D_h are the heights of the predicted bounding box and detection, respectively, x̂_y and D_y are their **bottom y-axis positions**"

**这正是对「斜视走廊 + 透视」这个条件的直接答案**：用**框高**和**框底边 y** 做关联代价，因为这两个量在透视下比 x 和框宽稳定得多；而且框底边 y 就是「脚点」的近似。

### C-BIoU（WACV 2023）—— 一个纯几何的、几乎免费的强机制

机制：把 IoU 换成 **BIoU（Buffered IoU）**——把框按比例放大后再算 IoU，中心、宽高比、形状都不变，只是「匹配空间」被撑大了。然后**级联**两次：先用小 buffer (`b1`)，剩下的再用大 buffer (`b2`)。

DanceTrack 验证集上的 ablation（oracle detections）：

| Tracker | 级联匹配 | 运动估计 | HOTA | DetA | AssA | MOTA | IDF1 |
|---|---|---|---|---|---|---|---|
| IoU Tracker | ✗ | ✗ | 76.6 | 97.5 | 60.2 | 99.2 | 73.6 |
| GIoU Tracker | ✗ | ✗ | 77.1 | 97.6 | 60.9 | 99.2 | 74.0 |
| DIoU Tracker | ✗ | ✗ | 75.1 | 97.0 | 58.2 | 99.2 | 72.9 |
| BIoU Tracker | ✗ | ✗ | 78.1* | … | … | … | … |
| **C-BIoU Tracker** | ✔ | ✔ | **81.7** | 97.6 | 68.4 | 99.3 | **80.5** |

（*BIoU 单独一行的确切数值在 PDF 表格中被排版打散，原文文字说「integrating cascaded matching and BIoU can slightly improve... with a HOTA gain of 0.2 on DanceTrack」；下面那行 81.7 是 C-BIoU 完整版。）

**注意对比**：同一张表里 **OC-SORT 在 DanceTrack 验证集只有 79.1 HOTA / 76.1 IDF1**，**C-BIoU 是 81.7 / 80.5**。也就是说**一个纯几何的 buffer 技巧打败了 OC-SORT 的一整套观测中心机制**（在 DanceTrack 上）。这与 Roboflow 独立复现的 DanceTrack 测试集结果一致：**C-BIoU tuned IDF1 58.7 / MOTA 92.4，是那张表里最高的**。

**但 C-BIoU 有一个必须知道的致命限制**，论文自己的 Table V：

| 检测噪声 | Tracker | HOTA | DetA | AssA | MOTA | IDF1 |
|---|---|---|---|---|---|---|
| 0% | OC-SORT | 79.1 | 97.7 | 64.0 | 99.6 | 76.1 |
| 0% | IoU Tracker | 76.6 | 97.5 | 60.2 | 99.2 | 73.6 |
| 0% | C-BIoU Tracker | 81.7 | 97.6 | 68.4 | 99.3 | 80.5 |
| 20% | OC-SORT | 61.4 | 78.3 | 48.1 | 79.3 | 65.3 |
| 20% | IoU Tracker | 57.6 | 79.5 | 41.7 | 81.7 | 59.6 |
| 20% | C-BIoU Tracker | **62.3** | 78.3 | 49.5 | 79.2 | **66.0** |
| **40%** | OC-SORT | 28.0 | 40.4 | 19.4 | 41.4 | 34.3 |
| **40%** | **IoU Tracker** | **38.3** | **58.6** | **25.0** | **60.4** | **40.8** |
| **40%** | C-BIoU Tracker | **29.2** | 58.0 | **14.7** | 57.7 | **29.1** |

**读法（极重要）**：检测噪声到 40% 时，**最朴素的 IoU Tracker 反而比 C-BIoU 好得多**（HOTA 38.3 vs 29.2，IDF1 40.8 vs 29.1）。原因很直白：**buffer 把匹配空间撑大，检测噪声大时会把错误的框也拉进来配上，AssA 从 25.0 崩到 14.7。**

> **对我们场景的直接含义**：C-BIoU 的收益极度依赖检测质量。我们现在 `conf=0.15`（很低，为了召回）意味着**低分框里混着大量噪声**。在这种检测质量下盲目加大 buffer 可能适得其反。**必须先量一下我们门口区域的实际检测质量，再决定 buffer 大小。**

而且论文说 buffer 尺度**敏感度极高**：`b1, b2` 在 0.1~0.7 里扫 21 种组合，**只有 [0.3, 0.4] 给最大 HOTA**。这不是一个「设了就不管」的参数。

## 硬数据横向对比

### MOT17 测试集（YOLOX 检测，Roboflow 独立复现，trackers v2.3.0，2026-03）

| Tracker | HOTA (默认) | IDF1 | MOTA | HOTA (调参后) | IDF1 | MOTA |
|---|---|---|---|---|---|---|
| SORT | 58.4 | 69.9 | 67.2 | 60.4 | 72.5 | 75.8 |
| ByteTrack | 60.1 | 73.2 | 74.1 | 60.5 | 72.7 | 76.1 |
| OC-SORT | 61.9 | 76.4 | 76.0 | 62.0 | 76.5 | 77.3 |
| BoT-SORT | **63.7** | 78.7 | **79.2** | **63.8** | 78.7 | **79.4** |
| C-BIoU | 63.0 | **79.1** | 77.4 | 63.0 | **79.1** | 77.4 |

调参后 **SORT → ByteTrack 只涨 0.1 HOTA、0.2 IDF1**。**ByteTrack → OC-SORT 涨 1.5 HOTA、3.8 IDF1。** 这是很干净的「边际收益递减」证据。

## 学术界共识与争议

### 争议一：低分框二阶段关联到底有多关键？

**支持方证据**：ByteTrack 自己的核心 ablation（前文表格）+ BYTE 套到 9 个 tracker 上 IDF1 涨 1~10 点。Roboflow 的结论也直接：*"ByteTrack is the default recommendation for most applications... The two-stage association adds almost no extra compute and consistently reduces missed tracks and identity switches."*

**反方证据（很硬）**：
1. **Ultralytics 把 OC-SORT 和 Deep OC-SORT 的 `use_byte` 默认设成了 `False`**。源码注释直写：`use_byte: False # (bool) Enable ByteTrack-style low-confidence second association pass`。OC-SORT 论文自己也**没有**用 BYTE（它用的是 OCR 重连）。
2. **Ultralytics Deep OC-SORT 的类文档字符串明确列出**：*"ByteTrack-style low-confidence second pass **disabled by default**"*，并且把「OCR recovery pass」列为替代方案。
3. **C-BIoU 的 cascade 在语义上取代了 ByteTrack 的第二阶段**：Roboflow 文档写 *"In this implementation, this larger buffer corresponds to ByteTrack's recovery stage for unmatched tracks and low-confidence detections."*
4. **C-BIoU Table V 的教训**：低分框在检测噪声大时是**负担**，不是资产。BYTE 之所以在 MOT17 有效，是因为 MOT17 的 YOLOX 检测器在低分区间里 TP 明显多于 FP（ByteTrack 论文 Figure 4 用真实标注验证过这一点）。**这个前提在我们的低 conf 设置下未必成立。**

**我的判断**：二阶段关联本身是对的（「漏检时用低分框救一下」），但**它不是免费的**——它会引入假阳性配错，而且这个风险随检测噪声上升。**关键在于低分区间里的 TP/FP 比**，必须实测。

### 争议二：只跟踪人、一屏个位数时，ReID 是否必要？

**反方（省掉 ReID）**：
1. **ByteTrack 论文**：*"we surprisingly find BYTE also has additional gains compared with DeepSORT. This suggests **a simple Kalman filter can perform long-range association and achieve better IDF1 and IDsw when the detection boxes are accurate enough**. We note that in severe occlusion cases, **Re-ID features are vulnerable and may lead to identity switches, instead, motion model behaves more reliably.**"*
2. **DanceTrack 的立论**：整个数据集就是为了证明「外观不 discriminative 时 ReID 是 bias」。官网原文：*"existing tracking datasets, where most objects tend to have distinguishing appearance and re-ID models are sufficient for establishing associations. In response to such bias, we would like to re-emphasize that methods for multi-object tracking should also work when object appearance is not sufficiently discriminative."*
3. **Savant 的小目标跟踪综述**：*"**Do not buy appearance re-identification.** At this scale you are paying a **4.3× throughput tax** for an embedding computed from one pixel."*
4. **DeepMoveSORT 在静态数据集上不用 CMC / 大幅依赖外观**，但它的 SportsMOT 结论是外观值 6.6 HOTA，DanceTrack 值 6.6 HOTA —— **数字上外观很值钱**。

**正方（要 ReID）**：Deep OC-SORT ablation 的外观项 MOT17 +1.5 HOTA；BoT-SORT-ReID 是 MOT17/MOT20 双榜第一。

**我的判断（结合我们的约束）**：
- **工程上 ReID 在我们板上直接出局**：`ultralytics/trackers/utils/reid.py` 第一行硬 `import torch`；Deep OC-SORT 的 ReID 依赖 `fast_reid`（torchreid），要单独下载 SBS-50 权重再跑一次前向。RK3588 NPU 已经被 YOLO 占了一核，没有余量再跑一个 ReID 网络；CPU 跑 ReID 又会把帧率进一步打下去——而我们**最缺的就是帧率**。
- **业务上 ReID 收益可疑**：我们是「门口 1~2 米区域内、通常 1 个人、偶尔 2 个」。ReID 的价值在于**长时间遮挡后重连**（换衣服/走回来）。我们门口区域没有人能遮挡那么久。反而 ByteTrack 论文说的「ReID 在严重遮挡下脆弱、会导致 ID switch」对我们更贴切。
- **结论：不抄 ReID。** 如果真要重连，用**位置 + 时间 + 框高**（HPC）做几何重连就够了。

### 争议三：恒定速度 Kalman 在急停/转向时的问题

**共识：这是公认的、被反复证实的缺陷。**

- OC-SORT 论文标题就是冲这个来的：*"Kalman filter (KF) based methods for MOT make an assumption that objects move linearly... **linear estimates of motion for prolonged time can be highly inaccurate**. Moreover, when there is no measurement available to update Kalman filter parameters, the standard convention is to trust the priori state estimations for posteriori update. **This leads to the accumulation of errors during a period of occlusion.**"*
- **ByteTrack 论文直接在 BDD100K 上把 Kalman 关掉了**（前文引文）。
- **实测数据（最有说服力的一条）**：一篇 2025 年的论文在**快速移动小目标**（壁球，150mph+）上评测了 5 个 SOTA KF tracker，结论是全部崩溃：

  | Scenario | Metric | DeepOCSORT | OCSORT | StrongSORT | BoTSORT | ByteTrack |
  |---|---|---|---|---|---|---|
  | 1 | ADE (px, 越低越好) | **22.97** | 65.26 | 99.82 | 51.7 | 39.4 |
  | 2 | ADE | **31.31** | 93.5 | 169.7 | 158 | 146.4 |
  | 3 | ADE | **50.42** | 111.8 | 157.22 | 74.11 | 56.48 |
  | 4 | ADE | **19.9** | 39.16 | 153.7 | 178.5 | 215 |

  原文：*"all Kalman filter-based trackers exhibit significant tracking drift with spatial errors ranging from 3-11cm... **The KF assumptions fail** because... There is a short and frequent change in motion that **breaks the internal state parameters of the KF** leading to poor tracking performance."*

  注意 **DeepOCSORT 全面最优**，且原文归因于它的**自适应外观 + 自适应加权**机制（而非滤波器本身）。

- **OC-SORT 的 ORU 就是为了修这个**（+1.4 HOTA on MOT17）。但 ORU 只在**轨迹重连时**触发，它修的是「遮挡期」，不是「急停/转向」本身。

**对我们的具体含义**：人走过门口时会有「转身进门」这个动作——从横向走变成纵向走（甚至停下来掏钥匙）。这正是恒定速度模型最不擅长的。但**我们有一个别人没有的优势**：我们只关心门口那 1~2 米，不关心全局轨迹质量。**一个预测误差在 5 帧内从 10px 涨到 30px 的 Kalman，如果 IoU 阈值足够宽（或 buffer 足够大），照样能配上。**

### 争议四：有没有人证明「简单 IoU 关联 + 好的运动模型」就够用？

**有，而且证据挺强。**

1. **DanceTrack 官方 ablation** 直接给了结论：
   > *"Comparisons of different association strategies on DanceTrack validation set. The detection results are output by the same YOLOX detector. **Both Kalman filter and LSTM outperform naive IoU association by a large margin, indicating the great potential of motion models in tracking objects, especially when appearance cues are not reliable.**"*
   —— 即：IoU 是基线，**运动模型是必需的增量**，外观不可靠时更是如此。

2. **Roboflow 的定性结论**：*"**SORT** is the right choice when speed is the primary constraint and scenes are not heavily occluded... **Use SORT as a baseline before adding more complex trackers, or when deploying on edge devices with tight compute budgets.**"*

3. **Savant 的小目标跟踪结论**（那段关于「六年关联研究后被 2016 年的 Kalman + 换掉 IoU 打败」）：
   > *"Twenty years of association research, and on small objects the winning configuration is a **2016 Kalman filter with the IoU replaced**."*
   > *"Replace IoU with **expanded IoU plus a normalised centre-distance penalty**. That plus **EMA velocity** is **+11 SO-HOTA measured, with no new model**."*

4. **C-BIoU 的 Harness 实验**：一个**没有任何运动模型**的纯 IoU tracker（只做几何匹配），在 DanceTrack oracle 检测下拿到 **76.6 HOTA**；加上运动估计（"we simply average the speeds of recent frames"——**连 Kalman 都不是，就是速度求平均**）后到 81.7。**也就是说「运动模型」的实质贡献可以由「最近几帧速度的滑动平均」提供，不需要 Kalman。**

**综合**：学术界的共识正在往「**运动模型必需，但不必是 Kalman；关联度量（IoU 的变体）比滤波器架构更重要**」这个方向收敛。Learned filter（TransFilter）值 2.5 HOTA，但代价是训练 + GPU。

### 逐个看的真实结论

#### `boxmot` —— **不要用**（对我们）

- 8313 stars、维护极活跃、算法最全（bytetrack / botsort / ocsort / deepocsort / strongsort / hybridsort / sfsort / occluboost / boosttrack）。
- **但它是 PyTorch-first 的重框架。** `find boxmot -name "*.py" | xargs wc -l` = **141,910 行**。而且**在任何 tracker 能跑之前，要先加载 3722 行的 `boxmot/trackers/common/` 基础设施**（`base.py` 872 行、`factory.py` 343 行、`config.py` 421 行、`registry.py` 194 行、`specs.py` 238 行…），这是 DI 容器 + 插件注册表 + 配置系统的组合。
- 单个 tracker 本体其实不大：bytetrack 511 行、ocsort 623 行、deepocsort 624 行、strongsort 693 行。**也就是说 90% 的代码是框架，不是算法。**
- `pyproject.toml` 硬依赖 `torch`（连 CPU 版都要从 `download.pytorch.org` 拉专用 index）。
- **AGPL-3.0**。对比赛原型不算问题，但如果日后要交付/闭源，AGPL 是传染性的。
- **可持续性评估**：单人项目（mikel-brostrom 一个人 3542 commits，第二贡献者只有 46）。资金来自 Zenodo DOI + Discord，**没有大厂/基金会背书**。活跃是活跃，但**bus factor = 1**。

**结论**：boxmot 是很好的 benchmark harness 和算法参考书，**但它的架构理念（可插拔、DI、多后端）与我们的「初级程序员不看注释能读懂」标准完全相反**，且拖 PyTorch，板上装不了。

#### `OC_SORT` 官方实现 —— **推荐作为抄写对象**

- 1153 stars 不算多，但**质量真的高**，而且**活着**（2026-04 还有 PR 合入，作者 Jinkun Cao 是 Amazon 的人，`jinkunc@amazon.com` 出现在 commit 里）。
- 核心代码量：
  - `trackers/ocsort_tracker/ocsort.py` **427 行**
  - `trackers/ocsort_tracker/association.py` **333 行**
  - `trackers/ocsort_tracker/kalmanfilter.py` **1611 行** ← **这是唯一的坑**
- **依赖分析（关键）**：
  - `association.py` 只有 `import numpy as np`，匈牙利算法用 `scipy.optimize.linear_sum_assignment`，或者可选的 `lap` 包。**纯 numpy + scipy，没有 torch。**
  - `ocsort.py` 只 import `numpy` + 自己的 `association` + `kalmanfilter`。
  - **`kalmanfilter.py` 1611 行里有 13 处 `filterpy` 引用**——它是从 FilterPy（Roger Labbe 的库，MIT）**整份 copy 进来的**，而这个 copy 版本把 `filterpy` 当成外部依赖没删干净。
  - 好消息：**MOT17 之外的部分（yolox/、trackeval/、motmetrics/）完全不需要**。`trackers/ocsort_tracker/` 三个文件总共 **2371 行**，其中 1611 行是不必要的通用 Kalman 实现。
- **仓库里还有 C++ 移植**（`deploy/OCSort/cpp/src/`：`OCSort.cpp` / `KalmanBoxTracker.cpp` / `KalmanFilter.cpp` / `lapjv.cpp`），说明这算法被认真工程化过。2026 年 4 月刚做过 "cpp implementation overhaul and optimization"。
- 它有 25 个 open issues，但 PR 流转正常（141/136/135/134 都在 2025-2026 年被合入）。

**结论**：OC-SORT 的**算法本身**（ORU + OCM + OCR）值得抄；**官方实现不要整个拿**，因为那个 1611 行的 filterpy 副本是负担。

#### `ultralytics` 内置 trackers —— **代码质量最高，但 AGPL**

**这是本次调研最大的意外收获。** Ultralytics 在 2026 年已经把 OC-SORT、Deep OC-SORT 全部内置了：

- `ultralytics/trackers/` 共 **2630 行**（不含 utils），`utils/` 共 **1374 行**。
- `oc_sort.py` **356 行** —— 完整的 ORU/OCM/OCR 实现，写得比官方仓库**干净得多**（有类型标注、有清晰的 hook 方法 `_pre_first_associate` / `_post_first_association` / `_fuse_appearance`）。
- `deep_oc_sort.py` **267 行**。
- `bot_sort.py` **219 行**（官方是 474 行）。
- `utils/kalman_filter.py` **485 行**，**纯 numpy，没有 filterpy**！这个 `KalmanFilterXYAH` 就是 OC-SORT 需要的那个 KF，而且只有 218 行（`KalmanFilterXYAH` 到 288 行），另 200 行是 `KalmanFilterXYWH`（BoT-SORT 用）。
- `utils/matching.py` **168 行**，`linear_assignment` 封装了 `lap.lapjv` 和 `ultralytics.utils.ops.linear_sum_assignment` 两条路。

**关键发现**：`ultralytics/trackers/byte_tracker.py` 只 import `numpy` + `..utils.LOGGER` + `..utils.ops` + 同目录几个文件，**不 import torch**。`oc_sort.py` 同样纯 numpy。

**更好的消息**：`deep_oc_sort.py` 的类文档字符串**主动列出了 Ultralytics 对 Deep OC-SORT 原始实现的修正**，这是一份免费的技术审计：

```
Fixes over naive integration:
- GMC correctly handles XYAH state (rotates only x,y positions, not aspect ratio/height)
- Cost combination uses min(IoU, appearance) following BOTSORT's proven approach
- OCR recovery pass also uses appearance features
- ByteTrack-style low-confidence second pass disabled by default
```

以及 `multi_gmc` 的 docstring 里讲了**一个我们绝对会踩的坑**：

> "The standard `multi_gmc` helper from `utils.stracks` would rotate `(a, h)` along with `(x, y)`, which is **wrong for an aspect-ratio dim**. This variant only rotates the position `(x, y)` and the velocity `(vx, vy)` blocks, leaves `(a, h)` and `(va, vh)` untouched"

**坏消息**：
- **AGPL-3.0**。整个 ultralytics 是 AGPL，这些 tracker 文件头部都写着 `# Ultralytics 🚀 AGPL-3.0 License`。**你不能「借鉴」代码再闭源。**
- `utils/reid.py` **硬 `import torch`**（第 15 行）。一旦要 ReID 就必须有 torch。

**结论**：**当参考实现读，抄设计不抄代码**。尤其 `oc_sort.py` 的 ORU 实现（`apply_oru` 方法，30 行）和 `_velocity_direction_cost`（34 行）是极好的伪代码。

#### `norfair` —— 轻但不对路

- 2694 stars，BSD-3-Clause（最友好的 license），核心 `tracker.py` 792 行、`distances.py` 550 行、`camera_motion.py` 441 行。
- **但它的抽象层次不对**：norfair 是「给任意 detector 加跟踪」的通用库，核心抽象是 `TrackedObject` + `Distance` 函数（可以塞任意自定义距离，包括 `IouDistance`、`CosineDistance`、`ScipyDistance`）。它**没有 Kalman 运动模型**（用的是一个简单的 `mean`/速度外推）。
- 最后 commit **2025-04-30**，一年多没动。
- **结论**：不适用。我们要的恰恰是「好的运动模型」，而 norfair 的卖点是「灵活的距离函数」。

#### 已死 / 不推荐

- **`Deep-OC-SORT` 官方**：286 stars，**最后 commit 2023-05-06**，3 年没动。代码里拖了整个 `external/fast_reid`（含 `nasnet.py` 991 行）和 `external/deep-person-reid`，还有 `Caffe/caffe_pb2.py` 10970 行。**总共 96,147 行 Python**。这是纯学术仓库。
- **`ByteTrack-V2`**：170 stars，**2023-03-27 后没动**。基本没人在用。
- **`NirAharon/BoT-SORT`**：1565 stars 但 **2024-08-08 后停更**，79 open issues。而且它捆绑了 `fast_reid/` 整个目录。
- **`ImprAssoc`**：**我搜遍 GitHub 和 Google Scholar 都没有这个东西**。可能是记忆中的名字有误，或者根本不存在。**不作为选型考虑。**

| ultralytics `utils/kalman_filter.py` | 否 | 否 | 否 | **218 行**（XYAH 部分） | 2 |
| OC-SORT 官方 `ocsort_tracker/` | 否 | **是**（或 lap） | 否 | **2371 行** | 8 |
| BoT-SORT 官方 `tracker/` | **是**（ReID） | 是 | 否 | **~2000 行** + fast_reid | 15+ |
| Deep OC-SORT | **是** | 是 | 否 | **~2400 行** + fast_reid | 15+ |
| boxmot | **是** | 是 | 否 | **141,910 行**（含框架 3722 行） | 30+ |

### 纯 numpy 能不能重写？能。

关键证据：
- **`ultralytics/trackers/utils/kalman_filter.py` 就是纯 numpy 的**，485 行里 `KalmanFilterXYAH` 只占 218 行。**可以直接照着自己写一个 60~80 行的 7 维或 8 维 KF**——矩阵都是固定的常量，predict/update 各一次矩阵乘法。
- **匈牙利算法**：`scipy.optimize.linear_sum_assignment`。板上 `scipy` 是纯 Python + numpy 编译的，能装但有点重。**但我们的问题规模极小（一屏个位数人，候选矩阵 个位数 × 个位数）**——现有 `_match` 的**贪心 IoU 已经够用**。OC-SORT 官方代码自己也有这个判断：
  ```python
  a = (iou_matrix > iou_threshold).astype(np.int32)
  if a.sum(1).max() == 1 and a.sum(0).max() == 1:
      matched_indices = np.stack(np.where(a), axis=1)   # 唯一匹配，直接取
  else:
      matched_indices = linear_assignment(-iou_matrix)  # 才用匈牙利
  ```
  **「每行每列最多一个候选时直接取，否则才上匈牙利」—— 这个短路在我们的稀疏场景下几乎总是生效。** 也就是说**可以完全不引入 scipy**。
- **`lap`（Jonker-Volgenant）需要 C 编译**，板上装它会引入工具链依赖。**不装。**

### 参数量对比（我们的心理负担指标）

现有 `ByteTracker.__init__` 只有 4 个参数：`high_conf=0.4, iou_thresh=0.3, max_age=10, min_hits=2`。这符合项目「初级程序员不看注释能读懂」的标准。

如果要加 OC-SORT 的机制，新增参数是：
- `delta_t=3`（OCM 速度方向的帧间隔）
- `inertia=0.2`（OCM 权重）
- `max_age` 要调大（DanceTrack 上 SORT 调参把 buffer 从 30 提到 91）

**净增 2 个参数。** 可接受。

如果加 C-BIoU：`buffer_ratio_first`、`buffer_ratio_second`，**净增 2 个，但这两个参数敏感度极高**（只有 [0.3, 0.4] 最优），我不建议引入。

## 落到我们场景的结论

### 值得抄的机制（按性价比排序）

#### 1. ORU（Observation-centric Re-Update）—— **最值得，优先级第一**

**证据**：OC-SORT ablation，ORU 单独加 MOT17 HOTA 64.9→66.3（**+1.4**），DanceTrack 47.8→48.5（+0.7）；原文说 *"the performance gain from ORU is significant on both datasets"*。它修的正是我们的病：**漏检若干帧后轨迹重连时，Kalman 状态已经被先验污染，导致 IoU 掉到阈值以下**。

**为什么值**：我们丢 ID 的头号机理就是「漏了几帧 → tracker 用外推位置跟当前框配 → IoU 不够 → 新建 id → 跨线那一刻新的 id 没有 side 记录 → 漏计」。ORU 直接修这个。

**代价**：`ultralytics/oc_sort.py` 的 `apply_oru` 方法**只有 30 行**，纯 numpy。逻辑是：重连时把状态回滚到最后一次真实观测，在旧观测和新观测之间线性插值出「虚拟观测」，逐帧 predict+update 走一遍，再 predict 到当前帧。

**不改架构**：可以作为一个「轨迹重连时」的分支加进现有 `Track.update()`。新增参数 0 个（`gap` 是算出来的）。

#### 2. 用「框高 + 框底边 y」而不是「框中心」做关联与判定 —— **优先级第二，且能同时修两个问题**

**证据（关联侧）**：DeepMoveSORT 的 HPC 机制定义（原文公式已贴在前文）：`C_HPC = λ_h·|ĥ−h| + λ_y·|ŷ−y|`，其中 y 是**底边**。原文理由是 *"due to perspective, objects that are further away appear higher on the y-axis... these [height and bottom position] tend to fluctuate less over time compared to the width and x-axis position"*。DanceTrack 上 HOTA 增益 0.0（不挤），但原作者说它在**拥挤场景**有用，且这是专门为**透视相机**设计的机制。

**证据（判线侧）**：一篇 2026 年 MDPI 的室内行人计数论文明确采用：
> *"we adopt **the center point of the bottom boundary** of the pedestrian target bounding box as the designated position of the pedestrian."*
> —— [Optimization of Indoor Pedestrian Counting](https://www.mdpi.com/2220-9964/15/3/136)

**为什么值（这是本文我最想强调的一点）**：我们现在的 `counter.py` 用 `t.center`（框中心）。在**斜视透视**下，人走向相机时框变高，**框中心会向下漂移**；而人的实际位置（脚）几乎不动或移动方向相反。这会造成 side 的**假翻转**——即**多计**。反过来人远离时框变矮、中心上移，也可能假翻转。

**用框底边中点（脚点）**：
- 透视下，脚点是**地面点**，它的运动轨迹直接对应人在走廊地面上的真实位移，缩放关系是单调的、方向正确的。
- 判定线画在门口地面上时，与脚点的几何关系稳定，不随框大小变化。
- 代价：**零**。`counter.py` 改一行：`cy` 从 `(y1+y2)/2` 改成 `y2`。同时**判定线应该画在地面的门口线上**（而不是画在人身上任何高度），并把死区改为按「脚点尺度」算。

**这是本次调研性价比最高的单点改动，一次改动能同时改善「关联」和「判定」两侧。**

#### 3. OCR（Observation-centric Recovery）—— **优先，廉价保险**

**证据**：OC-SORT ablation 里 OCR 值 +0.1 HOTA / −0.1 IDF1（很小），**但**它是用 `last_observation`（上次真实观测框）而非 Kalman 预测框去做第二次 IoU。当 Kalman 飘了之后，这一步是兜底。

**为什么值**：我们现在的两阶段是「高分框 → 低分框」，**没有任何一阶段用「上次真实观测位置」兜底**。加上 OCR 等于多一层保险，而且它是「拿真实观测去配」，不依赖运动模型质量。

**代价**：`Track` 多存一个 `last_observation` 字段；新增一次关联循环，~30 行。

#### 4. 把 `max_age` 调大 —— **零成本，可能是收益最大的一项**

**证据（硬）**：Roboflow 在 DanceTrack 上 grid search 的结果显示，**SORT 把 `lost_track_buffer` 从默认 30 提到 91（3 倍），HOTA 从 47.2 涨到 54.3（+7.1）**，是所有 tracker 里调参增益最大的。同时 `minimum_iou_threshold` 从 0.3 降到 0.21、`minimum_consecutive_frames` 提到 3。

**为什么值**：我们的 `max_age=10`（10 帧）在低帧率下可能只对应 **1~2 秒**。人走过门口 + 转身进门这个过程，中间完全可能被门框遮挡 1~2 秒。**轨迹在被遮挡期间就死了**，再出现时是全新 id，跨线判定失败。

**但有个陷阱**：`max_age` 调大会让「已离开视野的轨迹」长期存活，如果它被错误地重连到另一个人身上，就会**多计**。所以 max_age 调大**必须配合 OCR/ORU**（用真实观测重连，而不是靠 Kalman 外推位置瞎配）。

**建议**：配合 `min_hits` 一起想。我们 `min_hits=2` 意味着新轨迹要 2 帧才被返回——如果人在门口只被检测到 1 次就过去了，**这条轨迹永远不返回，直接漏计**。在低帧率场景下 `min_hits` 应该考虑降到 1。

#### 5. OCM（Observation-centric Momentum）—— **可选，低优先**

**证据**：OC-SORT ablation 显示 **OCM 在 MOT17（相机相对稳）上只值 +0.1 HOTA，在 DanceTrack（剧烈运动）上值 +3.6 HOTA**。原文：*"OCM only shows good help on DanceTrack dataset where object motion is more complicated."*

**判断**：我们相机**完全固定**，人走的是直线（走廊），**不是 DanceTrack 那种剧烈非线性运动**。OCM 的收益按 MOT17 那档估（~0.1 HOTA）。而且它的实现依赖 `delta_t`，**在变帧率下这个参数会失真**（见「不确定点」）。**建议：先不做。**

#### 6. 动态帧率（timestamp-aware prediction）—— **值得，但依赖我们对帧率做改造**

**证据**：Roboflow trackers 库专门有 `dynamic-frame-rate` 模式，文档讲得很清楚：

> *"Most tracking examples assume you call `update()` once per video frame, in order, at a steady FPS. That breaks when **frames are dropped** (you skip frame 2 but still call `update()` on frame 3) or when you **only process some frames**."*
> *"**Process noise** grows on longer gaps so the box does not stay artificially tight. Within the ~4 ms wall-clock tolerance of `frame_step = 1.0` you get the same as with default usage. On bigger steps the library **rescales noise the way a constant-velocity model expects (stronger growth on position than velocity)**, instead of naively multiplying a one-frame matrix by Δt."*

**为什么值**：我们的 `viewport.py` **明确「多快算多快，没有帧率目标」**。RK3588 上帧间隔会抖动（NPU 调度、CPU 抢核、UI 渲染）。**固定 dt 的 Kalman 在帧间隔抖动时会系统性地错估速度**——帧间隔变长时它以为人只走了一步。

**代价**：Kalman 的 `predict` 里把固定 `F` 矩阵换成按 `dt` 缩放的版本（位置项 `dt`、速度项 1），`Q` 按 `dt` 放大。**~15 行。** 但前提是我们**得记录每帧的时间戳**——现在 `viewport.py` 没有。

**注意 OC-SORT 的例外**：Roboflow 文档明确说 *"**OC-SORT:** ORU still steps in frame units, not wall-clock gaps."* —— 如果我们抄了 ORU，ORU 内部的虚拟轨迹重放仍然是按帧数算的，跟动态 dt 不一致。这是个已知的、可接受的近似。

### 明确不值得抄的机制

#### 1. ReID / 外观特征 —— **明确不做**

**证据（三重）**：
- **ByteTrack 论文原文**：*"in severe occlusion cases, **Re-ID features are vulnerable and may lead to identity switches, instead, motion model behaves more reliably**."*
- **工程上直接出局**：`ultralytics/trackers/utils/reid.py` 第 15 行 `import torch`；Deep OC-SORT 依赖 `fast_reid`（96,147 行 Python 的 `external/` 目录）。**板上无 torch，NPU 已被 YOLO 占满。**
- **Savant 综述**：*"**Do not buy appearance re-identification.** At this scale you are paying a 4.3× throughput tax."*
- **我们的场景不需要**：门口 1~2 米、通常 1 人、偶尔 2 人。ReID 解决的是「长时间遮挡后重认同一个人」，我们的遮挡最多 1~2 秒，且几何位置已经足够区分。

**唯一反证**：DeepMoveSORT 在 DanceTrack 上外观值 6.6 HOTA（是全表最大单项）。**但这个数字的前提是「有 GPU 且已经跑了 ReID 网络」，我们连前提都不满足。**

#### 2. CMC（相机运动补偿）—— **明确不做**

**证据**：
- **DeepMoveSORT 原文**：*"We use CMC only on the MOT17 dataset, since it is the only dataset with frequent unpredictable camera motion. **We did not see significant improvements (i.e, more than 0.1 as measured in terms of HOTA) when we applied CMC to MOT20, DanceTrack, SportsMOT, or SoccerNet datasets.**"* —— HOTA 提升 **< 0.1**。
- 我们的相机是**固定安装的监控摄像头**，比 MOT20 还稳（MOT20 至少是手持/临时机位）。
- CMC 的实现（`gmc.py`：稀疏光流 + RANSAC）在 315 行左右，每帧要跑一次 `goodFeaturesToTrack` + `calcOpticalFlowPyrLK` + `estimateAffinePartial2D`。**在 RK3588 的 CPU 上这是一笔实打实的帧率开销**，而我们最缺帧率。

**唯一反证（必须诚实标注）**：Deep OC-SORT 的 ablation 显示 CMC 在 **MOT20（静态相机）上也涨了 0.75 HOTA / 0.94 IDF1**。两个来源结论矛盾。**我的判断是：DeepMoveSORT 的结论更可信，因为它明确说了「<0.1 HOTA」这个量化门槛，而 Deep OC-SORT 的 MOT20 增益可能来自 CMC 与它其他机制（自适应加权）的交互。** 无论如何，收益远小于它在我们板上的 CPU 代价。

#### 3. Transformer / learned filter（TransFilter、MOTR、MOTIP）—— **明确不做**

**证据**：
- DeepMoveSORT ablation：**TransFilter 换回 KF 只掉 2.5 HOTA**（72.6→70.1）。也就是说整个「可学习滤波器」的净价值是 2.5 点，**代价是在板上训/跑 PyTorch**。
- MOTIP 类：BFT 数据集 HOTA 70.5（Apache-2.0），但**在 RTX 4090 上只有约 12 FPS，且训练用了 8 张 4090**。
- 端到端方法在 edge 上的共识是「算力 prohibitive」：*"Heavyweight models improve accuracy but are impractical for real-time deployment"*。

**结论**：需要 torch + GPU，**我们的约束下直接不成立**，不需要进一步讨论。

#### 4. C-BIoU 的 buffer —— **不引入，理由比看上去更微妙**

**表面证据很诱人**：DanceTrack 上 C-BIoU（81.7 HOTA / 80.5 IDF1）**击败 OC-SORT（79.1 / 76.1）**，而且是纯几何、零训练。Roboflow 独立复现也确认 C-BIoU 在 DanceTrack 上调参后 IDF1 58.7 / MOTA 92.4 双双最高。

**但 C-BIoU 论文自己的 Table V 是决定性的反对证据**：

| 检测噪声 | IoU Tracker HOTA | C-BIoU HOTA | IoU Tracker IDF1 | C-BIoU IDF1 |
|---|---|---|---|---|
| 0% | 76.6 | **81.7** | 73.6 | **80.5** |
| 20% | 57.6 | **62.3** | 59.6 | **66.0** |
| **40%** | **38.3** | 29.2 | **40.8** | 29.1 |

**检测噪声 40% 时，C-BIoU 全面劣于最朴素的 IoU Tracker。**

**为什么这条直接打中我们**：我们的 `detector.py` 用 **`conf=0.15`**（极低，为了召回快速移动的人）。这意味着**进入 tracker 的框里有大量低分噪声框**。在这个检测质量下加大 buffer，等于**主动把错误的框也纳入匹配空间**（AssA 从 25.0 崩到 14.7 就是证据）。

**而且 buffer 尺度极度敏感**：论文在 0.1~0.7 里扫了 21 种 `[b1, b2]` 组合，**只有 [0.3, 0.4] 给最大 HOTA**。这不是一个能拍脑袋定的参数，需要标注数据来 grid search——**我们是比赛原型，没有标注数据。**

**结论**：**不引入 C-BIoU。** 它的核心思想（匹配空间要能容忍快速运动）是对的，但**正确的实现方式对我们来说是「把 IoU 阈值调低」这一件事**，而不是引入两个敏感参数。Roboflow 的 DanceTrack 调参表也证实了这点：SORT 把 `minimum_iou_threshold` 从 0.3 降到 **0.21** 就拿到了 +7.1 HOTA 的大部分收益。

#### 5. 匈牙利算法 / `lap` / `scipy` —— **不引入**

**证据**：一屏个位数人 → 代价矩阵是 个位数 × 个位数。OC-SORT 官方代码自己就写了短路逻辑：**每行每列最多一个候选时直接取，只有冲突时才上匈牙利**。我们的稀疏场景几乎总是走短路分支。现有 `_match` 的贪心 IoU 在稀疏场景下与匈牙利结果一致。

**代价**：`lap` 需要 C 编译（板上要装工具链）；`scipy` 虽然能装但增加体积和启动开销，而我们只需要它一个函数。

### 最终推荐：一个「三改一调」的最小方案

**不做架构替换，只在现有 84 行 `tracker.py` 上做四处改动：**

| # | 改动 | 行数 | 依据 | 预期收益 |
|---|---|---|---|---|
| 1 | **判定点改脚点**：`counter.py` 的 `t.center` → 框底边中点；判定线画到地面门口线上 | ~3 行 | DeepMoveSORT HPC；MDPI 室内计数论文 | 消除透视引起的假跨线（**多计**） |
| 2 | **加 ORU**：轨迹重连时用虚拟观测重放 KF | ~30 行 | OC-SORT ablation ORU **+1.4 HOTA**（MOT17） | 修「漏检后重连失败 → 丢 ID」（**漏计**） |
| 3 | **加 OCR**：第二次关联用 `last_observation` 而非 KF 预测框 | ~30 行 | OC-SORT OCR | 廉价保险 |
| 4 | **调参**：`max_age` 10 → 30~45；`min_hits` 2 → 1；`iou_thresh` 0.3 → 0.2 | 改 3 个数字 | Roboflow DanceTrack：SORT `lost_track_buffer` 30→91 得 **+7.1 HOTA** | 可能单项最大 |

**总计约 65 行新代码，净增 0 个参数（`delta_t` 不需要，因为不做 OCM）**。仍然是一个初级程序员能读懂的 tracker。

**如果连 Kalman 都不想上**：还有一个更简的版本——**只做 #1 和 #4**，把「KF 预测框」替换成「上次观测框 + 恒定速度外推」（就是 C-BIoU 论文说的 *"we simply average the speeds of recent frames"*）。C-BIoU 的实验表明这一档运动模型已经能拿到 81.7 HOTA（DanceTrack oracle）。这个版本**约 15 行**，零矩阵运算，但抗抖动能力弱于真 KF。

**我的建议是上 Kalman**，因为：板上 numpy 跑 8 维矩阵乘法的开销可以忽略（OC-SORT 论文说纯关联部分在单 CPU 上 700+ FPS），而且 `ultralytics/trackers/utils/kalman_filter.py` 证明了这个 KF 可以是纯 numpy 的 218 行。

### 先量再改：三个必须先测的数字

在动手之前，应该先量三个数（都是几行脚本的事）：

1. **门口区域的检测质量**：站在门口录一段，统计「人在门口时有多少帧被检出」。如果检出率 < 80%，那么问题主要在**检测**而不是跟踪——应该先调 `conf`/`nms`、或门口区域用更大输入尺寸（RK3588 跑 640 有多少余量也要先量）。
2. **实际帧率分布**：`viewport.py` 加一行打时间戳，跑 5 分钟，看帧间隔的 P50/P95。**如果 P95 是 P50 的 3 倍以上，动态帧率改造就是必需的。**
3. **跨线过程的帧数**：人在门口从线的一侧到另一侧，平均被检出多少帧。**如果是 1~2 帧，那么任何 tracker 都救不了，必须降 `min_hits` 到 1 并考虑降低判定线死区。**

## 不确定点与风险

1. **CMC 的结论在两个来源之间矛盾。** DeepMoveSORT 说静态相机上 CMC 收益 <0.1 HOTA；Deep OC-SORT 的 ablation 说 MOT20（静态相机）上涨 0.75 HOTA / 0.94 IDF1。我倾向于前者（更明确的量化门槛），但**这个矛盾没有解决**。对我们的决策影响不大（因为 CPU 代价），但如果以后有余量可以复测。

2. **OC-SORT 的 `delta_t=3` 假设帧率恒定。** 我们的帧率不恒定。Roboflow 文档明确说 ORU 仍然是按帧步进、不吃 wall-clock gap。**如果我们上动态帧率改造，OCM/ORU 会出现内部不一致。** 因为我不建议做 OCM（收益按 MOT17 估只有 0.1 HOTA），这个风险实际很小；但 ORU 的虚拟轨迹重放会受到轻微影响（近似，可接受）。

3. **「框底边中点 = 脚点」在斜视透视下是近似，不是精确。** 当人侧身走过门口、或者两腿分开时，框底边中点会偏离真正的脚落地位置。**DeepMoveSORT 的 HPC 也是把底边 y 当特征用，不是当精确坐标。** 更严格的做法是做地面单应性变换（把图像坐标投影到走廊地面平面），但那需要标定，属于 overengineering——**比赛原型不做。**

4. **DanceTrack 不是我们场景。** DanceTrack 是「相似外观 + 剧烈非线性运动 + 密集人群」。我们是「不同外观 + 近似线性运动 + 稀疏」。所以 DanceTrack 的排名**不能直接搬**：OC-SORT 在 DanceTrack 上调参后一点没涨（说明它被过拟合），而 SORT 调参涨 7.1（说明 DanceTrack 的收益主要来自「调大 buffer」，而不是算法）。**我上面推荐 max_age 调大正是基于这个推理，但它没有在我们自己的数据上验证过。**

5. **我们没有自己的标注数据来验证任何改动。** 上面所有建议都基于公开 benchmark。**在「斜视走廊 + 门口判定线」这个特定任务上，公开 benchmark 的排名与实际收益的相关性未知。** 建议至少手动数一段 5 分钟的视频做 baseline（现在漏计几次），改完再数一次。这是唯一可靠的验证方式。

6. **`ImprAssoc` 不存在。** GitHub 搜索和 Google Scholar 都没有这个东西。如果这是从某处听来的名字，那个来源不可靠。我按「不存在」处理。

7. **所有 ultralytics 的 tracker 代码是 AGPL-3.0。** 我推荐「读设计、抄思路」，但如果直接复制 `apply_oru` 的代码，会引入 AGPL 传染。**要么自己按 OC-SORT 论文（MIT）重写，要么确认项目的 license 兼容性。** 这是需要主智能体/用户决策的事，不是我能在调研层面解决的。
