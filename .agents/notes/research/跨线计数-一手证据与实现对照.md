| 问题 | 结论 | 证据强度 |

## 1. 锚点选择：box center vs 脚点 vs 头

### 1.1 NVIDIA DeepStream `nvdsanalytics` —— 明确用**脚点**

**这是最直接、最可引用的一句官方定义。** 来源：<https://docs.nvidia.com/metropolis/deepstream/dev-guide/text/DS_plugin_gst-nvdsanalytics.html>（2026-10-16 抓取全文）

> "For all the analytics calculations **bottom center coordinate of bounding box** of an object is being used. If bounding box is defined as (x_left, y_top, width, height) then the **bottom center coordinate would be (x_left + width/2, y_top + height)**"

注意 "**For all the analytics calculations**" —— 不只越线，ROI filtering / overcrowding / direction detection **全部**统一用脚点。

同一页还确认了越线需要 tracker：
> "ROI based analytics work on primary detector output, but **Direction Detection and Line Crossing requires a tracker-id as previous history/state is required** to do both the analytics."

`[line-crossing-<n>]` 组的配置键（原文）：
> `line-crossing-<label>`: "The value indicates 2 coordinates of direction followed by 2 coordinates of virtual line... `line-crossing-<label>=x1d;y1d;x2d;y2d;x1c;y1c;x2c;y2c`. The **direction indicates the direction of object in which it should be moving that can be considered for counting**, so the object should be in direction x1d,y1d to x2d,y2d, which indicates a direction vector."

另外两个值得注意的官方键：
> `extended`: "Boolean parameter to check crossings only on the configured line or for the **extended line covering the video frame**. If extended is 0, the line crossing only the configured line would be counted"
>
> `mode`: "Parameter to allow user configuration of adherence of object direction with configured direction for crossing. Possible options **strict, balanced, loose**. Operate as per name suggestion, where **loose will just check if the object has crossed the line and would need the object just to be in same direction with very high tolerance**"

> **对项目的意义**：`mode=loose` 正是"人在线上抖动"场景的官方旋钮；`extended` 解决"贴边越线"。但注意 DeepStream 用脚点，而它**没有**任何死区/连续帧确认参数 —— 防重复计数靠的是 tracker-id 与方向向量，不是 N-of-M。

### 1.2 AXIS Object Analytics —— 明确"脚点"，且**车辆用中心**

来源：<https://help.axis.com/en-us/axis-object-analytics>（文档标注 **September, 2026**；2026-10-16 抓取）

> "Each classified object has a **point of detection** that the application uses to decide if an object is inside or outside an include area or **when it crosses a virtual line**. For a human, the **point of detection is at its feet**, and for a vehicle it's at its center. **If a human's feet or a vehicle's center gets obstructed from the camera's view, the application makes an assumption of the location of the point of detection.**"

以及越线语义（非常关键的一句话，直接回答"停在线上会不会重复计数"）：
> "To trigger an alarm the object must cross the line. As shown in the illustration, the **object's point of detection must cross the line** for the application to trigger. **Objects that only touch the line don't trigger alarms.**"

> "In the illustration to the left, the man doesn't trigger an alarm, as his point of detection has not yet crossed the line."
> "In the illustration to the right, the man triggers an alarm, as his point of detection has crossed the line."

**虚拟线布置建议（原文，可直接抄作业）**：
> "Adjust the virtual line so that: objects are unlikely to be **waiting at the line**; objects are clearly visible in the image **before** they cross the line; an object's point of detection is likely to cross the line."

补充视野/安装约束（斜视走廊直接相关）：
> "**Avoid mounting the camera so that it looks down from above**, since this can make it difficult for the application to classify objects."
> "Make sure the camera tilts far enough toward the ground so that the center of the image is below the horizon. Mount the camera so that the **minimum detection distance is more than half of the mounting height** (minimum detection distance > camera mounting height / 2)."
> "**Objects moving perpendicular to the camera's field of view are detected faster than objects approaching the camera in a straight line.**"
> "Objects need to **move within the scene for at least 2 seconds** to be detected."
> 最小人体高度：**Minimum height 4%, Recommended height 8%**（相对整幅图像高度）。车辆 3% / 6%。

### 2.2 Frigate 路径最小位移阈值 —— **5% 画面对角线**

`frigate/track/tracked_object.py:370-384`：
```python
# calculate a reasonable movement threshold (e.g., 5% of the frame diagonal)
threshold = 0.05 * math.sqrt(width**2 + height**2) / max(width, height)

if not self.path_data:
    self.path_data.append((bottom_center, obj_data["frame_time"]))
    path_update = True
elif (
    math.dist(self.path_data[-1][0], bottom_center) >= threshold
    or len(self.path_data) == 1
):
    # check Euclidean distance before appending
    self.path_data.append((bottom_center, obj_data["frame_time"]))
```

> 这是一个**位移死区**：轨迹点只有移动 ≥ 画面 5% 才记录。对"抖动"天然免疫。**注意它用在路径可视化/速度，不是 zone 判定** —— 不要错误归因。

### 2.4 Ultralytics ObjectCounter —— **无死区，只有永久闩锁**

## 3. 透视 / 斜视：要不要做 IPM（homography 鸟瞰变换）？

### 3.1 结论：**IPM-before-tracking 不是主流工业实践**；主流是**按 y 标定尺度**

我逐仓库 grep 了 `getPerspectiveTransform` / `warpPerspective` / `findHomography`：

- **Ultralytics**：`ultralytics/` 内仅命中 `ultralytics/data/augment.py:1210, 1376, 1403` —— 全是**训练数据增强**的仿射/透视抖动。`ultralytics/solutions/` 内**零命中**。`config.py:37` 只有一句注释 `vision_point (tuple[int, int]): Reference point for directional tracking or perspective drawing.` —— 是画图用的。
- **Savant**：`savant/` + samples 内**零命中** homography/IPM。
- **Frigate**：有"地面平面"但是**双线性按 y 插值**，不是完整单应（见下）。

### 3.2 Frigate `create_ground_plane` —— 工业界的"轻量 IPM"

`frigate/util/velocity.py:30-78`（<https://github.com/blakeblackshear/frigate/blob/62ca5b25ea0a69bc4922e65ff8a26206e5e7336e/frigate/util/velocity.py#L30>）：
```python
def create_ground_plane(zone_points, distances):
    """
    Create a ground plane that accounts for perspective distortion using real-world dimensions for each side of the zone.
    """
    A, B, C, D = zone_points
    AB_px = np.linalg.norm(np.array(B) - np.array(A))
    ...
    AB, BC, CD, DA = map(float, distances)
    AB_scale = AB / AB_px
    ...
    def distance_per_pixel(x, y):
        if (B[0] - A[0]) == 0 or (D[1] - A[1]) == 0:
            return 0
        # Normalize x and y within the zone
        x_norm = (x - A[0]) / (B[0] - A[0])
        y_norm = (y - A[1]) / (D[1] - A[1])
        # Interpolate scales horizontally and vertically
        vertical_scale = AB_scale + (CD_scale - AB_scale) * y_norm
        horizontal_scale = DA_scale + (BC_scale - DA_scale) * x_norm
        # Combine horizontal and vertical scales
        return (vertical_scale + horizontal_scale) / 2
    return distance_per_pixel
```

**关键判断**：
1. 它**不是**单应矩阵，而是**按 y 在两个已知边的真实/像素比值之间线性插值**的 `meters_per_pixel(y)`。
2. 它**只用于速度估计**（`calculate_real_world_speed`，调用点 `tracked_object.py:218-223`），**不参与跟踪，不参与 zone 判定，不做 warp**。
3. 输入是用户在 zone 配置里手填的 `distances: 10,15,12,11`（`reference.md:1021`，"Real-world distances for each side of the zone quadrilateral, used for speed or distance calculations. Must have exactly 4 values if set."）。

> **这实质上就是"按 y 归一化尺度"的落地实现。** Frigate 认为：修正透视是为了**把像素速度换成真实速度**，而不是为了修 IoU 关联。**没有任何一处 warp 图像再做跟踪。**

### 3.3 AXIS `Calibrate perspective` —— **这正是你问题 3 想问的东西**

<https://help.axis.com/en-us/axis-object-analytics>（September, 2026）
> "### Calibrate perspective
> If the scene has a significant depth, you need to **calibrate the perspective to remove false alarms due to small objects**. During calibration, the application **compares the height of the objects as they appear in the image with the actual heights of the corresponding physical objects. The application uses the calibrated perspective to calculate the object size.**
> Place **vertical bars** in the image to calibrate perspective. The bars represent physical objects at different distances from the camera.
> 1. Go to **Settings > Advanced > Perspective** and click **Calibrate**.
> 2. In the live view, choose **two objects of the same, known height**, that are located on the ground and at **different distances** from the camera. You can use, for example, fence poles or a human.
> 3. Place the bars by the objects and adjust the length of each bar to the height of the object.
> 4. Select the scenarios you want to apply the perspective to.
> 5. Enter the height of the objects in **Perspective bar height**."

以及由此带来的下游好处：
> "**Small objects** filter: Note: If you have calibrated the perspective, enter the width and height of objects to ignore in **centimeters (inches) instead of as percentage of the image**."

> **这是对你第 3 问最有力的答案**：AXIS 承认"画面纵深大 → 远处物体小 → 误报"，其解法是**两根竖标尺 + 高度标定**，得到一个 `y → 物体真实高度` 的映射，然后**用它对物体尺寸做归一化**（从而"小物体"阈值可以是厘米而非画面百分比）。
> **它没有把画面 warp 成鸟瞰再跟踪。** 它修正的是"尺寸判据"，不是"关联"。这与你担心的"IoU 关联被大小差异破坏"是**不同的修法**。

### 3.4 学术证据：IPM/homography 出现在哪

**注意：以下为学术文献，与你的单目-单人-越线场景有显著 gap，请谨慎外推。**

- Eshel & Moses, *Homography based multiple camera detection and tracking of people in a dense crowd*, CVPR 2008，被引 261。PDF：<https://faculty.runi.ac.il/moses/papers/CVPR08-EshelMoses.pdf> —— 用 homography 做**多相机**在**密集人群**中的**跨视角融合**。
- Mousse, Motamed & Ezin, *People counting via multiple views using a fast information fusion approach*, Multimedia Tools and Applications 2017，被引 20。PDF：<https://www.academia.edu/download/58413619/mousse2016.pdf> —— 摘要片段："compute a **planar homography projection of each camera's visual**..."。**仍是多视角**。
- Elasal, *Unsupervised Methods for Camera Pose Estimation and People Counting in Crowded Scenes*, York University 2016。PDF：<https://yorkspace.library.yorku.ca/server/api/core/bitstreams/f7c4b604-057a-4b9f-9992-1b5254fb1374/content> —— "the **oblique angle of the camera induces a projective** ... As a final step, I can apply the homography H of Eqn. (2.2)"。**密集人群计数**（密度图回归），不是单人越线。
- Coifman & Li, *Partial trajectory method to align and validate successive video cameras for vehicle tracking*, TR Part C 2024。PDF：<https://par.nsf.gov/servlets/purl/10560106> —— 车辆、**多相机串联**："use a **homographic transformation for each camera** to project... tracking can still be done using **oblique angles** from cameras"。

> **共同点：所有这些 IPM 用法都是 (a) 多相机融合，或 (b) 密集人群密度估计，或 (c) 车辆轨迹对齐。**
> **我没有找到任何一篇论文主张"单目斜视 + 单人越线计数，应先把地面 warp 成鸟瞰，再做 ByteTrack/IoU 关联"。**
> 综合 Frigate/AXIS/DeepStream/Ultralytics/Savant **五家实现全部不做 IPM-before-tracking**，我的判断是：**对你的场景，IPM-before-tracking 属于 overkill / 非实践做法。**

### 3.5 "按 y 归一化 box" 有没有人做？

**有，但不是为了修 IoU，而是为了修"尺寸阈值"和"速度换算"**：
- AXIS：`Calibrate perspective` → 把物体尺寸判据从"画面百分比"变成"厘米"（§3.3）。
- Frigate：`create_ground_plane` → 把像素速度变成真实速度（§3.2）。
- Ultralytics：`speed_estimation.py:57-58, 108` 用**单一标量** `meter_per_pixel`（`config.py` 默认 `meter_per_pixel`，docstring："Real-world meters represented by one pixel for scene scale conversion"）—— **全图一个常数，完全不考虑透视**。源码：
  ```python
  self.max_hist = self.CFG["max_hist"]  # Required frame history before computing speed
  self.meter_per_pixel = self.CFG["meter_per_pixel"]  # Scene scale, depends on camera details
  ...
  meters = pixel_distance * self.meter_per_pixel  # Convert to meters
  ```

> **对你的项目的实际建议**：如果你的实际症状是"远处小人 box 小、近处大人 box 大，IoU 关联失败"，**先不要上 IPM**。ByteTrack 用的是 **Kalman 预测框 vs 检测框的 IoU**，两点同帧尺度是自洽的 —— 尺度差异本身不直接破坏 IoU，真正破坏 IoU 的是**帧间位移相对 box 尺寸过大**（见 §5）。先按 §5 调 FPS / buffer / match_thresh，若仍不行，再考虑 Frigate 式的 `y → 尺度` 修正来**自适应放大远端的关联搜索半径**。这是一个**假设，不是已证结论**，我明确标记为**推测**。

def store_tracking_history(self, track_id: int, box) -> None:
    """Store the tracking history of an object.

    This method updates the tracking history for a given object by appending the center point of its bounding box to

### 4.3 死区？—— **没有帧数死区**，只有 `counted_ids` 永久闩锁

- `object_counter.py:77`：`track_id in self.counted_ids` → 已计数的 ID 直接跳过。
- `object_counter.py:98`：越线后 `self.counted_ids.add(track_id)`。

- `line_width`（默认见 `config.py`）只用于绘图和 `self.margin = self.line_width * 2`（`object_counter.py:52`），**不是几何死区**。

> **重要**：`counted_ids` 是**永久**的（在该 track 存活期内），因此"同一 ID 在线上来回抖动"**不会**重复计数。风险来自 **ID 切换**（§5）与 **track 被回收后重开同一个 ID**。上游在 `object_counter.py:123-130` 加了 `forget_tracks` 钩子来防止 `counted_ids` 在 24/7 流中无界增长：
> ```python

>     """Drop retired IDs from `counted_ids` so it doesn't grow across a 24/7 stream (see BaseSolution)."""
>     super().forget_tracks(track_ids)
>     self.counted_ids.difference_update(track_ids)
> ```
> ⚠️ **这是一个真实的漂移风险点**：ID 被回收后再复用 → `counted_ids` 已移除 → 同一个真人可能被**二次计数**。对你的"净计数不能漂移"目标，这是需要显式处理的地方。

## 5. "走快丢 ID"：帧率 / 关联失败的证据与修法

### 5.1 ByteTrack 原论文的硬数字

Zhang et al., *ByteTrack: Multi-Object Tracking by Associating Every Detection Box*, ECCV 2022。
HTML 全文：<https://arxiv.org/html/2110.06864v3>（2026-10-16 抓取）

**运动线索在低帧率下失效（原文）：**
> "On BDD100K, Re-ID achieves much better results than IoU in the first association. This is because BDD100K contains **large camera motion and the annotations are in low frame rate, which causes failure of motion cues**."

**关键数字（原文表格）：**
> "For the lost tracklets, we **keep it for 30 frames** in case it appears again."
> "In the linear assignment step, **if the IoU between the detection box and the tracklet box is smaller than 0.2, the matching will be rejected**."
> "For BYTE, the **default detection score threshold is 0.6**"（注意：不是 0.25 —— Ultralytics 用了更低的 0.25）

**Ablation：IoU 前向关联在低帧率下的 ID 代价（原文表）：**
| Similarity#1 | Similarity#2 | MOTA | IDF1 | IDs (MOT17) | mMOTA | mIDF1 | IDs (BDD100K) |
|---|---|---|---|---|---|---|---|
| IoU | Re-ID | 75.8 | 77.5 | 231 | 39.2 | 48.3 | **29172** |
| IoU | IoU | 76.6 | 79.3 | 159 | 39.4 | 48.9 | **27902** |
| Re-ID | Re-ID | 75.2 | 78.7 | 276 | 45.0 | 53.4 | **10425** |
| **Re-ID** | IoU | 76.3 | **80.5** | 216 | **45.5** | **54.8** | **9140** |

> **解读**：在低帧率数据集 BDD100K 上，把前向关联从 **IoU 换成 Re-ID**，ID 切换从 **27902 → 9140（降 67%）**，IDF1 从 48.9 → 54.8。**这是"低帧率 → 运动线索失效 → 应改用外观线索"的直接量化证据。**
> 但注意代价：Re-ID 版本 FPS 从 29.6 掉到 **11.8**。RK3588 NPU 上要谨慎。

### 5.2 APPTracker（ACM MM 2022）—— 专论低帧率 MOT

Zhou et al., *APPTracker: Improving Tracking Multiple Objects in Low-Frame-Rate Videos*, MM'22。
PDF：<https://infzhou.github.io/folder/Zhou_APPTracker_Improving_Tracking_Multiple_Objects_in_Low-Frame-Rate_Videos_MM_2022.pdf>（2026-10-16 抓取全文）

**核心机制陈述（原文）：**
> "Tracking with a low frame rate poses particular challenges in the association stage as **objects in two successive frames typically exhibit much quicker variations in locations, velocities, appearances, and visibilities** than those in normal frame rates."
> "First, **the displacement of objects between frames becomes larger; in some cases, two detections of the same target in two consecutive frames even have no overlap.** Methods that assume objects moving slightly between frames thus fail in low-frame-rate cases."
> "Besides, the larger displacement leads to the **failure of motion models (like the Kalman filter) with zero-velocity initialization assumptions**."
> "Second, the appearances and visibilities of objects change more abruptly. In high frame rate videos, objects are occluded gradually. While in low-frame-rate videos, **one highly visible object in the previous frame may be occluded in the current frame**."

**ByteTrack 在低帧率下的量化退化（原文表，MOT17 val，`n_d` = 帧采样间隔）：**
| Method | n_d=1 IDF1 | n_d=10 IDF1 | n_d=30 IDF1 | n_d=1 IDs | n_d=10 IDs | n_d=30 IDs |
|---|---|---|---|---|---|---|
| **ByteTrack\*** | **73.0** | **61.5** | **54.9** | 262 | 5282 | 8502 |
| FairMOT | 72.8 | 66.5 | 55.1 | 298 | 2436 | 4274 |
| CenterTrack | 69.4 | 67.4 | 62.9 | 347 | 1941 | 4205 |
| Ours (APPTracker) | 68.7 | **70.3** | **66.2** | 326 | 1686 | 3890 |

> **ByteTrack 的 IDF1 从 73.0（正常帧率）掉到 54.9（1/30 帧率），ID 切换从 262 暴增到 8502（×32）。** 这就是"走快丢 ID"的量化上界证据。
> 论文对 ByteTrack 的评语原文："Though its performance in normal-frame-rate cases is good, **it drops more quickly than other methods since no other information (e.g., appearance embeddings, optical flows) except motion cues is leveraged in the association.**"

**buffer size 与帧率的关系（原文附录 B，Table 5）：**
> "A proper **buffer size**, above which an inactive tracklet is terminated, is required for preserving the identities of objects involved in occlusions."
> "Sampling interval n_d: **1 → 30, 2 → 15, 3 → 10, 6 → 10, 10 → 10, 15 → 6, 30 → 3**"

> **这是最实用的一张表**：buffer 的**帧数**要随帧率降低而**减小**，因为 buffer 的真实含义是"丢失后容忍的**时间**"，而 `track_buffer` 是按**帧**计的。
> **反向推论（对你的项目）**：如果你把相机 FPS 从 15 提到 30，而 `track_buffer` 仍是 30，则容忍时间从 2s 变成 1s —— **必须同步把 `track_buffer` 加倍**，否则 ID 保持能力反而下降。

**Kalman 在低帧率失效的机理（原文）：**
> "Without a good initial velocity estimation (the velocity of an object is usually initialized to zero) or a good velocity measurement, **the Kalman filter fails to chase objects in low-frame-rate cases**."
> "in normal-frame-rate cases, the motion information contains a large portion of noise caused by the jitter of detections. Kalman filter can filter out such measurement noise... However, the influence of such noise is reduced as the displacements of objects become larger in low-frame-rate videos."

## 7. 对你项目的具体建议（含证据强度标注）

**证据强、建议直接采纳：**
1. **锚点改用脚点 `(xc, y2)`**，不要用 box center。三方独立一致（NVIDIA 官方文档明文、AXIS 官方文档明文、Frigate 源码）。斜视走廊尤其重要：box center 会随人体在画面中的**高度投影**上下浮动，而脚点始终贴地、受"人走近/走远导致的 box 高度变化"影响最小。**这是本次调研最强的结论。**
2. **加 N-of-M 帧确认**：Frigate `inertia: 3` 是经过验证的默认值。对越线，等价做法是"连续 3 帧都在线的同一侧才确认状态翻转"。
3. **用"上一帧→当前帧线段与计数线求交"**判定越线（Ultralytics `LineString` 做法 / Savant `Segment` 做法），而不是判定"点在线的哪一侧"。前者天然处理"一帧跨过整条线"，**且不会被线上的抖动反复触发**（因为抖动产生的微小线段与线相交后，`counted_ids`/状态机会吸收掉）。
4. **用 `counted_ids` 式的 per-track 闩锁**防同一 ID 重复计数，但**必须**处理 ID 回收后 `counted_ids` 被清除导致的二次计数（Ultralytics `forget_tracks` 的副作用）。
5. **把计数线画在"人不会停留"的位置**（AXIS 明文建议："objects are unlikely to be waiting at the line"）。例如门口内侧 30–50cm，而不是门槛正上方。这是**零成本、收益最大**的一条。
6. **`track_buffer` 必须随 FPS 换算**：其语义是"丢失后容忍多少帧"。若 FPS 从 15 → 30，`track_buffer` 应从 30 → 60，否则容忍时间减半（APPTracker Table 5 的逆向应用）。

**证据中强、建议评估：**
7. **净计数漂移的兜底**：FootfallCam 明文承认 "No people counter is 100% accurate. It would have accumulative errors as the day goes on"，并用 error correction + occupancy 过期 兜底。建议你的 `occupancy` 至少**永不为负**、并有**最大停留时长过期**。这是产品级成熟做法。
8. **提高 FPS 是"走快丢 ID"的第一修法**，但收益递减且有上限：ByteTrack IDF1 在 1/10 帧率已掉到 61.5。若无法提 FPS，**优先加大 `track_buffer`、放宽 `match_thresh`（越大越宽松）**，其次考虑 BoT-SORT/OC-SORT 的观测中心化修正（OC-SORT 的 ORU 正是为"速度漂移"设计）。
9. **不要**上 IPM-before-tracking。五家实现零采用；学术上的 IPM 用法都是多相机/密集人群/车辆，与你的场景 gap 大。若要应对远近尺度差，参考 Frigate `create_ground_plane` 式的 **`y → 尺度` 标定**，用它自适应调整远端的关联搜索半径。**此条为推测，需实测验证。**

**证据不足、明确标记：**
10. Xovis 的锚点/算法**未找到一手披露**；Sensmax 页面抓取失败。**不要引用这两家作为证据。**
11. 我没有找到任何论文或实现主张"斜视单人越线必须用 IPM"。这是"未找到"而非"已证明不存在"——**证据强度：中强（反面证据充分）**。
