# 房间人数统计：真实工程实践与替代路线

> 调研问题：走廊广角摄像头 + 每扇门一条判定线 + 跨线计数，用来推「每间客房当前有几个人」。
> 痛点：人走快一点就丢 ID → 漏计。**累积量只增不减，漏一次就永远少一个人。**
> 核心待答：**「重做一个更好的 tracker」是不是解决漏计的最优解？**

结论先写在最前面：**不是。** 见文末《落到我们场景的结论》。

---

## 一、开源监控栈是怎么数人的

### 1.1 Frigate：用 tracker，但**不用**它来数人

Frigate 是这一领域最主流、最活跃的开源 NVR。**它有一等的 tracker，却把「人在不在区域里」这件事完全绕开了 tracker。**

源码位置 `/tmp/agents/research/frigate`（HEAD `62ca5b2`，2026-10-15）：

**（a）区域在场判定 = 底部中心点落在多边形内，与 tracker 无关**

`frigate/track/tracked_object.py:187-206`：

```python
# check zones
current_zones = []
bottom_center = (obj_data["centroid"][0], obj_data["box"][3])
...
if cv2.pointPolygonTest(contour, bottom_center, False) >= 0:
```

官方文档 [Zones](https://docs.frigate.video/configuration/zones/) 原文：

> Presence in a zone is evaluated based on the bottom center of the bounding box for the object. **It does not matter how much of the bounding box overlaps with the zone.**

注意：**这不是跨线计数**。它不需要「上一次在哪一侧」，因此**不需要 ID 连续**。
一个人丢 ID 再拿到新 ID，只要他还在区域里，占用数就是对的。这是 Frigate 面对我们的痛点时
天然免疫的地方——**它压根没用累积量**。

**（b）区域抖动靠 `inertia` 去抖，不是靠 tracker 稳定性**

> Zone inertia helps guard against this by requiring an object's bounding box to be within the zone for multiple consecutive frames.

```yaml
zones:
  front_yard:
    inertia: 3      # 连续 3 帧才算进入
```

**（c）它确实有 tracker，而且很认真——但对我们的问题帮助有限**

Frigate 用的是 **Norfair**（`frigate/track/norfair_tracker.py`），带 **Kalman 滤波 + 自定义距离函数 + 直方图 re-ID**：

```python
from norfair.filter import OptimizedKalmanFilterFactory
...
self.default_tracker_config = {
    # R is the multiplier for the sensor measurement noise matrix, default of 4.0
    # lowering R means that we trust the position of the bounding boxes more
    # testing shows that the prediction was being relied on a bit too much
    "filter_factory": OptimizedKalmanFilterFactory(R=3.4),
    "distance_function": frigate_distance,
    "distance_threshold": 2.5,
}
```

它的距离函数不只看位置，还看**宽高比变化**（`norfair_tracker.py:36-70`）：

```python
# change in x relative to w
distance[0] /= estimate_dim[0]
# change in y relative to h
distance[1] /= estimate_dim[1]
# get ratio of widths and heights
width_ratio = widths[1] / widths[0] - 1.0
height_ratio = heights[1] / heights[0] - 1.0
change = np.append(distance, np.array([width_ratio, height_ratio]))
return float(np.linalg.norm(change))
```

并且对人（PTZ 场景）开了 **re-ID（颜色直方图）**：

```python
"person": {
    "filter_factory": OptimizedKalmanFilterFactory(R=4.5, Q=0.25),
    "distance_threshold": 2,
    "past_detections_length": 5,
    "reid_distance_function": histogram_distance,
    "reid_distance_threshold": 0.5,
}
```

**（d）关键数字：Frigate 的 `max_disappeared` 默认是 `fps × 5`**

`frigate/config/config.py:1211-1219`：

```python
# Default min_initialized configuration
min_initialized = max(int(camera_config.detect.fps / 2), 2)
...
# Default max_disappeared configuration
max_disappeared = camera_config.detect.fps * 5
```

Frigate 推荐 `detect.fps = 5`（`config.py:1201` 明确警告 fps>10 会掉性能）。
**所以业界默认值是「允许一个人消失 25 帧 = 5 秒」才注销轨迹。**
而我们的 `max_age=10`（帧）。如果我们是 15~25fps 跑，我们的容忍时间只有 0.4~0.7 秒。

**（e）`min_score` 官方明确说会「confuse the tracker」，且是权衡**

`docs/docs/configuration/object_filters.md:35` 原文：

> If `min_score` is too low then false positives may be detected and tracked which can **confuse the object tracker** and may lead to wasted resources. If `min_score` is too high then lower scoring true positives like objects that are **further away or partially occluded** may be thrown out which can also confuse the tracker and cause **valid tracked objects to be lost or disjointed**.

我们 `conf=0.15` 属于**极低**。按 Frigate 的说法，这是「宁可放进来一堆假框去 confuse tracker」的那一侧。
注意我们的场景正是「远处 + 遮挡」——这一侧的矛盾是**双向**的，调 conf 不能同时解决。

**（f）Frigate 的 track 生命周期默认值汇总**

| 参数 | Frigate 默认 | 我们 |
|---|---|---|
| `min_initialized`（最小命中才确认） | `max(fps/2, 2)` ≈ 2~3 | `min_hits=2` |
| `max_disappeared`（丢帧容忍） | `fps × 5` ≈ **25 帧 / 5 秒** | `max_age=10` |
| 匹配依据 | Kalman 预测 + 位置/尺寸比距离 | 贪心 IoU ≥ 0.3，无预测 |
| re-ID | 有（直方图，person 可选） | 无 |

### 1.2 关于「更早的 Frigate 用 IoU 匹配」

Frigate 0.13 换到 Norfair 时的官方发布说明（[discussion #8366](https://github.com/blakeblackshear/frigate/discussions/8366)）：

> **New Object Tracker** — Frigate now uses Norfair for object tracking, this means that object attributes like size, width/height ratio, and position are used to intelligently track objects. **ID swapping between tracked objects is greatly reduced** in situations where a car in the driveway was confused with a car passing in the street.

同一线程里，Frigate 维护者 `NickM-27` 面对一个「车互相遮挡导致轨迹混乱」的案例，直接承认：

> the car drove by **occluding** the other car and the tracker became confused about which car was which. The new tracker is much smarter but **cases where one object occludes another is very challenging.** There are ways this can be improved in future versions of frigate

**这是整个调研里最重要的一句之一：把 tracker 从 IoU 升级到 Kalman+Norfair 之后，遮挡仍然是「very challenging」。**
换更好的 tracker，收益是「greatly reduced」，不是「解决」。

### 1.3 supervision（Roboflow）：ByteTrack + LineZone，且**明确不信任单帧翻转**

`/tmp/agents/research/supervision`（HEAD `6ecb279`）。它的 `LineZone` 是跨线计数的工业级参考实现。
`src/supervision/detection/line_zone.py:177+` 的核心逻辑，注意 `minimum_crossing_threshold`：

```
Detection needs to be seen on the other side of the line for this many consecutive
observations to be considered as having crossed the line. Only frames that place the
detection on one side of the line count: a frame in which it is temporarily missing,
falls outside the line's limits, or straddles the line is skipped, and neither extends
the run nor resets it. ... Excursions shorter than this are treated as noise
```

实现（`line_zone.py:290-315`）：

```python
sustained_run = islice(crossing_history, 1, None)
if any(state != tracker_state for state in sustained_run):
    continue
```

它还有两个我们完全没有的机制：

1. **未确认轨迹不计数**：`unconfirmed = detections.tracker_id < 0` → `continue`。即「还没被跟踪器确认的轨迹一律不数」。
2. **越过线的位置限制**：`_calculate_region_of_interest_limits` —— 只统计在线的线段范围内的穿越，避免远处越界误计。

我们的 `counter.py` 是**单帧符号翻转即计数**（`old * side < 0` 立刻 `in_count += 1`），
只有 2% 画面高的死区。这正是 supervision 文档里说的 "noise" 那一类。

### 1.4 Ultralytics solutions：区域计数 vs 跨线计数

[Object Counting](https://docs.ultralytics.com/guides/object-counting/) 用 `ObjectCounter`，`tracker` 默认 `tracktrack.yaml`（可选 `bytetrack.yaml`/`botsort.yaml` 等），**必须靠 tracker**。

[Region Counting](https://docs.ultralytics.com/guides/region-counting/) 用 `RegionCounter`，官方原文：

> The RegionCounter solution tracks objects across video frames and, on every frame, **counts the objects whose bounding-box center falls inside each region** you define. ... **Because counts restart every frame, the number shown on a region is its current occupancy** ... not a running total. To count objects crossing a boundary cumulatively, use the ObjectCounter solution instead.

**这就是我们需要的那条路线的官方说法**：区域占用是「每帧重算」，天然**不会漂移**；
跨线计数是「累积量」。Ultralytics 把两者并列成两个不同 solution，各有各的用途。

### 1.5 NVIDIA DeepStream

有 `Gst-nvtracker`（NvDCF / NvSORT / NvDeepSORT 等），ReID 用于遮挡后重关联（[RidgeRun 文档](https://developer.ridgerun.com/wiki/index.php/ReID_and_Target_Reassociation_using_NVIDIA_Deepstream)）。
但 NVIDIA 论坛有两个一线信号：

- [NVDCF Tracking Parameters Detailed Info](https://forums.developer.nvidia.com/t/nvdcf-tracking-parameters-detailed-info/157064)：用户报告 "peoples tracker ID's change fairly frequently as they get partially obscured by other people in the queue"。
- [Accuracy Discrepancy between NvDCF Tracker and Non-tracker output](https://forums.developer.nvidia.com/t/accuracy-discrepancy-between-nvdcf-tracker-and-non-tracker-output/374418)：用户报告**加了 tracker 反而比不加 tracker 精度更低、更不一致**。

第二条尤其值得注意：**tracker 本身会引入误差**，不是纯增益。

### 1.6 Home Assistant 的人在场判定

HA 生态里，**房间级在场的主流做法根本不是摄像头**，是 BLE（ESPresense / Room Assistant）、mmWave 雷达（Aqara FP2、Apollo MSR-2）、PIR 这几类。
摄像头（Frigate）在 HA 里主要做的是**单房间的二值 occupancy**（有人在/没人），不是「有几个人」。

Frigate 的 HA 集成里，occupancy 传感器有一个官方 FAQ 承认它比较毛躁，维护者 `hawkeye217` 在
[discussion #16697](https://github.com/blakeblackshear/frigate/discussions/16697) 解释：

> The Home Assistant sensors have **fewer filters in place** and do not go through the process of checking if detected objects are false positives or not. ... We've decided to leave the sensors **unfiltered** ... (since many use them for turning on lights or switches)

即：**HA 场景人家要的是「快」，不是「准」**——因为「开灯」这个业务对误差不敏感（多开一次灯无所谓）。
**我们的业务是「人走断电 / 人来上电」，且要数人数——我们对误差的敏感度和 HA 完全不是一个量级。**
拿 HA 的成熟度来推断「我们照做就行」是错位的。

### 1.7 关键反面证据：Frigate **故意不做跨线计数**，而且社区最后都退回了「区域」

这是本调研里对我们决策最直接的一条。Issue [#93 "Can frigate detect object line crossings?"](https://github.com/blakeblackshear/frigate/issues/93)
**2020-01-15 提出，到 2026 年仍然是 OPEN**，35 条评论，横跨 6 年。

作者/维护者 Blake Blackshear 在开帖当天的回复：

> 0.4.0 introduced the ability to track objects, which makes it possible to implement this type of use case **in a future release**. **At the moment, there isn't a way to accomplish this with 0.4.0.**

**6 年过去，Frigate 有了 Kalman tracker、re-ID、区域惯性、速度估计、目标生命周期路径绘制——
唯独没做跨线计数。** 这不是疏忽：Frigate 的核心抽象是 **zone（区域）**，不是 **line（线）**。

**更关键的是社区最终给出的替代方案（2024-02，维护者 NickM-27 亲自回答）：**

> [用户] Line Crossing with Direction of travel would be amazing. ...
> [用户追问] How do I define order of zones entered?
> **[@NickM-27] the `entered_zones` field contains the order that the object entered the zones**
> [@FigJam23] You can also just add **two zones**, and run an automation that checks **what zone triggered first**

以及维护者写的官方指南：<https://github.com/blakeblackshear/frigate/discussions/2898>

**即：连 Frigate 社区想要「方向性」时，官方推荐的实现方式是「两个区域 + 进入顺序」——
用区域序列来推方向，而不是画一条线。**

**还有一条 2026 年的现场报告，和我们的症状一模一样**（同帖 @Rudder2, 2026-01-18）：

> Frigate is constantly saying my red truck and my wife's silver car, **which is 3/4 covered by a tree** parked next to the truck, **are the same vehicle** and moves sideways back and forth ...
> [维护者 @NickM-27 回复] ... **bounding boxes can change in various ways** while the object is moving in the expected direction. What you're suggesting would mean specifically overriding the boxes the detector returns ... which would not be consistent or generalizable.

**注意最后那句：这不是配置问题，是 bbox 的固有不稳定性，维护者明确拒绝为此加特例。**
这正是「遮挡 → 框变化 → ID 混淆」在 2026 年仍未解决的一手证据。

**最后一条特别值得记下来的现场细节**（@noelhibbard, 2024-02-29），有人试图把 Frigate 的 MQTT 坐标拿出来自己画轨迹：

> I just did a proof of concept where I made a little web service that forwards the relevant MQTT events over a websocket to a web page ... and when watching the live video feed vs my little webpage, **the events are too delayed and too few to be all that useful**

**「事件太少」= 有效帧率不足。** 这正是第五节里排第 5 位的误差源（帧率/吞吐），
而且**在外挂式方案里会更严重**——因为多了一层 MQTT/网络传递。

## 二、商用客流统计产品的技术路线（含硬指标）

### 2.1 Axis：**拒绝给精度数字**，并把「斜视」列为风险因素

Axis 官方白皮书 [Axis counting solutions](https://whitepapers.axis.com/en-us/axis-counting-solutions)（2025-06）是全调研里**最诚实**的一份官方文档。

**（a）它明确训斥「精度百分比」这种说法：**

> The accuracy of counting analytics is a complex matter that **neither can nor should be reduced to a general accuracy percentage**. Every installation is different ...
> At Axis, **we don't provide an overall accuracy number**. Such a number would be correct only in a laboratory test setup ...

**（b）它直接说斜视视角会增加遮挡风险——正好命中我们的装法：**

> **Angled views can increase the risk of occlusion**, so objects are partially or completely hidden from view, leading to **missed detections or inaccurate counts.** In contrast, a **top-down mount** focuses on the head and shoulders for detection, **reducing the likelihood of obstruction and improving accuracy.**

**（c）跨线计数它给的前置条件是「人过线前后都要完整可见」：**

> Crossline counting tracks objects crossing a virtual line ... The objects should be **fully visible to the camera both before and after crossing the line.**

**（d）对占用它建议「把区域划在遮挡风险最小的地方」：**

> Occupancy in area: For optimal results, we recommend defining an area of interest to estimate occupancy in **where the risk of occlusion is minimized.**

**（e）精度自测方法（可以直接抄来做验收）：**

> start by measuring accuracy for people going in only. Make a note of the total count on the counting unit and **immediately start counting people manually until reaching 200 people going in** ... The error percentage is given by the formula (#IN - 200)/2.
> Another method is to compare IN minus OUT for a period ... (IN-OUT)/(IN+OUT)x200
> However, it should be noted that **manual counting is far from 100% accurate**, especially in crowded scenarios

### 2.2 Axis People Counter：**承认累积误差，并为此专门做了一个「smart occupancy」模式**

[AXIS People Counter 技术文档](https://help.axis.com/en-us/axis-people-counter) 是本调研**第二重要的证据**。
它把 occupancy 明确分成两种模式：

> **Smart occupancy mode** — The application analyses frequency of passages and in turn calculates an average visiting time, which is then used to **filter away counting errors that accumulate throughout the day** ... as well as a **corrected full day analysis** at the end of the day.
>
> **Naive occupancy mode** — If you select the naive occupancy mode, the application estimates the occupancy by counting "people coming in" minus "people coming out". This estimation is not as sophisticated ... and **the occupancy error accumulates over time.** The error will be larger if there is a high flow of people and if the counter is poorly configured.

**换句话说：连 Axis 都认为「进-出」这个朴素累积法会累积误差，需要专门的纠偏算法。**
而且它给 `naive` 模式配的兜底动作是：

> If you select naive occupancy mode, we recommend that you **schedule a reset of the counter.**

它的验收标准也很实在：

> If the difference between number of persons going in and out is **<5%** it's a good first indication that the system is configured correctly. ...
> Under normal circumstances, the total accuracy percentage should be **95% or higher**.
> **The software doesn't count correctly** → Make sure people pass the entire counting zone, crossing both blue lines. **They should not turn left or right before they have passed both lines.**

以及一个非常好用的诊断项：

> The software prompts me with a warning saying that **the frame rate is too low** → Make sure the scene has sufficient lighting. If the scene is too dark, the camera does not deliver enough frames per second for the application to work.

**注意 Axis 的 95% 是「双向各自对齐」的验收标准，而且 5%/天 的 IN-OUT 失配在累积口径下就是灾难**（见 2.5）。

### 2.3 Hikvision：推荐高度 < 4.0m，且主推**双镜头/俯视**

Hikvision 客流相机安装指南（官网 PDF，本文档抓取时被 CDN 拦截，仅引搜索到的官方摘要）：

> The counting width depends on the installation height. **The recommended installation height for dual-lens camera is less than 4.0m (13.1ft).**

重点在于：**Hikvision 的客流产品线是「双镜头 + 俯视」，不是「单目斜视」。**
它们做人数统计靠的是**多一维深度**，不是靠更聪明的 tracker。这和 Xovis 是同一条技术路线。

另外需要警惕的一条：商用客流统计的「精度」**默认前提是俯视**。
[Retail Sensing 对比](https://retailsensing.com/video-analytics/best-people-counting-system/) 里对 2D 视频计数的要求写得很直白：

> **Requires camera positioning at suitable height and angle**

### 2.4 Milesight：靠 ToF 拿 99.8%，但**营销材料不给失败条件**

[Milesight VS133 AI ToF People Counting Sensor 白皮书](https://resource.milesight.com/milesight/iot/document/milesight-vs133-ai-tof-people-counting-sensor-whitepaper.pdf)（PDF 17 页，纯图片版，已渲染逐页读取）。

它宣称 **99.8% 精度 + 100% 匿名**，靠的是 **2nd Generation ToF**（ToF 出深度信息，不采集图像）。
**但整份白皮书没有一句安装约束、没有失效场景、没有给出 99.8% 的测试前提。**
——这本身就是一条证据：**越是营销材料，越不写失败条件。**

有意思的是同一份白皮书里，它**自曝了另外两条路线的短处**（第 10 页）：

> **Radar** ... it can be easily influenced by the multipath effect. When detecting objects **still or close**, the accuracy of results decreases on account that it **cannot well detect static objects and near objects** respectively.
>
> **Thermal Imaging** ... But **sunlight will be a trouble** for its performance since it works by the principle of temperature. Thermal energy can be reflected by shiny surfaces and **can't get through solid obstacles or even just a group of people**, which will all influence the detection accuracy and results.

### 2.5 Xovis：3D 立体视觉，~99%，但**价格量级完全不同**

[Xovis 传感器页](https://www.xovis.com/technology/sensor)：

> Xovis' sensor technology permits **accurate people counting of up to 99%**. Market-proven for over a decade.

Xovis 用的是 **3D 立体视觉（双目）**，且明确是针对「most crowded and complex indoor and outdoor environments」。

### 2.6 商用路线的技术全景表（**带硬价格**）

来自 [SMS Storetraffic《People counting technologies compared》](https://storetraffic.com/people-counting-technologies/)（2026-09，作者是装了 20 年这类设备的集成商，**自己卖其中两种并主动声明**）。

| 技术 | 检测什么 | 典型精度 | 并排走 | 方向 | 安装 | 硬件成本 |
|---|---|---|---|---|---|---|
| **无线红外对射** | 光束被打断 | **95–98%，单列成人** | **不能——两个人并排算 1** | 是（双光束） | 门框墙面，**54in(137cm)** 只数成人 / 24in 数所有人 | **$100–$500** |
| 顶装热成像阵列 | 热形状 | 85–95% | 可以，直到形状粘连 | 是 | 门框顶，≤3.6m | $300–$800 |
| 2D 单目视频 | 镜头 + AI 检测 | 旧式 80–95%；AI 宣称 95–98% | AI 后改善 | 是 | **天花板俯视** | $200–$700 |
| **3D 立体视觉** | 双镜头算高度图 | **95–99%**，部分厂商保底 | **可以** | 是，多线 | 天花板 2.2–6m | **$300–$1,200**（多数 $650–$1,200） |
| **ToF / LiDAR** | 红外脉冲深度图 | 95–99% | 可以 | 是 | 天花板 2.5–5m | $500–$1,200 |
| WiFi/蓝牙嗅探 | 手机等设备 | **数的是设备不是人** | — | 否 | 任意 | $100–$500 + 平台 |
| 压力垫/闸机/门摆计数器 | 重量/闸杆/门开合 | 闸机 ~100%/次；垫子和门计数器低 | 否 | 闸机可以 | 地面/闸口/门 | 跨度大 |

**对我们场景最相关的三件事：**

**（1）红外对射明确「两人并排 = 1 个计数」**，而且它**只适合单个/双开门**：

> **Two abreast is one count.** On a standard single or double door this rarely bites: people open one door and come through one at a time ... On a wide and very busy entrance it does.
> **Verdict:** for single and double doors that open outward, a beam is the simplest and cheapest counter to run and to check.

**（2）红外对射的实测精度区间比宣传低**（[Retail Sensing](https://retailsensing.com/video-analytics/best-people-counting-system/)）：

> Infra-Red Beam Systems — Accuracy: **85-95%** ... Claimed accuracy of 95% is achievable in **narrow, low-traffic doorways**; real-world accuracy in busy retail is **frequently 85-90%**.

**（3）「复用现有监控摄像头」这件事，商用视角是明确负面的：**

> A security camera is mounted **at an angle to see faces, which is the wrong geometry for separating people who overlap.** It is also doing another job ... every stage another thing that can fail or fall behind.
> **Looking straight down.** Separating people needs a top-down view; a camera mounted at an angle to see faces, **the way a security camera is, is the wrong geometry.**

## 三、累积型在场人数怎么纠偏（我们的核心难题）

我们真正的业务是「房间内当前人数」，这是**累积量**。这一节是本调研最有价值的部分。

### 3.1 Density（商用 occupancy 平台）专文：《Understanding Drift in Entry-Based Occupancy Counting》

这是**决定性证据**。原文：<https://support.density.io/hc/en-us/articles/47782967345563-Understanding-Drift-in-Entry-Based-Occupancy-Counting>

> Occupancy derived from Density's Entry sensors is calculated as: **Previous occupancy + entrances − exits** ...
> Entry sensors are 100% anonymous and **highly accurate**, but like any **event-based system**, they do not capture 100% of doorway crossings. When recorded entrances and exits are not perfectly balanced, **a cumulative offset can develop** in the reported occupancy. We refer to this cumulative offset as **drift**.

它列的丢事件原因（**几乎逐条命中我们的场景**）：

> * A sensor not installed according to recommendation
> * **People entering or exiting side-by-side or in groups**
> * **People lingering beneath the threshold**
> * Objects or equipment moving through the threshold
> * Space configuration changes
> * Sensor health issues

**它给的量化例子（这段值得完整抄下来）：**

> Between 11:00 am and 2:00 pm, the cafeteria records 250 entrances and 250 exits — 500 total doorway events. Of those 500 events, **25 exits go unrecorded** before 1:45 pm.
> 25 unrecorded exits ÷ 500 total doorway events = **5% drift**
> Because traffic moves in and out quickly, the cafeteria is **fully empty by 1:45 pm**. The system, however, **still counts 25 people as present** ...
> When 25 new visitors enter between 1:45 and 2:00 pm, the running total includes: 25 actual occupants + 25 carried over = **50 reported occupants**
> Actual occupancy at 2:00 pm: **25**. Reported occupancy at 2:00 pm: **50** (**100% more than actual occupancy**)

> **This does not mean the system is inaccurate.** It illustrates how **drift affecting just 5% of doorway events can accumulate in a running total, producing a much larger difference in reported occupancy at a given point in time.**

**这就是我们的痛点的严格数学表述**：跨线计数单项误差 5%，在累积口径下可以变成 100% 的人数误差。
再叠加一条它给的规律：

> Counts are typically closest to actual **earlier in the day**. Differences, if present, are **more noticeable later in the day**. **This pattern is expected behavior in entry-based occupancy systems.**

### 3.2 Density 的兜底手段：**每日重置**

> That difference remains in the total **until the system resets overnight**. The system **does not recount the space during the day** ...
> **Reset times are selected during implementation and automatically set the next day's count to 0.** The reset time should be set to **when everyone has left the space**, including night staff and cleaning crews.

它的缓解清单：

> * Ensure optimal sensor placement and doorway coverage
> * Minimize interference near doorways
> * **Cover all doorways**, including doorways meant only for staff
> * Use a wired Ethernet connection rather than wifi

### 3.3 Axis 的兜底：「smart occupancy」用平均停留时间滤掉累积误差

见 2.2。核心思想：**用停留时间分布反推合理在场人数**，把「进-出」的漂移滤掉。
它甚至对不适合的场景（图书馆、影院、咖啡店——人流低且停留时间变化大）**建议退回 naive 模式 + 定时重置**。

**这告诉我们：连 Axis 都认为「smart」不是万能的，低流量 + 停留时间方差大的场景就是退化成 naive + reset。**
**民宿客房恰好就是「低流量 + 停留时间方差极大（有人住 1 小时有人住 8 小时）」的那一类。**

### 3.4 学术/工程界的门磁纠偏：PIR + 门磁把精度从 91.5% 拉到 99.8%

[Arqaios《Hotel room occupancy detection compared》](https://arqaios.com/blog/hotel-room-occupancy-detection-compared)（2026-09，作者是卖 mmWave 方案的，但引用的是同行评审文献）：

> A building-simulation study found that adding a door sensor raised PIR-based occupancy accuracy from **91.5 percent with four PIR sensors to 99.8 percent with one PIR and a door contact** [20].
> [20] Kim S, Moon J, Yoon S. **Occupancy detection accuracy with PIR and door sensors.** Building Simulation 2017.

**这是「便宜方案 > 视觉方案」最硬的一个数字。** 一个 PIR + 一个门磁，99.8%。

### 3.5 同业对「门磁」的评价（同一份文档）

| 方法 | 实际感知什么 | 哪里会错 | 客人操作 | 隐私 |
|---|---|---|---|---|
| 插卡取电 | 卡槽里有没有卡（任何卡） | **任何卡/名片都能让房间"一直有人"**；酒店给两张卡 | 必须插拔卡 | 无 |
| PIR 被动红外 | 视场内移动的红外热变化 | **睡着/不动的客人 = 空房**，空调会关掉 | 无 | 仅动作 |
| **门磁 + 定时** | 门开关事件 + 动传感器 + 超时 | 从"最后一次门事件"推断；**两个人分别离开**、或客人始终没触发传感器的会搞混 | 无 | 仅门事件 |
| mmWave 雷达 | 房间里的人，含静卧者的多普勒微动 | 覆盖是整间房，每个房间都要一个设备 | 无 | 存在/位置/动作，无图像无身份 |

行业标准做法就是「**PIR + 门磁 + 超时**」：

> Honeywell's INNCOM logic, for example, will "only go unoccupied after it has seen the room entry door shut" and no motion for the timeout [17]; Telkonet's EcoContact+ keeps the room in an "occupied" status until a subsequent door event [18]; Salto's Universal ESD combines a "passive motion infrared detector and micro door sensor" with a 60-minute motion window

**关键洞察：酒店行业卖的「occupancy」是二值（有人/没人），不是人数。**
他们绕开「数人数」这件事本身，因为**「人走断电」这个业务根本不需要知道有几个人**。

### 3.6 雷达方案的真实精度（含**厂商自己承认的局限**）

**TI IWR6843 官方参考设计** [TIDEP-01000](https://www.ti.com/lit/ug/tidue71c/tidue71c.pdf)（Rev.D）：

规格：60-64GHz，FOV 120°×40°，最大距离 8.1m，距离分辨率 8.4cm，功耗 2W，定位精度 ±10cm，**人数密度 1 人/m²**。

**它的修订历史里官方承认了性能退化（这段是金矿）：**

> As we add more people to the scene, the **tracker accuracy slowly decreases**, due to complexities introduced in the point cloud when multiple people interact with each other. **The tracker performance is also poor when many people in the room are sitting, as they become static and are no longer detected by the point cloud.**

即：**雷达的人头计数在「多人」和「静止」两个方向上都退化。** 而民宿里客人坐着/躺着正是常态。

**Seeed MR60BHA2 官方 wiki 直接劝退人数统计**（[GitHub 文档原文](https://github.com/Seeed-Studio/wiki-documents/blob/docusaurus-version/sites/en/docs/Sensor/mmWave_radar_sensor/mr60bha2-mmwave-kit/ha_with_mr60bha2.md)）：

> ### 4. Environment Occupant Count
> This function is currently in a **developmental stage and should be considered experimental**. The returned value is a **rough estimation** ...
> Its accuracy is heavily influenced by factors such as the **overlapping of signals from multiple people**, individual postures, and movement patterns.
> Consequently, **this feature is not suitable for applications that depend on precise occupant numbers.**

以及它的静止目标跟踪成功率（同一文档）：

| 距离 | 状态 | 跟踪成功率 |
|---|---|---|
| 0.5–1.5m | 静止 | >96% |
| 1.5–3m | 静止 | >90% |
| 3–5m | 静止 | 下降，偶尔丢目标 |
| 靠近 | 移动 | 到约 **3m** 才稳定跟踪 |

Seeed 官方论坛里，对「用 60GHz 雷达数房间里的人」的答复（[论坛帖](https://forum.seeedstudio.com/t/mmwave-radar-sensor-60-ghz-to-count-numner-of-people-in-room-indoor/280630)）：

> No, AFAIK it is **too specific for sensing breathing and falls**, the best way is to count them **IS as they enter**.
> [另回复者] the SeeedStudio 60 GHz mmWave sensor is more commonly used for presence detection and tracking, **not specifically for counting people**. For accurate people counting, you might want to consider sensors like the TI IWR6843 or the Infineon BGT60TR13C

**价格**：MR60BHA2（含 XIAO ESP32C6 套件）大致 $25–35 量级（Seeed 官方店 / Amazon / AliExpress），
但**它的「人数」字段厂商自己说是 experimental、不适合精确人数**。
MR60FDA2（跌倒检测版）静态在场探测 ~6m，是更合适的「有人在吗」器件。

**mmWave 的定位结论**：**能可靠告诉你「这间房有没有人」，不能可靠告诉你「有几个人」。**

### 3.7 WiFi CSI / 探针

[Retail Sensing](https://retailsensing.com/video-analytics/best-people-counting-system/) 明确否定：

> since iOS 14 (2020) and Android 10+ (2019), devices **randomise their MAC addresses** ... making repeated identification of the same device impossible and **undermining both count accuracy and tracking capabilities** ... **Counting accuracy tends to decrease as the number of people increases.**

[Storetraffic](https://storetraffic.com/people-counting-technologies/)：

> Wi-Fi, Bluetooth and cellular sensing **count devices, not people** ... **Not a counter.**

且还有 GDPR 风险。**直接排除。**

## 四、免跟踪的视觉做法：区域占用 / 脚点 / 姿态

### 4.1 区域占用（人框中心落在多边形内即算在场）

**Frigate（`pointPolygonTest` + `inertia`）、Ultralytics（`RegionCounter`）、supervision（`PolygonZone`）三家都用这个。**
`PolygonZone` 默认锚点是 `Position.BOTTOM_CENTER`（`polygon_zone.py:37`），和 Frigate 一致。

**它在「走廊多个门」场景下比跨线计数**好**，原因是结构性的：**

| | 跨线计数 | 区域占用 |
|---|---|---|
| 依赖 ID 连续？ | **是**（靠 side 翻转，必须认出是同一个人） | **否**（每帧独立判定） |
| 丢 ID 的后果 | **漏计一次，永久偏移** | 丢一帧只影响一帧，下一帧恢复 |
| 主循环内还是循环外？ | 累积量，跑一天就漂 | 每帧重算，**自动归零** |
| 需要「过线前后完整可见」？ | 是（Axis 明说） | 否 |
| 输出语义 | 进/出/净 | **当前人数（正是我们要的）** |

**结论：对我们的场景，区域占用严格优于跨线计数。** 不是「更好一点」，是**在误差传播机制上根本不同**。

### 4.2 姿态关键点（脚点/头部）计数

用姿态估计取脚踝/头部关键点做点计数，比 bbox 中心稳（bbox 在遮挡时抖动大，脚点相对稳定）。
**但**：需要额外的姿态模型（RK3588 上要多跑一个网络，yolo11n-pose），而我们**没有 PyTorch**，
rknnlite 上的 pose 模型要另外导。**投入产出比在我们的约束下不划算**——收益只是「锚点更稳」，
而区域占用已经把「丢 ID」这个主要误差源消掉了。

### 4.3 热力图

只是区域占用的可视化形式，没有新的精度机制。**不解决我们的问题。**

### 4.4 遮挡 / 并排走：业界的官方说法汇总

| 来源 | 原话 |
|---|---|
| Axis 白皮书 | "**Angled views can increase the risk of occlusion** ... leading to missed detections or inaccurate counts." |
| Axis 白皮书 | 跨线计数：人"should be **fully visible** to the camera both before and after crossing the line" |
| Frigate 维护者 | "cases where **one object occludes another is very challenging**" |
| Storetraffic（2D 视频） | "**Overlap from above.** Two people overlapping in the image are separated by **inference**; a depth sensor separates them by **measurement**." |
| Storetraffic（安全摄像头复用） | "A security camera is mounted at an angle to see faces, which is **the wrong geometry** for separating people who overlap." |
| Density | 丢事件原因含 "People entering or exiting **side-by-side or in groups**" |
| Milesight | 热成像"can't get through ... **even just a group of people**" |

**业界共识：斜视 + 并排走 + 遮挡，是 2D 单目视觉的结构性弱点，靠软件（tracker）只能缓解。**
所有宣称 95%+ 的产品，前提都是**俯视 + 深度（双目/ToF）**，不是「斜视 + 单目 + 更好的 tracker」。

## 五、跨线计数的最大误差来源排序

综合上述一手材料，按**对累积口径的影响**排序：

**第 1 位：检测漏检（detector miss）→ 直接丢事件，无法恢复。**
- Frigate 官方（`object_filters.md:35`）：`min_score` **太低**会放入假框拖垮 tracker，**太高**会把"远处或部分遮挡"的真目标丢掉，导致 "valid tracked objects to be lost or disjointed"。
- 我们的 `conf=0.15` 在"太低"这一侧；但我们的漏检主要来自**遮挡 + 远处小目标**（`letterbox 640` 会把走廊远处的人缩得很小）。
- **这是唯一一个"漏了就真没了"的误差源。**

**第 2 位：轨迹 ID 切换 / 轨迹提前注销。**
- 我们的 `max_age=10` 帧 vs Frigate 默认 `fps×5`（≈25 帧 @5fps）。**如果我们是 20fps，我们只容忍 0.5 秒——这就是"人走快一点就丢 ID"的直接原因。**
- supervision `LineZone` 用 `minimum_crossing_threshold` 抗单帧翻转；我们的死区只有 2% 画面高，**单帧符号翻转立刻计数**。

**第 3 位：判定线位置与几何。**
- Axis："The objects should be **fully visible** ... before and after crossing the line"，"placing it ... avoiding the outer parts of the FoV"。
- 斜视走廊里，"线"在图像上对应的真实空间位置随人的身高/远近变化——**同一条线对不同距离的人不等价**（近处线很宽，远处挤成一点）。
- supervision 专门做了 `_calculate_region_of_interest_limits` 来限制越线统计范围。

**第 4 位：遮挡造成的框融合 / 粘连（两人并排被检成一个人）。**
- 这一条**在检测阶段就已经错了，tracker 拿不到证据**。
- Axis/Frigate/Storetraffic 一致认定这是斜视 2D 的结构性弱点。

**第 5 位：帧率 / 推理吞吐。**
- Axis 明确有 "**the frame rate is too low**" 告警，并把它归因于光照不足导致相机掉帧。
- RK3588 单 NPU 上，YOLO11n@640 的推理耗时会直接决定最大处理帧率。**dropped frame = 人移动的位移变大 = IoU 匹配率暴跌**。
- 这就是"人走快一点就丢 ID"的**第二重机制**：不是人快，是**采样间隔大**。
  IoU 匹配假设帧间位移小于框尺寸；位移 ≈ 速度 × 帧间隔，**降帧率等于降低可容忍速度**。

**第 6 位：tracker 本身引入的误差。**
- NVIDIA 论坛: 加 tracker 后精度反而不如不加。
- 即：**换 tracker 不是单调改进**。

> 值得强调：**第 1、4 位在 tracker 的管辖范围之外。**
> 换句话说，**很多误差根本不在 tracker 里，重写 tracker 治不到。**

## 六、落到我们场景的结论

### 6.1 直接回答：重做一个更好的 tracker 是不是最优解？

**不是。** 四条独立理由：

**理由零（最硬的一条）：这个领域最成熟的玩家，6 年都没做跨线计数，而是让人用区域。**

Frigate（3.6 万星，活跃度极高，有 Kalman tracker + re-ID + 速度估计 + 路径绘制）
**至今没有实现跨线计数**（[issue #93](https://github.com/blakeblackshear/frigate/issues/93)，2020 开帖，2026 仍 OPEN）。
当社区问「怎么判断方向」时，**维护者官方推荐的是「两个区域 + 记录进入顺序」**，
而**不是**「画一条线」。见 1.7。

Ultralytics 也是把 `RegionCounter`（每帧重算的占用）和 `ObjectCounter`（跨线累积）
**并列成两个不同的 solution**，并明确说前者是 "current occupancy"、后者是 "running total"。

**人家不是不会做跨线计数，是在「要准确的人数」这个需求下主动不选它。**

**理由一：我们的业务需要的是「在场人数」，而这条路线本身选错了口径。**

跨线计数是**累积量**，它的误差按 Density 的公式传播：
**单项 5% 的漏计 → 在场人数 100% 的偏差**，且一天之内不会自愈。
这是**口径选择**的问题，不是**tracker 质量**的问题。
**只要还在用「进-出累积」，tracker 再好也只是把漂移速度从 5%/天 降到 2%/天——它仍然漂。**

**理由二：我们最大的误差源不在 tracker 里。**

漏检（第 1 位）和遮挡融合（第 4 位）发生在检测阶段，tracker 拿不到证据，无从修复。
Frigate 把 tracker 从 IoU 换成 Kalman+Norfair 之后，维护者自己说遮挡仍然 "very challenging"；
到 2026 年，还有用户报「车被树遮住 3/4 就被认成另一辆车」，维护者的回复是
**这种 bbox 变化"would not be consistent or generalizable"（不值得为此加特例）**。
**换 tracker 是在治一个不是主要病因的病。**

**理由三：我们已经有了一个严格更优的、更便宜的做法，而且它就在我们的代码结构里。**

把 `LineCounter` 换成 `PolygonZone` 式的区域占用。工作量极小（`counter.py` 那个文件本来就只有 60 行），
但**误差传播机制根本不同**：每帧重算，不累积，丢 ID 只影响一帧。

**理由四：投入产出比。**

重写 tracker（Kalman + 运动模型 + re-ID）是几百行、需要我们**没有的 PyTorch embedding 模型**，
收益上限只是「ID 切换率下降」——**而漂移仍然存在**。
这**直接违反**项目 AGENTS.md 的「不要 Overengineering，不要为边缘场景做防护」。

### 6.2 推荐路径（按性价比排序）

**方案 A（首选，改动最小，治本）：把「跨线累积」换成「区域占用」**

- 每个门划一个**多边形区域**（不是一条线），覆盖「门口 + 门内一小块」。
- 人数 = **当前落在该区域内的 person 框数**（去重后计数）。
- 语义直接就是「这间房现在有几个人」，**不需要进/出，也不需要净累积**。
- 关键调整：
  - `max_age`：从 `10` 提到 **接近 Frigate 的 `fps×5`**（若 20fps → 100 帧；若 5fps → 25 帧）。**这一条单独就能缓解"走快丢 ID"。**
  - 加 `inertia`（连续 N 帧在区域内才算在场），防抖。
  - 占用数用「1 秒内的多数表决」或简单滑动窗口，避免单帧跳变。
- `conf=0.15` 可以保留甚至略降——因为**区域占用不怕多一帧的假框**（下一帧就没了），
  而跨线计数怕（假框过线就是永久 +1）。**这正好把 conf 的两难解开了。**

**方案 B（与 A 组合，性价比极高）：加门磁/干簧管做「房间空了」的硬复位**

- 我们场景有天然优势：**一间房一个门**。
- 门磁（干簧管 + ESP32，已经是我们的下位机方案）能给出**门开/关事件**。
- 用法：**门关闭 + 区域内 N 秒无人 → 该房人数硬置 0。**
  这是 Density 的「reset」，但**不需要等到半夜**，每次关门都是一次校准机会。
- 成本：几乎为零（ESP32 已有，干簧管几块钱）。
- 证据支撑：Kim/Moon/Yoon (Building Simulation 2017) 用「一个 PIR + 一个门磁」做到 **99.8%**；
  酒店行业的 Honeywell INNCOM / Telkonet / Salto 全都是这个逻辑。
- **这直接干掉累积漂移——因为累积量被周期性清零了。**

**方案 C（如果 B 加上还不够，或为了演示效果）：mmWave 雷达做在场真值**

- 一间房一个 MR60FDA2（或同类），**只取「有人在/没人」这个二值**，不取人数。
- 与 A 的视觉人数做交叉验证：视觉说 0 但雷达说有人 → 拒绝把人数降到 0（防漏计）；
  视觉说 N>0 但雷达说没人 → 把人数收敛到 0（防误计）。
- 注意别指望雷达数人数（见 3.6，厂商自己说 experimental）。
- 成本：每房 ~$25–35 + WiFi 覆盖。

**方案 D（不推荐现在做）：重写 tracker**

- 收益上限：把 ID 切换率降下来。**但漏检和遮挡融合还在，累积漂移还在。**
- 成本：Kalman + 运动模型 + re-ID，几百行，且**我们没有 PyTorch，re-ID 的 embedding 要另外找模型**。
- 这**违反**项目 AGENTS.md 的「不要 Overengineering，不要为边缘场景做防护」。
- 如果一定要动 tracker，**先只改一个数**：把 `max_age` 从 10 提到 `max(25, fps×5)`。
  这是一行改动，先看效果，再决定要不要更多。

### 6.3 如果坚持「视觉 + 跨线计数」，务实的代价清单

| 要做的 | 为什么 | 代价 |
|---|---|---|
| `max_age` 提到 `fps×5` | 容忍漏检帧，抗快速移动 | 一行；副作用是 ID 保持久，可能串人 |
| 加 `minimum_crossing_threshold`（如 2） | 抗单帧符号翻转（supervision 做法） | ~15 行；代价是响应慢 1–2 帧 |
| 加越线范围限制 | 防远处/画面边缘误计 | ~10 行 |
| 提高检测分辨率或分区域检测 | 治漏检（第 1 位误差源） | RK3588 NPU 算力，可能掉帧率 → 恶性循环 |
| **每日/每次关门定时重置** | 治累积漂移 | 必须做，否则一切白搭 |
| 接受「并排走漏 1 人」 | 斜视 2D 的结构性缺陷 | 无解，只能靠俯视或深度相机 |

**即使全做完，跨线计数仍然严格劣于方案 A。** 因为 A 不需要这些防护。

### 6.4 一句话

**漏计的主要病因是「检测漏检 + 遮挡融合 + 累积口径」，不是「tracker 不够好」。**
**把累积口径换成每帧重算的区域占用（方案 A），再叠一个门磁硬复位（方案 B），
用比写一个 Kalman tracker 更少的代码，拿到结构上不会漂移的人数。**
「重做一个更好的 tracker」是在错误的口径上做优化，投入产出比最低。

## 七、生态成熟度与可持续性（这批东西值不值得依赖）

数据取自 `gh api repos/<name>`，查询时间即本次调研：

| 项目 | Stars | Forks | Open issues | 最后 push | License |

| `tryolabs/norfair` | **2,694** | 280 | 31 | **2025-04-30** | BSD-3-Clause |

**这里有两条相互独立的结论：**

**（1）计数这件事本身是「已解决问题」，不要自己造。**

Frigate 3.6 万星、supervision 5.1 万星、两者都在**调研当天**还有提交。
Frigate 的 tracker 调试经验（`min_score` 的两难、`inertia` 去抖、`max_disappeared = fps×5`）、
supervision 的 `LineZone`（`minimum_crossing_threshold`、越线范围限制、未确认轨迹不计数）
都是**别人踩完坑沉淀下来的默认值**。

按 solution-research 的原则：**「找谁解决过」优先于「我来做这个」**。
我们要的那几个机制，**在 supervision 的 `LineZone` 里是现成的参数，在 Frigate 里是现成的配置项**。

**（2）但 Norfair 是停更的——这是一个真实的依赖风险。**

Norfair 最后提交 **2025-04-30**（`e517b42`，bump to v2.3.0），距今**约一年半**，
而 Frigate 的 HEAD 是 2026-10-16。Frigate 通过 `docker/main/requirements-wheels.txt:34` 依赖它：

```
norfair == 2.3.*
```

**解读要克制，但风险要讲明：**

- 对 Frigate 而言，Norfair 已经"够用且冻结"——2.3.0 之后没有新需求，属于**成熟到不再改**，
  不必然是"死了"。Frigate 仍在活跃开发且未替换它。
- 但如果**我们**打算直接采用 Norfair 作为追踪库，就要接受：**上游不再修 bug、不再跟进新 Python/新 numpy**。
  `norfair` 的 31 个 open issue 会长期挂在那里。
- 好在 Norfair 的算法本身（Kalman + 距离函数 + 匈牙利匹配）是教科书内容，
  **真要用，量也不大，自己按需实现一个最小子集反而更可控**。
  这也符合项目「代码要短、可读」的要求。

**（3）生态维护者与资金**

Frigate 的 `FUNDING.yml` 只有 GitHub Sponsors 的三个人：

```yaml
github:
  - blakeblackshear
  - NickM-27
  - hawkeye217
```

即 **Frigate 是个人主导 + 赞助模式**（不是 CNCF / Linux Foundation / 大厂）。
它有一个商业侧面 **Frigate+**（付费定制模型订阅），但**核心功能完全开源且不依赖 Frigate+**。
从 issue 响应看（维护者在 `discussion #8366`、`#16697` 里都亲自且迅速地给出了技术解释），
**项目健康度是好的**，但**别指望厂商级 SLA**。

**（4）值得注意的新鲜度信号**

- supervision 的 `LineZone` 文档在**近期**还在演进（`minimum_crossing_threshold` 的语义说明写得非常细，
  包括"临时缺失的帧既不算扩展也不算重置"这种边角），说明这块逻辑**是被真实需求反复打磨过的**，
  不是一次写完就烂在那里。这对我们很有价值——**这些边角正是我们会踩的坑。**
- Frigate 的 tracker 在 0.13 做过一次大换血（IoU → Norfair）并附带 `inertia` 等机制，
  说明**这条路他们已经走过一遍并留下了经验值**。
