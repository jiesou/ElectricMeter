## 一、身份：只有一层

**决策**：`ref = deviceId:key`，例如 `esp-301:light`。

- deviceId 是一台 ESP32，定下来
- key 是设备内的回路号（`light` / `socket` / `ac` / `light_power` …）
- name 是显示名，随便改，服务器不较劲
- 实体**可以**增删，设备自报什么就是什么，不再上报的直接摘掉

**否掉的方案**：HA 的 `unique_id` + `entity_id` + `device_id` + `area_id` 四层 ID。
那是给「几千个实体、几百个集成」的通用平台设计的。

---

## 二、device 是一等公民

**决策**：一台 ESP32 = 一个 device。在线/离线是 **device 的属性**，不是实体。

**否掉的方案**：`binary_sensor.<device>_connectivity` 那种做法。
ESP32 在不在线，是连接层的事实，不该占用一个实体。

---

## 三、area 整个概念不要

**决策**：整个项目只有「一台设备管一间房」，删掉 area。

- 删掉 `area` 表、`device.area_id`、`Area` 类型、`/api/areas`、`Target.area`
- 「整房断电」的能力不丢：它本来就等于「对这台设备的所有开关下令」，
  所以 target 从 `area` 变成 `device`

**否掉的方案**：HA 的 area registry（扁平、不可嵌套、可独立寻址）。

---

## 四、实体只有两个字段描述

**决策**：

```ts
kind: "relay"   // 一路可通断的回路
      | "meter" // 一只读数
```

**没有 `unit` 字段。** 瞬时功率和累计电量天生就是两个量，设备各发各的：

| key 后缀 | 含义 | 单位 |
|---|---|---|
| `xxx_power` | 实时功率 | 瓦 |
| `xxx_energy` | 自上电以来的累计电量 | 千瓦时 |

下位机把电量在板上就累加好了，服务器只管存。

服务端按 key 后缀判断读数语义，代价只在服务端两行。

**否掉的方案**：

- HA 的 `domain` / `device_class` / `state_class` 三层分类学
- `unit` 字符串字段 —— **在单片机上是实打实的负担**。字符串拼接和解析要占 MCU 内存，
  能少一个就少一个。这块工作量要压到最小

## 五、通信协议：四条基座

**用户给的协议基座，任何业务消息都从它展开，不要另立消息体系**：

```ts
export interface WSMessage {
  type: string;
  ts?: number; // 秒
  [key: string]: unknown;
}
export type WSMessageHandler = (client: Client, socket: WebSocket, message: WSMessage) => void;

/* XX PostMessage      客户机->服务器 post新数据 */
/* XX PostAckMessage   客户机<-服务器 回馈成功失败 */
/* XX GetMessage       客户机->服务器 get数据 */
/* XX GetAckMessage    客户机<-服务器 返回数据 */
```

**线上就四种消息，外加应用层 ping**：

| 消息 | 方向 | 时机 |
|---|---|---|
| `post_entities` | 设备 → 服务器 | 连上后一次，声明自己有什么 |
| `post_state` | 设备 → 服务器 | 500ms 一条 |
| `post_relay` | 服务器 → 设备 | 下通断令 |
| `post_ack` | 双向 | 回执 |
| `ping` | 双向 | 应用层心跳 30s |

**配套约定**：

- 下位机只出站，`ws://host/ws?deviceId=xxx` 建连时绑定身份，**消息里不再重复带 deviceId**
  （一个连接一个身份，建连时定死不可中途改；消息里再带一份就多一个能骗人的地方）
- `WSMessageHandler` 数组，谁关心谁注册；不做按角色的 switch 分流
- **没有 `hello` / `welcome`** 这类握手消息，身份在 URL，能力在第一条 Post
- **回执不做 `ref` / `callId` 关联**，收到几个算几个
- **应用层 ping 要留**。WS 协议自带的 ping/pong 检测不到半开连接（拔网线那种）

**否掉的方案**：

- `welcome` 里带 `snapshot` —— 没人用，CLI 走的是 REST 快照
- 按 role 分流（meter / sense / console）—— 那份稿子已经弃用，见 `../research/WS通信架构-*.md`
- 归零 `requested`、清 stale 命令等握手期状态机

## 六、不做粘连判定

**决策**：**现在不判断接触器粘连。**

- `requested` 字段删掉，动作入口不做「服务器下的令 vs 设备回报」的对账
- 板子只做三件事：收 `post_relay` 动继电器、回 `post_ack`、下次 `post_state` 报实际值
- 板子**不知道自己粘没粘**，也没有资格说自己没执行

**如果将来要做**，正确的判据只有一个：**下了动作之后，功率数值有没有变**。
不是拿服务器的命令和设备的回执对比。

**这是一次 agent 判断错误**：早期实现用 `requested ≠ state` 判粘连，逻辑不成立。
ESP32 回报什么它就报什么，那是它观测到的实际状态，不是执行结果。

---

## 七、只有一个 action 概念

**决策**：没有 `service`。动作就是 `POST /api/actions/{turn_on,turn_off,toggle}`，
body 里 target 是 `entity` 或 `device`。

**否掉的方案**：`POST /api/services/switch/turn_off`。
已经有 action 了，为什么还要一个 service。

---

## 八、落盘：500ms 采样，5 秒一个桶

**决策**：

- 模拟器 500ms 一采，服务器收到就往 SSE 推，实时曲线顺滑
- 收到采样只改内存里**未闭合的 5 秒桶**，桶跨过整 5 秒才写一次库
- 30 天保留，约 1 GB —— 演示优先，这个体积换得起
- **原始样本一律不落盘**

**均值按时间加权**：`Σ(值 × 持续秒) / 窗口秒`，不是 `AVG()`。
电水壶这种占空比负载两者能差 1.5 倍。

**电量两个来源**：板上累加的 `*_energy` 累计读数（权威），
和服务端对 `*_power` 的时间积分（分辨率更细）。总表 `total_energy` 可以跟三路加起来对账。

**states 表只记开关**：高频读数一律进 statistics，states 只留「什么时候开的、什么时候关的」。

**否掉的方案**：

- 60 秒桶 —— 演示效果优先，5 秒的波形才看得出电水壶
- 5 秒 / 60 秒两档 + rollup —— 当时被判定为过度工程
- Ctrl-C / SIGINT 特殊处理 —— **「该怎么死就怎么死，不需要处理任何 Ctrl-C」**。
  为了「反复重启不丢数据」去写信号处理是自找的复杂度
