# 数据模型与协议

- 数据模型：类型定义在 `shared/types.ts`，全局共享
- 协议：WS 消息就是这几样东西在线上的样子，增量覆盖
- 数据库表结构： `server/prisma/schema.prisma`

## 项目模型

一台 ESP32 管一间房，负责采集电能数据和控制断路器；服务器负责管理实体并下发通断动作。

## 身份

两大一等公民：

- Device 的身份是 `id`。
- Entity 的身份是 `device_id` + `id` 两个字段。

- `shared/types.ts` 类型定义是数据模型的真理之源，现已定死。
- 数据库结构顺着类型定义走
- **实时读数一律不落库。** 数据只是经过服务器：服务器信任下位机报来的值，不加工、不积分、不聚合。

## 消息基座

> 命名灵感借鉴自 MQTT PUBLISH / PUBACK 的命名模型

| 基座 | 含义 | type 前缀 |
|---|---|---|
| `pub` | 发布业务消息 | `pub_` |
| `ack` | 回复对方的发布消息 | `ack_` |

基座不编码消息方向。业务类型由基座前缀和业务名组成，具体方向由消息流程决定。

## 消息例程 example

> 具体消息类型也应该直接落到 `shared/types.ts` 里去
> 以下只是举几个规划的例子例程，不一定实际用到

| type | 方向 | 时机 |
|---|---|---|
| `pub_alive` | 设备 → 服务器 | 应用层心跳，30s 一次 |
| `ack_alive` | 服务器 → 设备 | 心跳回复 |
| `pub_entities` | 设备 → 服务器 | 连上后一次，声明自己有什么（带 `name` / `model`） |
| `pub_entities` | 设备 → 服务器 | 之后哪个实体变了补一份，没提到的保持原样 |
| `pub_action_switch` | 服务器 → 设备 | 下通断令，说明要哪个实体到什么状态 |
| `ack_action_switch` | 设备 → 服务器 | 设备确认执行完成 |

- 增量报文里没有的字段，是「没变化」，不是「变成空」。
- 报文里出现什么字段就更新什么字段，服务器不做字段之间的换算。
- `ack` 不携带关联 ID。

## 连接与身份

- 下位机通过 `ws://host/ws?device_id=xxx` 出站连接，身份绑定在 URL 中。
- 设备连上后以一条简单的 `pub_entities` 声明实体。
- WSMessageHandler 谁关心谁注册：服务端使用 `WSMessageHandler` 数组，按消息类型注册处理器，`routes/core/*.ts` 中，什么业务需要，就注册什么处理器

## 动作 Action

动作入口为 `POST /api/actions`，目标是 `entity_id` 或 `device_id`（也许将来？）。

## 数据库落地

- 表就两张：`Device` / `Entity`，顺类型定义走，见 `server/prisma/schema.prisma`。
- 库是底账，内存里那张设备表是它的运行期镜像：服务器启动时全读一遍，之后只有连接（`ws` / `online` / `lastSeen`）停在内存里。
- 读数（`state` / `powerW` / `energyKwh` / `lastUpdate`）落在 `Entity` 行上，报来一次写一次；REST 只读内存那张表。
- 设备名由**服务端**分配，设备报文里不带设备名；实体名由设备申报。
- 运行期只有 Prisma Client（`@prisma/adapter-libsql`，Bun 跑不了 better-sqlite3），不再有手写 SQL；建库 `bun run db:push`。
- 测试跑在独立测试库（`server/.env.test`），`bun run test` 先 `--force-reset` 出一份干净库。
