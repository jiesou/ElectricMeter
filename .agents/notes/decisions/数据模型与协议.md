# 数据模型与协议

类型定义只有一份：`shared/types.ts`。报文是它的线上样子，数据库表结构跟着它走，服务器内存那张表是它的运行期样子。

## 模型

一台 ESP32 管一间房：采集电能数据，控制断路器。服务器管实体，下发通断动作。


两大一等公民：

- Device 的身份是 `id`。
- Entity 的身份是 `device_id` + `id` 两个字段。

- `shared/types.ts` 类型定义是数据模型的真理之源，现已定死。
- 数据库结构顺着类型定义走
- **服务器信任下位机报来的值**，不加工、不积分、不聚合。读数落在 `Entity` 行的当前值上，历史快照见「历史记录与统计」。

## 消息基座

> 命名灵感借鉴自 MQTT PUBLISH / PUBACK 的命名模型

| 基座 | 含义 | type 前缀 |
|---|---|---|
| `pub` | 发布业务消息 | `pub_` |
| `ack` | 回复对方的发布消息 | `ack_` |

基座不编码消息方向。业务类型由基座前缀和业务名组成，具体方向由消息流程决定。

## 消息例程 example

> 具体消息类型也应该直接落到 `shared/types.ts` 里去
> 以下只是举几个规划的例子例程，不一定实际用到

| type | 方向 | 时机 |
|---|---|---|
| `pub_alive` | 设备 → 服务器 | 应用层心跳，3s 一次 |
| `ack_alive` | 服务器 → 设备 | 心跳回复 |
| `pub_entities` | 设备 → 服务器 | 连上后一次，声明自己有什么（带 `name` / `model`） |
| `pub_entities` | 设备 → 服务器 | 之后按字段部分更新，没提到的字段保持原样 |
| `pub_entities` | 服务器 → 设备 | 替房间报的读数（人数）原样下发给那间房自己的设备 |
| `pub_name` | 服务器 → 设备 | 房名：连上补一份，网页上改名再推一次 |
| `pub_action_switch` | 服务器 → 设备 | 下通断令，说明要哪个实体到什么状态 |
| `ack_action_switch` | 设备 → 服务器 | 设备确认执行完成 |

- `pub_entities` 是字段级的部分更新：报文里出现的字段才更新，没出现的字段保持服务器上的原值。
  - 注意，**部分更新不是增量更新**，避免项目中的任何地方计算diff
  - **数据有更新就推送更新后的数据，而不是N秒钟轮询一次，像这样形成一条流，这样就没有任何地方需要计算diff了**
- 没出现不等于空：`powerW: 0` 表示功率为 0，报文里没有 `powerW` 表示本次不更新功率。
- 除 `id` 外所有字段都可以缺，`id` 之外一个字段都不带的报文合法但没有意义。
- 报文里出现什么字段就更新什么字段，服务器不做字段之间的换算。
- 每条实体的归属：`e.device_id ?? 连接的 device_id`，两处都没有就丢掉这条。
- 替房间报的读数（人数）服务器原样下发给那间房自己的设备，设备刚连上时补一份当前的数 —— 矩阵屏这类只读的消费端不订阅、不轮询，等推就行。
- 房名由服务器分配：连上推一条 `pub_name`，`PATCH /api/rooms/:device_id` 改名后再推一条，设备屏幕照它显示，不在固件里写死。
- `ack` 不携带关联 ID。

## 下通断令

- 网页点闸 → `POST /api/entities/:device_id/:id/switch`（body `{state}`）→ 服务器给那台设备发一条 `pub_action_switch` 就返回，**不挂着等回执**。
- 设备翻闸后回 `ack_action_switch`（带它自己的 `ts`）。**服务器上的 `state` 只有这一个写入点**：ack 处理器写内存、写库、推 SSE，网页那边的新状态是 SSE 推回来的。
- 所以闸的真相在下位机，服务器和网页都只是听回执。
- 未知设备 / 未知实体 / 不是开关 / 设备离线：REST 直接 404 / 400 / 409，不下发。

## 两层时间戳

全部时间戳都是 **number 毫秒级时间戳**（`Date.now()` 的口径），不出现任何特定时间格式。

两个 `ts` 各管一摊，不冲突：

- `WSMessage.ts`：**通信层的时刻**，这条报文什么时候走的，心跳保活这类用。
- `Entity.ts`：**业务层的时刻**，这个读数是什么时候产生的，即「实例存在的时间点」。

读数时间**由设备说了算**：`Entity.ts` 是设备报上来的，服务器不覆盖、不加工（与「服务器信任下位机报来的值」一致）。

一轮 RS485 采集约 290ms，三只表是分开读的，所以 `Entity.ts` 精确到毫秒，同一轮里三只表各有各的时刻。

### 对时

时间基准只有服务器一个：`pub_alive` 心跳（3s 一拍）的回包 `ack_alive` 里带着服务器的 `ts`，下位机收到就记下「服务器毫秒 + 当时的 millis」，之后 `now()` = 基准 + millis 增量。下位机不连外网 NTP，没有外网也能对时；局域网单向延迟几十毫秒以内，而读数点间距是 ~290ms，忽略不计。

还没对上时 `now()` 返回 0，报文里就不带 `ts`（`if (e.ts)`），服务器沿用旧值 —— 与「没出现不等于空」的字段语义一致。

## 连接

- 下位机通过 `ws://host/ws?device_id=xxx` 出站连接，身份绑定在 URL 中，缺了直接抛（`app.onError` 统一回 500）。
- **实体算哪台设备名下由报文里的 `Entity.device_id` 说了算**，报文没带就用这条连接的 `device_id`。
- 大屏也走这条路：随便报个 `device_id`（如 `bigscreen`）连上来，服务器不认人、不做特判，它报的实体归谁全看报文里的 `device_id`。
- 设备连上后以一条简单的 `pub_entities` 声明实体。
- WSMessageHandler 谁关心谁注册：服务端使用 `WSMessageHandler` 数组，按消息类型注册处理器，`routes/core/*.ts` 中，什么业务需要，就注册什么处理器。

## 数据库落地

- 四张表 `Device` / `Entity` / `EntityHistory` / `EnergyUsageTime`，见 `server/prisma/schema.prisma`。
- 库是底账，内存那张表是它的运行期镜像：启动全读一遍，之后只有连接（`ws` / `online` / `lastSeen`）停在内存里。REST 只读内存。
- 读数落在 `Entity` 行上，报来一次写一次；账本（`EntityHistory` 的 `powerW` / `energyKwh`）与入住区间（`EnergyUsageTime`）见「历史记录与统计」与「统计与入住记录」。
- 设备名由服务端分配，报文里不带；实体名由设备申报，没报就用 `id`。
- 运行期只有 Prisma Client（`@prisma/adapter-libsql`，Bun 跑不了 better-sqlite3），没有手写 SQL；建库 `bun run db:push`。
- 测试跑独立测试库 `server/data/electric.test.db`：`bun test` 自带 `NODE_ENV=test`，`db.ts` 认它选库，从哪个目录跑都落到测试库；根目录 `bun run test` 先删掉测试库文件重新建一份，再全跑。
